# Run a round's test modules in small runs, nearest first

Status: accepted

The executor replies once for a run and the store takes a run whole (ADR-0002), so a result waits for its run's end and an interrupted run stores nothing. Measured on 2026-10-02 over a consumer written for it (610 test modules in one workspace, Vitest 4.1.11, Node 24.19.0, Windows 11, a Ryzen 7 8700F with 16 logical CPUs): five test modules put first in the workspace's run had their results after 1.5 s, and the run ended at 38.9 s; a run of 50 modules aborted once 25 had finished lost 3 s of work. On Fleet Cooling a save during its 207 s Convex run loses all of it, and every save restarts it.

A round sends each due workspace's due test modules as runs of at most 50 modules (a target until measured on Fleet Cooling). Each is an executor job of its own, in a new executor process, that replies once and is stored whole (ADR-0010). The first run holds the modules nearest the edit and no other, however few they are: the test modules that changed, then those whose usable load record holds a changed file (ADR-0011). The modules whose latest result failed follow, then the rest in the discovery's order. So the nearest results are stored when a run of those modules alone ends, a change interrupts and loses at most the run in progress, and the daemon plans again between two runs, so a newer edit's nearest modules go first. The load record only orders here: every due module still runs, and under a Vitest install with no confirmed reading of the record canaries the order leaves the record out.

Each run pays its own process start, Vitest load and first transforms. On the consumer above a run of 50 modules alone took 4.51 s, against 3.2 s for each 50 of the workspace's own run (38.9 s for its 610), so about 1.3 s more for each run. On Fleet Cooling 38 Convex test files run alone cost 0.30 s a file against 0.33 s a file for the whole suite of 583, so its 12 runs of 50 are computed, not measured, at about 16 s more than its 191 s. A project's global setup runs once for each run.

Rejected: sending each module's result from the executor as it finishes. It reports results one by one and pays no cost per run, but it needs a message before the job's reply, a run stored in parts, a settle rule for part of a run, and it rests on the order in which Vitest starts the files it is given, which was measured on 4.1.11 only. Rejected: one Vitest instance kept open between runs (0.29 s against 1.30 s for one module, measured). It needs a process that outlives its job (ADR-0002, ADR-0006), a guard that re-reads every cached module before each run, and a reopening on every config or setup change, to remove about 1.0 s of each run; it stays a later choice.
