## Current implementation

### Core: evidence and test identity

`packages/core/src/evidence.ts` assesses a historical result against a caller-supplied fingerprint. It preserves the outcome and returns freshness plus an explicit current-pass predicate. Missing or empty fingerprints produce unknown freshness. `packages/core/src/test-identity.ts` gives each test of one module a test identity (its Vitest workspace, Vitest project, module path, suite and test names, and its position among tests sharing those names), and marks a test whose names repeat in its module as a duplicate.

### Vitest discovery and runs

`packages/daemon` holds Vitest discovery and runs.

#### Workspace listing

`findVitestWorkspaces` lists a consumer's Vitest workspaces from the root `package.json` `workspaces` field and config file names (a `vitest.config.*`, or a `vite.config.*` in a directory whose `package.json` depends on Vitest), reading files only; it reports a root `pnpm-workspace.yaml` and each pattern it cannot expand as not read. Apart from those, it lists as not covered each package workspace other than the root whose `package.json` has a string `test` script, which holds no Vitest config file and lists no Vitest in its `dependencies` or `devDependencies`, with a reason quoting the script. It lists no directory that a `workspaces` pattern resolves outside the consumer root, through `..` or a link, deciding by canonical real path, and reports each such directory as not read with the real path it resolves to, so only the started project's own directories are loaded. When entries reached by different paths resolve to the same canonical real path, it lists only the first in pattern order, the consumer root first, and reports each later one as not read, naming the workspace listed in its place; a pattern that repeats a path already examined adds nothing. So no directory is loaded or run twice.

#### Test discovery and reported project facts

`discoverTests` loads each workspace's own Vitest, 4.1.x or 5.x, collects the modules of every project without running a test body or hook, and returns each test with its identity. It reports modules and workspaces that failed to load, workspaces with no supported Vitest, browser-mode projects, and typecheck modules, each as not discovered; it keeps each not-covered workspace in which none of its discovered workspaces' tests or failed modules lies, which the summary and status name as `workspace-not-vitest`; it never collects a typecheck module. For each workspace it discovers, it also reports, per project not in browser mode, the project's setup files and global setup files as root-relative paths (a file outside the root climbs with `..`, or on Windows names its other drive), leaving out RT Test's snapshot guard and crediting the root project's global setup to every such project, since Vitest runs it on every run; the project's Vite root; each alias of the project's resolved config in order: its `find` (a RegExp as its source text and flags), its replacement, and whether it has a `customResolver`; and the project's `include`, `exclude` and `includeSource` patterns with the directory they match from, both root-relative and as Vitest's glob spells it, and, for each `include` and `includeSource` pattern, the directories before its first glob segment (or the file a pattern with none names) as the pattern spells them, with the root-relative path that spelling resolves to, and each directory link found below those directories by a walk that follows at least every link Vitest's crawl follows, as the crawl spells it, with the root-relative path it resolves to, or why those links are not known.

#### Workspace runs, interruption and force-stop

`runWorkspace` runs one workspace's tests on that same Vitest and records each test under the identity discovery gives it, with its outcome (passed, failed, skipped or error) and whether it finished or was interrupted as separate fields. It records modules that failed to load, hook errors on their module, crashed modules, modules not run and the run's unhandled errors apart from test outcomes, and gives a run in which no test passed or failed the reason nothing ran. The caller's `AbortSignal` interrupts a run, and a run Vitest stops itself under the consumer's `bail` is interrupted too. `discoverTests` takes an `AbortSignal` as well: once it aborts, discovery loads no further workspace, interrupts the collection in progress, and rejects with the signal's reason after the Vitest instance has closed and the host is restored, so an aborted discovery has no result. When a run or a discovery has not ended `FORCE_STOP_GRACE_MS` (10 s) after its signal aborted, Vitest force-stops its workers, which skips the project's `afterAll` hooks and teardown, and each run that loaded its workspace records whether that happened in a field beside its execution state. Work on Vitest's own thread, such as config loading or `globalSetup`, is beyond that force-stop.

#### Host and consumer isolation during discovery and runs

Discovery and runs share one queue, so none overlaps another, and each restores the host's environment and exit code. Each also runs in its workspace's directory, as that workspace's own `vitest` does, and restores the host's working directory with its environment. Neither writes into the consumer's tree. Each forces coverage, snapshot updates, Vitest's results cache and its module cache off over the workspace's config, so a snapshot assertion with no stored snapshot fails its test. Each also puts a setup file first in every project that keeps the project's snapshot environment, the consumer's own included, from saving or removing a snapshot file, since under update none Vitest still rewrites a snapshot file holding an entry no test checked; snapshots are still read through that environment. Each also names the config file Vitest would load and loads it through Vite's runner loader when Vite treats it as ESM, or otherwise through Vite's bundle loader, which writes nothing for a CommonJS config. Vitest's forks pool copies each transformed module into a directory under the OS temp directory for its workers, outside the consumer's tree, and removes it at close; a falsification job turns those copies off. Writes made by the consumer's own code (test bodies, hooks, setup files, `globalSetup`, plugins and config code) are the consumer's own. So is the debug dump a consumer asks Vitest for with `server.debug.dump` or `VITEST_DEBUG_DUMP`: Vitest creates the dump directory under each project's root (`.vitest-dump/` unless the setting names one) in a discovery and in a run, and where a run ends, each run of a falsification job included, writes `vitest-metadata.json` there, which holds module paths and transform durations and no source text. Five documented exceptions remain, all under `node_modules`: Vitest 4.1 on Vite 6.0.x, which has no runner loader, leaves an empty `node_modules/.vite-temp/`; a consumer that turns on Vite's dependency optimizer gets its cache in `node_modules/.vite/vitest`; a workspace whose project config files differ in format from its root config leaves `node_modules/.vite-temp/` for an ESM project config under a CommonJS root, and fails to load, as a failed workspace, a CommonJS project config under an ESM root; a Vitest 4.1 project config that itself sets `experimental.fsModuleCache` gets the module cache written; a falsification job refuses such a workspace; and Vitest 5, which creates its API token file whatever `api: false` says, writes it to `node_modules/.vitest/` when it cannot write the user data directory.

#### Confirmed start gate on discovery and runs

Both load Vitest configs and import test files, so only the daemon's executor process calls them, after an explicit start. Each takes the start the user confirmed: it loads only a workspace whose path and chosen config file match a confirmed entry, and makes that match again as each workspace is loaded, so a config file added or swapped after the start is never loaded. Discovery lists every other workspace as not discovered, with the reason "not confirmed at start", and a run whose config file no longer matches loads nothing and is not stored.

#### Falsification jobs

`falsifyWorkspace` runs one workspace's defect experiments in one Vitest instance, and is given the error names that count as assertions beside the two forms Vitest marks itself (the `assertionErrors` the `falsify` request carries). It loads the instance through the same confirmed-config gate, host restore, no-write options and snapshot guard as a run, and it executes project code. Each experiment names a defect, its intended test's identity and its mutation: an absolute file, the exact `old` text and its `new` replacement. Before any run, the job reads each mutation's file once. It counts `old` there with the anchor matcher (`falsify/anchor-match.ts`), which counts non-overlapping and matches a line break in `old` to LF or CRLF, writing `new` with the line ending the match used. It applies the mutation in memory and places its reach probe. An experiment is recorded not run, with its reason, when its file cannot be read, its anchor does not occur exactly once, its change has no probe site, or no resolved test module holds its test; a test in a browser-mode project or a typecheck module reads as held by no module. When every experiment is decided this way, no run happens and the record holds no baseline. Otherwise the job runs the baseline over the intended tests' modules. It runs each remaining experiment over its test's whole module, the baseline's own specification, but only when the baseline passed that test, found by its full identity; otherwise the experiment is recorded not run with the state the baseline gave the test, or that the baseline did not report it, or that the baseline left no record. An experiment whose run would be a detection ([ADR-0008](adr/0008-detection-from-task-facts-and-canaries.md)) runs once more at once, as its confirming run: over the same specification, with its own mutation alone, behind the same guard and abort check, before any other experiment and before the restored baseline. No other experiment runs twice, and none runs a third time. Once any experiment's run has left a record, the job runs the restored baseline over the baseline's modules. `globalSetup` runs once for the job.

Before its first run the job prepares the loaded instance:

- It forces isolation per test file and turns `bail` off in every project, whatever the workspace configures.
- It wraps each project's module fetcher, so the forks pool never copies a transformed module to the OS temp directory.
- It places the reach setup file first in every project.
- It wraps `pluginContainer.transform` in every environment of every project's Vite server and of the root's, which on Vitest 4.1 is a server of its own.

That wrap applies the active experiment's mutation to the module's plain id as Vite hands the module's text to its first plugin. It does so only while that experiment runs, and only when `old` occurs there exactly once. It records a digest of each text it passes on. Before each run, the stale-transform guard invalidates every module of the previous and the next mutated file, cached or still being transformed, so a mutated transform in flight when its experiment ended is discarded rather than cached. It also invalidates every module still cached from text other than its file's text now, or from text the guard never saw, a soft-invalidated module included. A run that would still read one is not started, and the record names the modules. A workspace in which a project keeps an on-disk module cache on runs nothing, and the record names each such project and its setting: on Vitest 4.1, a project config that sets `experimental.fsModuleCache` itself, and on Vitest 5 a project whose `fsModuleCache` is still on after the session's override. A preparation that cannot be installed also runs nothing. The job records which.

The reach probe (`falsify/reach-probe.ts`, placed by `falsify/probe-step.ts`) is a guarded call to a recorder that the reach setup file defines. It stands at the start of the step that holds the change, so its firing means execution reached that step, and says nothing of which part of the step ran. The mutated text is parsed with the dependency build's parser, and the step is the innermost statement that holds every changed character. In a statement list (a program's, a block's, a static block's or a `case`'s) the probe is a statement written just before that statement, after the list's directive prologue, or ending the list when the change follows its last statement. A statement standing alone as a branch or a loop's body becomes a block that starts with the probe, and a label stays with the statement it names. A change before a `case`'s first statement or after its last belongs to the step around the `switch`, and a statement inside a namespace to the step around the namespace. A change in a function outside every statement of its body (its parameters, its name, an arrow's expression body) is probed at the head of that body, an expression body as the first member of a comma expression, and a class field's initializer the same way, so a probe stands inside every function that holds the change and never fires where that function is defined. A function with no body is no step. Text a mutation removed has no extent in the mutated text, so the unmutated text is parsed too: the step holds the written text and the start of the step that held the removed text, and where the removed text began a step that is entered at its first character, as a function is, what stands there in the mutated text holds the change. A probe only inserts text, and adds no line break. No probe is placed inside an ambient declaration, in a hashbang line, in a module the mutation leaves with no statement, or where the parser rejects the text with the probe written in. Such a change is reported by the line and column where it starts with a node kind and role, and mutated text that does not parse by the line and column of the parser's first error or by its bracket nesting, never by source text or the parser's message. The setup file marks each test it runs for as observed. It marks the running test when the probe fires in the test or in its `beforeEach` or `afterEach`. When the probe fires outside any test, it marks the tests of the file or suite that was current. When it fires while several tests run together, it marks those tests unattributed. The marks return through test metadata.

Each run's record holds facts only from the modules of that run's own specifications that Vitest queued during it:

- each module's state, and its module and suite errors; a specification with no queued module is recorded missing, and a module a worker never collected with its state alone;
- each test's identity, mode, state, the repeats Vitest was told to give it when it has any, hook states, and errors as Vitest serialized them, with a bigint written as text and a cycle or nesting past 32 levels named, since the record crosses the executor's channel as JSON;
- reach, for an experiment's tests: executed in the test, executed outside the test, not executed, or unknown, because the setup file never ran for the test, the firing could not be attributed, or the mutation was served without a probe;
- the run's unhandled errors;
- for each unhandled error, the run's modules whose file the worker that raised it was running, read from the test file path Vitest stamps on the error and matched to the run's specifications by file as Vite keys a module's file: several when one file runs under several projects, and none when the error names no file of the run;
- whether the run was interrupted or force-stopped, and any cancel error.

An experiment's record also lists each transform of its mutated module: applied with or without a probe, or not applied with the count of `old`. An empty list means the module was never loaded. The record of an experiment whose run would be a detection also holds its confirming run: its record and transform list, or that it left no record, or that an abort interrupted it. An experiment's record also carries `mutationFileDigest`, a digest of its mutation file's text as the job read it when it started: `wholeDigest` of the file read whole as UTF-8, a byte order mark and its line endings kept. Every record carries it, whatever its status and its reason, except one whose file the job could not read. A file edited later in the job keeps the start text's digest on its record, and the record holds no part of the text. A run that throws is recorded as failed, and the other runs keep their records. The job's record carries the workspace's Vitest version, `FALSIFIER_VERSION`, the host-thread rejections and the instance's close error; a job whose workspace loaded reads `ran`, also when no run happened, or `refused`, and one that loaded nothing reads not confirmed, unsupported, failed, or interrupted before load. Each run reads the abort before it asks the guard, so an abort that came first reads interrupted whatever the guard would find. An abort ends the job at the run in progress, a confirming run included: the reply is marked interrupted and holds only the runs that finished, with no restored baseline. An experiment whose first run the abort ended, and every experiment after it, reads interrupted; one aborted in its confirming run keeps its first run's record beside a confirming run marked interrupted. The record keeps error messages raw, and stripping source text before anything is stored belongs to the evidence store.

Once the instance has closed, so the host thread's rejections and the close error are known, a job that read `ran` judges every experiment it was given and carries one judgement per experiment, in the order given: a verdict (`detected`, `survived`, `invalid-experiment` or `unclear`) or none, one reason from a closed set for every judgement but detected and survived, a detail where the reason has one, and the facts it was decided from. A job that did not read `ran` carries none. The facts (`falsify/fact-types.ts`, built from the raw records by `falsify/run-facts.ts`) hold states, kinds, names and counts, and never an error's message, its stack or source text; a fact a run did not record is absent. For the experiment's run, its confirming run and both baselines they give the intended test's state, mode, the repeats it declares, hook states, and each of its errors as a kind with the name Vitest serialized: an assertion, with what made it one (the name `AssertionError`, the `JestExtendError` constructor with an assertion name, or a declared name), or another kind. For the experiment's runs they also give its reach. Of the intended test's module alone they give whether it was collected, its module error count and its failing suites by name path; of the run, its unhandled error count and how it ended. A baseline's facts also count the unhandled errors that count against the experiment, those naming its test's module and those naming no test module of the baseline, and how many of those named none. The facts also give what each transform of the mutated module did in each of the experiment's runs, why the job gave an experiment no run, the job's own unhandled error count and whether the instance closed, and, for an experiment whose confirming run left a record, whether the run the job started next left a record, with its unhandled error count; a run the guard refused never started and is passed over. The judge (`falsify/verdict.ts`) is a pure function of those facts that loads neither Vitest nor a file, and reads an experiment's first run and its confirming run by one reading. It decides whether an experiment has a verdict before which, except that no probe site, no module and a baseline that did not pass read invalid experiment whether or not a restored baseline ran; then baseline trouble before the experiment's own runs; then the experiment's run, in the order that follows. No verdict: `interrupted`, `mutation-file-unreadable`, `anchor-count`, `baseline-unrecorded`, `run-unrecorded`, `confirming-run-unrecorded`, `restored-baseline-unrecorded`. Invalid experiment, the first that holds: `no-probe-site`, `no-module`, `baseline-not-passed`, `baseline-not-clean`, `restored-baseline-not-passed`, `restored-baseline-not-clean`, `run-not-clean`, `module-failed`, `suite-error`, `test-not-run`, `hook-not-passed`, `test-repeated`, `site-not-executed`, `reach-unknown`. Unclear, the first that holds: `not-an-assertion`, `unhandled-error`, `confirming-run-differed`, `next-run-unclean`, `job-unclean`.

`packages/daemon/canaries/` holds RT Test's canary fixtures: a Vitest project named `canaries` whose config includes only its `*.canary.mjs` modules, plain `.mjs` files that import no package but `vitest`, and `canaries.json`, which names the project, the assertion error names the set's job is given, and for each canary its intended test, its mutation and the judgement it must read (the verdict, and the reason where it has one), in the order the job runs them. That order carries a case: the canary that leaks an unhandled rejection comes directly after a canary that does not read detected, which its run's error would otherwise make unclear, and is not the last, so a late report of its error cannot land in the restored baseline. Every canary's test passes unmutated, and this repository's own suite does not collect the canary modules.

Known limits, each making an experiment invalid rather than detected unless it says otherwise:

- code a test runs in a child process reads the mutation as never loaded;
- so does a module served outside Vite's transform pipeline, and a mutated file whose path holds `#`, or `?` on Linux;
- a file the parser cannot read has no probe site;
- a step reached only in an `afterAll` reads not executed;
- reach is of the step, so a test that reaches the step without evaluating its changed part, as one that stops at `a` in `a && b` with `b` changed, reads as having reached it, and reads survived unless it fails an assertion by chance in the experiment and in its confirming run;
- a mutation that changes several statements is probed before the first of them;
- a method's name, `async`, `static` and accessor kind sit outside its function, so a change to one of them is probed where its class or object literal is defined, and a test that never called the method can read as having reached it;
- a changed parameter default or pattern that throws ends the call before the probe at the body's head, and a parameter's decorator runs when its class is defined, so each reads not executed;
- a class decorated before `export` has no probe site for a change in its decorators or its members' names, since no statement can stand between a decorator and `export`;
- a module that binds a name `globalThis` of its own makes the probe throw or record nothing;
- a class field whose value is an unnamed class loses the name the field gives that class when the change sits in the class outside its methods, its fields' initializers and its static blocks;
- a mutation of types alone, outside an ambient declaration, is run, and reads survived when the intended test reaches its step;
- code a finished or timed-out test left running, and a concurrent suite's `beforeAll`, can be credited to another running test, and a mark carries across a test's retries;
- an unhandled error a stopping worker reports after its run returned appears in the next run's record, so a detection reads unclear whenever the run started next records any unhandled error, the restored baseline included, even one that names another test module;
- an assertion that fails outside the test's body where Vitest records no failed hook state (a fixture's setup or teardown, a cleanup a `beforeEach` returns, an `aroundEach` hook, an `onTestFinished` callback, an `expect.soft` in a `beforeEach` or `afterEach`) reads as a failure in the body and can read detected;
- a suite error anywhere in the experiment's test module makes the experiment invalid, whichever suite holds the intended test;
- a failed test that declares repeats, its own, a suite's or the project's, reads invalid, so a defect on it can read survived but never detected;
- a test that fails before it reaches a file snapshot assertion makes every experiment whose test is in its module read invalid in that run, since Vitest reports the unchecked snapshot as a module error while no snapshot may be written;
- a test that fails under the mutation and passes on a retry reads survived;
- an `AssertionError` the code under test raises itself reads as the test's assertion, so a defect can read detected by a test whose own assertions do not check it;
- a source file edited while the job runs is served from its new text at the next run, and the record does not say that a file changed between its runs: the digest it carries is of the text the job read when it started.

### Daemon lifecycle, protocol and CLI

#### Daemon start, endpoint and proof

`startDaemon`, in `@rt-test/daemon/client`, starts one detached daemon process for a consumer worktree. It starts one only for a caller that states the project is trusted and passes the start the user confirmed, and resolves once the daemon answers, before its discovery has finished. The daemon takes its endpoint first, before anything executes: a named pipe on Windows, or a Unix socket in `/tmp/rt-test-<uid>` on Linux, a directory only its user can enter. Each is named from the worktree identity and found from the user alone, never from the environment. It refuses the start when another process holds that endpoint. It then writes a fresh key to a directory only its user can use, and holds a lock on the worktree's store in the state directory until it exits. Every client sends a fresh challenge on each connection and trusts the connection only once its first answer proves, with that key, that it came from this user's daemon for the worktree ([ADR-0006](adr/0006-daemon-proves-itself.md)). The daemon executes nothing until the client, having proven the daemon's status, accepts the start over the spawn-time channel. A daemon whose starter closes that channel first abandons the start, and a start that fails after the spawn, by a refusal, by its deadline or before its acceptance, ends that daemon, so a failed start leaves nothing running.

#### Reconciliation and the round of runs

It then opens the store, starts tracking its inputs, and once the first reconciliation has ended, and after each change of the input revision, waits until the revision has held still for 1,000 ms (a target) and the dependency build at that revision has ended, or none can. It then discovers every confirmed workspace again when the stored discovery is not current, and runs, one at a time, each confirmed workspace whose latest stored run is not bound to its current input fingerprint, each at most once per input revision and list of the test modules the discovery gives it (once more when a change while it ran left the revision unmoved), storing the discovery under the input fingerprint it started from, or as not fingerprinted when its inputs moved while it ran, and each run as the input tracker's section says. A change inside a running workspace's inputs interrupts its run once a newer revision's dependency build has ended; nothing is stored for it, the job is listed with the paths, and the workspace runs again once the inputs settle. Each round runs the workspaces owning a changed path first, then those whose latest run holds a failed or errored test, then the rest. A discovery that listed a failed workspace or stored nothing, and a workspace whose latest run failed or crashed or whose last attempt stored nothing while it is still due, are retried at each periodic reconciliation, which is any reconciliation that ends at least 5 minutes after the last one counted as periodic, the daemon's first reconciliation starting the measure. The log explains each round's selection. The daemon idles until it is stopped.

#### Holds on self-changing workspaces and discoveries

A workspace that becomes due three times in a row only through changes the daemon's own runs and discoveries made to the same input is held: no run of it begins, the periodic retry and the once-more rerun included, until an edit reaches its inputs or the daemon sees a change it cannot attribute. A change the tracker records while a run or discovery runs is the daemon's own, whichever workspace it reaches, unless a `changes` request names its file as edited; an edit is a path whose digest differs between the end of one such job and the start of the next, or a change to a file a `changes` request names as edited, recorded before that request or during a job running when it arrives or beginning before its named read ends. More than 1,000 paths changed in one job or between two jobs count as an edit to every input, and more than 1,000 changed since a workspace's last run began as an edit to its own. The third of those runs is not interrupted by a change, so it runs to its end, and a change inside its inputs while it runs leaves the run it stores invalidated; every answer names the paths and the jobs that changed them, and while a round is held after a failed step, the CLI's text also names the held round's retry, which may release it. The discovery is held the same way when it becomes due three times in a row only through changes the daemon's own runs and discoveries made to the same input: no discovery begins until an edit or a change the daemon cannot attribute, or until no discovery is in effect. That covers the rediscovery before due runs, the periodic retry and the once-more discovery. Runs are planned from the discovery in effect meanwhile. A discovery held once is held again after the one rediscovery an edit allows, when that rediscovery changes a path the hold named. A discovery stored not fingerprinted because an input or a listed file changed while it ran, at a revision the change did not move, is discovered once more at that revision, no sooner than 2 s after it ended; a change that moves the revision during that wait starts the wait again from the change. Every answer names a held discovery's paths and the jobs that changed them while no round is pending. The counts and holds are kept in memory only.

#### Executor processes, crashed runs and process trees

Vitest runs only in an executor process the daemon starts for each job, so Vitest's signal handlers, its environment writes and a stuck `globalSetup` never reach the daemon. In that process no unhandled rejection raised on Vitest's own thread, by the project's config, a plugin, `globalSetup` or its teardown, ends the job, whatever `--unhandled-rejections` mode `NODE_OPTIONS` sets: one raised while a workspace's Vitest instance is open, from its loading through its close, is labelled as raised on the host thread and becomes one of that run's or that discovered workspace's unhandled errors, up to 100 per instance with a count of the rest, or follows the error of an instance that failed, and the run goes on and is stored; one raised while no instance is open is written to the log. Neither Vitest's own listener, which would end the process, nor one the project adds on that thread receives it, and a rejection is recorded on the instance open when Node reports it, so in a discovery of several workspaces one a closed workspace's leftover work raises can be recorded on the next. An uncaught exception on that thread still ends the process. A run whose executor process ends during the run while no stop was asked of it, by an uncaught exception or a `process.exit` in the project's code on Vitest's own thread, a native crash, a kill from outside or the end of the job object helper holding its tree, is stored as a crashed run: it holds how the process ended and no test's result, since the executor holds a run's results until it replies, and it is bound to the inputs it started from as any run is. A run's executor that ends after a stop, and a discovery's, a dependency build's or a falsification job's that dies, store nothing; a falsification job loads the parser only in its own process, as the dependency build does. The daemon ends that process's whole tree when the job ends, so nothing a job started outlives it: on Linux through the executor's process group, and on Windows through a job object that allows no breakaway, held by a helper process that dies with the daemon, and that the daemon ends, with the tree it holds, once it can no longer rely on it ([ADR-0006](adr/0006-daemon-proves-itself.md)). Only a process the project deliberately detaches on Linux, or one started outside the job on Windows, such as by a service, is not ended. When a job has not ended 15 s after a stop, which is the force-stop grace plus a margin, the daemon ends that tree and stores nothing for the job.

#### Protocol, stop and log

The daemon speaks a versioned protocol of one JSON object per line, and writes nothing to a connection that has not sent it a line. It answers each connection's requests in the order they arrived, and an answer may come once its work ends rather than at once, while every other connection is answered meanwhile; a connection that leaves more than 8 requests unanswered is closed. A stop answers every request still pending with the stopping error, and a client that closes its connection ends the work its pending request started. A client sends one request at a time on a connection and waits for its answer up to the bound its caller gives, 10 s when it gives none. The daemon bounds neither what it holds for a client that sends requests without reading their answers nor how many clients connect, since only the user's own processes can connect. Status reports the daemon's identities, its activity, and each job whose latest attempt ended with nothing stored. The hello, the stop request, its acknowledgement, the version-mismatch error and the proof are frozen for every protocol version, so `stopDaemon` checks and stops a daemon of any version, and resolves with its process id once that process has exited. On Linux, `SIGTERM` and `SIGINT` stop it the same way. The daemon logs to one file per worktree in the state directory, which also receives its stdout and stderr.

#### Start plan and the CLI's start and stop

`startPlan` builds what a start would execute, reading files only: the consumer root, the state directory `startDaemon` would use, each Vitest workspace `findVitestWorkspaces` lists with the config file the daemon would load for it, each source it could not read, and what `rt-test.json` at the root declares, as `readNonInputs` reads it: no file, its non-input patterns, or why it declares nothing. `servingDaemon` answers whether a daemon serves the worktree, telling nothing listening apart from an endpoint holder it cannot confirm. `packages/cli` is the `rt-test` CLI, the client's one production caller. `rt-test start` refuses when a daemon already serves the worktree or its endpoint holder cannot be confirmed, shows the plan, and starts the daemon with exactly that plan once the user answers y or yes on a terminal, or, without a terminal, only when `--trust` is passed. Trust lasts for that one invocation. `rt-test stop` stops the worktree's daemon and names the process that stopped.

### Queries and the agent hook

#### Summary and path status queries

The daemon also answers two read-only queries from its open store: a summary of the worktree, and the status of one path inside its consumer root. It reads the worktree's latest stored discovery and each workspace's latest stored run in one read transaction, and gives each test of that discovery exactly one state from its workspace's latest run. That state is its outcome when it finished; interrupted; its module not run, crashed or failed to load; the run failed, found no supported Vitest, was interrupted before loading or crashed; the run refused as unreadable; not in the latest run; or never run when no run of its workspace is stored. No older run answers for a test. Freshness is counted beside the states: a test with no finished result is unknown, a finished result stored under another Vitest adapter version is stale, a test the discovery or its run marks duplicate is unknown while the discovery is not current, and any other goes to `assessEvidence` with its workspace's current input fingerprint, so it is current only when the digest it was stored under equals that fingerprint, and unknown when it was stored not fingerprinted or no current fingerprint can be computed. Every answer also carries the input revision, whether reconciliation is complete, when the last one ended, the watcher's health, and whether the discovery it counts from is current. A summary also lists what the discovery did not turn into tests, including each not-covered package workspace, since RT Test runs none of its tests, and each discovered workspace whose collection raised an unhandled error, since its listed tests may not be all it holds, each with a reason cut to 1,000 characters, and each workspace's latest run, a crashed one with how its executor process ended, or, for a latest run refused as unreadable, the refusal, each cut the same way. A path status counts the tests whose module file lies at or under the path, decided by canonical real path, gives one entry per file for a folder, and names the workspace, project and source entries above the path. Before it answers, a path status reads the file at the path, or each input the tracker holds under the folder, and answers once those reads and every earlier input event are read, so a file saved just before the query is never answered from its pre-edit result as current. Such a read is evidence of no write, so it changes only what it finds changed (a new entry, a changed content digest, or a held input now gone or no longer readable as one, which it drops): it keeps the held read of an unchanged file and marks no job for it, and counts as no pending change. When it finds an entry it cannot read, the status answers every result unknown, with a reason naming that path. While a reconciliation runs, a path status answers at once, every result unknown with the reconciliation's reason. On Windows a path naming nothing that exists is refused when a missing name in it ends in a dot or a space or holds `~` followed by a digit, an 8.3 short-name form, so a missing long name of that form, such as `notes~2.md`, is refused too. A query starts no job and changes no activity. A stopping daemon, a missing discovery, a summary whose discovery holds nothing to count, a path outside the root or with nothing at or under it, a query that throws, and an answer longer than the protocol's 1 MiB line limit each get an error with its reason instead of an answer.

#### Wait query

The daemon also answers a wait for given files: it reads each file as an event naming it would, binds to the first input revision whose committed inputs the tracker can vouch for, once those reads and every earlier event are read and no reconciliation runs, takes the tests covering each file from selection at that revision, with each workspace whose fingerprint lists the file, widening to every discovered workspace while there is no dependency information, and answers settled once each covering workspace reads current or has nothing coming, superseded once an input a covering workspace reads differs from the bound revision's, naming the newer revision, or unsettled at its time limit, 100 s by default. A file its reads could not read keeps it from answering settled. A wait sent before the consumer's first discovery answers superseded when `rt-test.json` declares a pattern matching a file there: no declared pattern applies until that discovery lands, so the matched files leave the inputs then and the input revision moves. A wait sent again binds at the newer revision. Each answer names each covering test that failed or errored and each covering module that failed to load or crashed, up to 20, with the first line of its first recorded error, if any. `queryWait` in `@rt-test/daemon/client` sends it.

#### Changes query

The daemon also answers `changes` for given files: it reads each file as `status` does, and, once every workspace's inputs at the current input revision are decided, lists each test covering the files, as a wait's coverage decides it, whose state or freshness changed since the cursor an earlier answer returned, and each entry it could not discover, in a covering workspace or naming no workspace, that appeared or went away, failures first, then recoveries, up to 20, with counts in scope and outside it and a new cursor. Its record of earlier standings lives in the daemon's memory, so a cursor from an earlier daemon life, or older than its bound, is answered as a baseline. A request may also name, among its files and spelled as one of them, those the caller edited, whose changes the daemon then counts as edits; a request naming any other file as edited is refused whole. `queryChanges` in `@rt-test/daemon/client` sends it.

#### Defects query

The daemon answers a read-only `defects` query for the whole worktree or for a file or folder inside its consumer root. It reads the definition files and each mutation's file as they are when it answers, caches nothing across queries, and takes the store's latest results, its view and its inputs only once those reads have ended, so the facts the answer carries are the ones that hold when it answers. The files are the regular files under the root that a root-relative pattern in the `defects` member of `rt-test.json` matches, in the grammar `nonInputs` uses, up to 256 patterns. With no `rt-test.json`, or no `defects` member, there are no definitions and every discovered test is a gap. One walk from the root finds them. It enters only a directory below which some pattern could match, never follows a link, and skips `node_modules`, `.git`, the state directory and, inside git, what git reports as ignored; a directory git lists as holding only ignored entries, without ignoring it itself, is entered, and git is asked about each entry under it. The walk descends at most 40 levels below the root. Each of these problems is one invalid entry, which counts in the total and lies in every scope: an `rt-test.json` that is a link or not a regular file, cannot be read or parsed, is not a JSON object, or whose `defects` member is not an array of at most 256 usable patterns; a usable pattern that matches no entry the walk meets; a link below which a pattern could match that leads to a directory, or whose target cannot be checked; a directory past the depth bound below which a pattern could match; a directory the walk would enter but cannot list; a matched link, a matched directory unless the pattern matching it could also match below it, and any other matched entry that is not a regular file; and a matched file that cannot be read, is not JSON, or holds no `defects` array. A directory or file that vanishes during the walk holds nothing. No reason quotes a definition file's text: a parse failure is named by the position V8 ends its message with, when it gives one. A reason may name a pattern of `rt-test.json`. Each file is read once however many patterns match it, and its BOM is dropped.

Each definition is `{ "id", "defect", "required", "test": { "module", "name", "project"?, "occurrence"? }, "mutation": { "file", "old", "new" } }`, and a member the format does not name is ignored. `occurrence` counts from 0, as every answer prints a test identity. A definition is invalid when it is not a JSON object; its `id`, its test's `module` or its mutation's `file` is not a non-empty string; its `defect`, `required`, `old` or `new` is not a string; its test's `name` is not a non-empty array of strings, its `project` is not a string, or its `occurrence` is not a whole number from 0; its `old` is empty, or equals its `new` once line breaks are compared as LF; its test's module or its mutation's file is absolute, names the root itself, or lies outside the root by its spelling; or its mutation's file resolves outside the root by its real path. Every definition carrying a repeated id is invalid, naming the others' files and positions. The reason joins each problem found, a path being checked only once its own member is well-formed. A definition with no usable id is named by its file and its position in that file's `defects` array. No reason quotes `old` or `new`.

A definition whose `test` is well-formed and names a usable module is matched against the latest stored discovery whatever else is wrong with it, so the test it resolves to is never a gap. Its module, separators normalized to `/`, `.` and `..` resolved and trailing separators dropped, names the root-relative module file, and its name path, project and occurrence narrow the discovered tests there. No match is invalid as not discovered: the reason says whether the discovery lists that module, says that the module failed to collect in that discovery, so none of its tests is discovered, when the discovery lists it as failed (or failed in one project, when it holds discovered tests in another), and says so when that discovery is not current. More than one match is invalid as ambiguous and resolves to none of them: the reason names the count and the fields that would tell them apart, or says that no field of the format does, as for one module that two Vitest workspaces collect under one project name. A definition with no problem of its own has its `old` counted in its mutation's file as it is now, by `countAnchor` in `falsify/anchor-match.ts`, the matcher falsification is to use: a line break in `old` matches LF or CRLF, and occurrences never overlap. For a valid, resolved definition, anything but exactly one occurrence, or a file that cannot be read or is not a regular file, is anchor missing with the count or the failure. Invalid wins over anchor missing, and both win over any stored evidence. Every other definition reads the verdict of its stored evidence (`detected`, `survived`, `invalid-experiment`, `unclear`), or `never-verified` when the store holds none for its id; a record the store refuses as unreadable reads as none, with the refusal as the definition's reason. Each state is one value of the Defect evidence dimension.

Evidence freshness is a field of its own, present only beside a verdict, decided when the query answers and never stored. It reads stale under every cause that holds: `definition-changed` (the definition digest, a digest of the definition's id, its resolved test's whole identity and its mutation's root-relative file, `old` and `new`, differs from the record's), `mutation-file-changed` (the digest of the mutation file's text, as the anchor count just read it, differs from the one the job recorded), `another-adapter-version`, `another-falsifier-version`, `another-vitest-version` (the record's Vitest version is not the one the latest stored discovery reports for the resolved test's workspace), and `inputs-changed` (that workspace's current input fingerprint, the one its ordinary results are rated against, differs from the record's). When no cause holds it reads unknown with each reason that applies: `no-current-fingerprint`, as before a daemon life's first reconciliation has ended, and `duplicate-test-discovery-not-current`, when the resolved test is told apart only by its position and the latest discovery is not current. Otherwise it reads current. A record stored under another falsifier version gives its verdict, its freshness and its causes and nothing else. A definition is eligible when it is neither invalid nor anchor missing and its resolved test holds a current pass in the answer's own test standings, whatever its evidence. Verified counts the definitions that read detected with evidence freshness current; no field says a scope is verified, so a reader compares it with the total, which keeps every invalid entry and invalid definition.

A definition whose test's module the latest discovery lists is in scope when that module lies at or under the path. One naming no usable module, or a module the discovery does not list, lies in every scope, since nothing places it. A test is in scope when its module does, and a gap when no definition's test resolves to it. The answer carries the facts every answer carries; its scope; the total and the invalid entries; the count of each state, of each evidence freshness over the definitions that read a verdict, of each cause of staleness and each reason for unknown (a definition counted under every one that holds for it), of the definitions that read never verified because their stored evidence could not be read, of the eligible and of the verified, every count complete whatever the listing leaves out; every invalid entry, its reason cut to 1,000 characters; the definitions in scope, up to 500 (a target), in the order invalid definition, anchor missing, survived, invalid experiment, unclear, never verified, detected, within a state those whose evidence is not current first, then by file and position, each with its id, file, position, test as written, the resolved test identity and its duplicate mark, its mutation's file, its state, whether it is eligible, its reason cut to 1,000 characters when it is invalid, anchor missing or holds unreadable evidence, and, beside a verdict, its evidence: the freshness with its causes or its reasons, the verdict's reason and detail, and, for a verdict that is unclear because an error is not an assertion, the kind and name of up to 3 (a target) of the errors the intended test held in the experiment's run, those that are not assertions first, with the number not listed, every text in the detail and every error's name cut to 1,000 characters with the number of characters cut; and the number of each state not listed; the count of tests in scope; the gaps, with a gap count for every module holding one; and the gap tests by module, up to 1,000 (a target), with the number not listed. A path that is not absolute, one outside the root, one refused on Windows, a missing or refused discovery, a scope holding no test, no definition and no invalid entry, and an answer past the protocol's line limit, which asks `defects` for a narrower path, each get an error with its reason. The query starts no job, runs no test and loads no consumer module. A `**` pattern walks the whole root on every query; that walk is unmeasured against the CLI's 100 ms p95 target. An id, a test as written, a mutation's file and a test identity are carried whole, so one very long id or test name can take the answer past the line limit, where a narrower path does not shed a definition that lies in every scope.

#### Claude Code agent hook

`rt-test hook claude-code` is an opt-in Claude Code hook. After each batch of tool calls it asks `changes` about the files the session's `Write`, `Edit` and `NotebookEdit` calls edited under the consumer root, from the cursor the batch's agent, the main agent or a subagent, got from its own last determined answer, and adds a report only when a covering test changed since that cursor; with no usable cursor (none yet, one from another daemon life, or an expired one) it adds one line counting the failing and not-current tests in scope while there are any. Each request also names, as edited, the files among those it asks about that the batch's own `Write`, `Edit` and `NotebookEdit` calls saved, counting a call as saved unless its result begins as Claude Code's wrapped error or the user's rejection does. The daemon counts every change to a named file as an edit, never as one its own runs or discoveries made, so the agent's saves never hold a workspace or the discovery as self-changing when the request reaches the daemon before the round that counts them, and they release a hold as any edit does. A change a shell call makes is still judged by when it happened. At turn end it shows the person one line, and adds it to the agent's next prompt, while covering tests are failing or not current or the answer is not determined. It keeps each session's memory in the user's own RT Test directory.

#### Query clients and CLI query commands

`querySummary`, `queryPathStatus`, `queryWait`, `queryChanges` and `queryDefects`, in `@rt-test/daemon/client`, send the queries on a connection whose hello the daemon proved, and turn an older daemon's unknown-request error into a reason to restart it. `rt-test summary`, `rt-test status`, `rt-test wait`, `rt-test changes` and `rt-test defects` print the counts, never a pass or fail for a set. `rt-test defects [path] [--root <dir>] [--json]` prints the total and how many of it are definition file problems, each state's count, each definition file problem, each listed definition that is invalid or anchor missing with its reason, how many of those it did not list, the count of tests in scope and of gaps, and the gap count of each module. None of the seven commands loads a Vitest module, consumer config or test file, and each gives one versioned JSON document on stdout under `--json`.

### Input tracker

An input tracker in the daemon fingerprints each Vitest workspace's inputs.

#### What counts as an input

The inputs are every file under the consumer root except `.git`, `node_modules`, the daemon's state directory and log file, `rt-test.json` at the root, each declared non-input, and, inside git, every path git reports as ignored, in the consumer's repository and each nested one. A path whose ignored status is unknown is an input, and a new path is asked about with `git check-ignore` before it counts. Every test module, setup file and global setup file the latest discovery lists is also an input of its own workspace, whatever git ignores; one the inputs leave out, such as one git ignores or one under `node_modules`, is read afresh each time the fingerprint is composed. So a result stored under a fingerprint that did not count its workspace's setup files reads stale when that workspace has a setup file the inputs leave out, such as a package's, and the workspace runs once more.

#### Env files as inputs

Every env file Vite loads for a discovered workspace's tests is an input of it too, whatever git ignores. For each project not in browser mode, discovery reports two env sources, the project's own Vite config and the root config, each with its resolved env directory (none when the config turns env files off), its env prefixes (`VITE_` when it sets none) and the mode Vite resolved for it, which is `test` for the root config, since Vitest passes one. Each source lists `.env`, `.env.local`, `.env.<mode>` and `.env.<mode>.local` in its env directory. A listed env file the inputs hold as a file's content is taken from them. Any other, such as one git ignores, a FIFO, or a link to anything but a file, is read afresh each time the fingerprint is composed, as Vite reads it: a path with nothing there, or with a directory, socket or device, counts as absent, and a FIFO is never read. A FIFO or an env file that cannot be read leaves its workspace and the discovery with no fingerprint, and so does a discovered workspace whose env sources are not reported, such as one in a discovery stored before they were, or not known. Under Vitest 5 they are not known for every project of a workspace in which a nested `projects` container declares projects, since Vitest gives those projects' tests the container's env and records which container config files exist but not which projects each declares. They are not known either for a workspace whose root config declares projects by path on a Vitest 5 minor later than the newest RT Test verified (5.0) while Vitest records no container where 5.0 does, or wherever Vitest keeps that record in a shape other than a list of paths. Every answer names the file, or says the workspace's env files are not known and why, naming up to 20 container config files. The discovery's fingerprint counts every env file its discovered workspaces list.

#### Declared non-inputs and protected files

A declared non-input is a file a pattern in `rt-test.json`'s `nonInputs` member matches, decided by `declaredNonInputs` in `inputs/non-inputs.ts`, which selection also calls. No pattern removes a `package.json`, a `pnpm-workspace.yaml`, a lockfile, a Vitest or Vite config file, a `tsconfig*.json` or `jsconfig*.json` file, a test module, setup file, global setup file or env file the discovery in effect lists, or a file a discovered project's `include` or `includeSource` patterns match while its `exclude` patterns match neither the file nor a directory above it that the glob walks, each matched as Vitest's discovery globs them through tinyglobby. A file is found when the patterns match it from the real path of the project's pattern directory, or when Vitest's crawl reaches it by another spelling (Vitest's own spelling of that directory, the directories a pattern spells before its first glob segment, or a directory link discovery records below them) and the patterns match it by that spelling. So a project started through a link, a `subst` drive, another drive-letter case or an 8.3 short name still protects the files an absolute pattern spelled that way finds. Discovery finds those links by walking below the directories each pattern spells before its first glob segment, as fdir 6.5.0 walks for tinyglobby 0.2.17: it follows every directory link it can resolve, skips one whose JavaScript `realpath` and that of a link followed on the way to it are equal or one begins with the other as a string, passes over a directory it cannot read and a link it cannot resolve as the crawl does, and prunes only the directories the glob's ignore list prunes (its `exclude` patterns and each negated include pattern). Starting at those directories rather than at the crawl's root, and skipping none of the crawl's other pruning, it follows at least every link the crawl follows. `protection` in `inputs/protection.ts` builds that set from the discovery in effect, for the tracker and for selection alike. While a declaration holds patterns and the discovery in effect is absent, lists a discovered workspace that does not report those files, holds a pattern picomatch cannot compile, or holds a project whose directory links are not known (a link the walk follows that the native `realpath` cannot resolve, or a walk below one glob's pattern directories that reads more than 200,000 directories or follows more than 1,000 links), no pattern applies, and every answer says why. The lifecycle hands the tracker the store's latest discovery before the first reconciliation, and each new discovery before that discovery's fingerprint is taken, so the stored digest already counts the files it protects. The tracker then reads the paths whose status that flips, and, when a project's patterns change or patterns stop applying, walks the root for the files the patterns no longer hide, without marking a job; any other input event during that read fails the discovery's fingerprint, and so does a file the walk finds that was modified after the discovery began. A directory a pattern matches is still walked and watched. An event naming only a declared non-input is dropped before it is queued, so it moves no revision and no job. A declaration that cannot be used declares nothing, and every answer carries the reason. An `rt-test.json` that is a symbolic link or not a regular file cannot be used, and the link, never its target, is excluded from the inputs. The tracker reads `rt-test.json` again at each reconciliation, and logs the declaration in effect after the first one and whenever it changes or its patterns stop or start applying, at warning level while they do not apply. It also logs, by name only, the variables counted by value, the listed entries counted as set and the declared entries, after the first reconciliation and whenever that changes.

#### Workspace fingerprints and narrowed inputs

A workspace's fingerprint is one digest over each input's root-relative path and content digest, a digest of the daemon's environment as it started, the Node version, platform and architecture, the Vitest version the workspace resolves, the adapter version and the selection policy version. Each discovered workspace's inputs are the inputs whose selection, by `selectTests` over the dependency information built at the current input revision, includes it, and every test module and env file the discovery lists for it; an input selection calls a declared non-input lies in every workspace's set. The daemon builds that information in an executor process of its own over the discovery in effect, after the first reconciliation, after each new discovery and after each change of the input revision, and only while the tracker can vouch for its inputs; a build during which an input changed is discarded and followed by another. While the current revision's build has not ended, no workspace has a fingerprint and the answer names the build; a run waits for that build, through one rebuild, and a run whose inputs keep moving proceeds unfingerprinted. A build that fails, a discovery that does not report every discovered workspace's selection facts, or a selection that refuses an input's path leaves every workspace over the whole project's inputs; the log and every answer say why (`inputsNotNarrowed`), and only the next change of the input revision or a new discovery builds again. A build that has not ended 120 s after it began (a target) is ended with every process it started and recorded at the revision it began at as timed out, even when an input changed while it ran, which then counts toward a run's wait as a discarded build does; it widens every workspace as a failed build does, and only a later input revision or a new discovery builds again. If the builds stop working for any cause other than a stop, every workspace covers the whole project's inputs for the rest of the daemon's life, no run waits for a build, and the log and every answer say so.

#### Environment digest and non-input variables

The environment digest covers every variable by name and value except the non-input variables: those a fixed list of shell, terminal, editor, agent and login session and process identifiers names (such as `WT_SESSION`, `VSCODE_*`, `CLAUDE_CODE_SESSION_ID`, `PWD` and `SHLVL`), and those `rt-test.json` declares in `nonInputVariables`, each entry a name or a prefix ending in `*`. Each entry that names a set variable counts once, only as set and as whether any variable it names is non-empty, so a restart from a new terminal or agent session keeps every result, while an entry coming to name a set variable or ceasing to, a variable it names turning empty or non-empty, and any other variable's value, `PATH` and `HOME` included, still stale every result. A listed or declared variable still counts by value for a discovered workspace whose tests Vite can hand it to: when an env file the workspace lists references it in Vite's expansion syntax (`$NAME`, `${NAME}`, or `${NAME` followed by `:-`, `-`, `:+` or `+`), directly or through the value of a variable so referenced, including each set variable whose name begins with the referenced name or begins it, or when one of the workspace's env prefixes begins its name. A listed env file, or a value it reaches, holding any other `$`, escaped or not, counts every listed and declared variable by value for that workspace, since Vite's expansion can build a name from a substituted value. The discovery's fingerprint counts the union over its discovered workspaces. The log names each such variable per workspace and why, never its value, whenever that changes, and warns, naming the env file or the variable whose value holds the `$`, when every one counts by value. On Windows a name compares whatever its case, as Windows looks it up, so `Path` and `PATH` are one variable, and names that fold together each keep their value. Each executor process starts with the environment the daemon copied as it began serving, the one the digest counts, so a test can read any variable, and a later change to the daemon's own environment reaches neither a test nor a fingerprint. Git, the Windows job helper and the Windows system tools read the daemon's live environment, since none runs a test. Vitest, Vite and std-env read no listed variable's value, at most whether it is set and non-empty, apart from what Vite's `.env` expansion and `envPrefix` carry, which counts by value; a variable the list misses fails toward staleness. Each input's digest is kept in memory only, the store keeps only each job's fingerprint, and no environment value or file content is stored or logged.

#### Reconciliation and watching

The tracker reads every input in a reconciliation at start, when the watcher reports an error or lost events, when HEAD, the ref it names, `packed-refs`, a file git reads ignore rules from, a git config file or `rt-test.json` changes, and 5 minutes after the last reconciliation ended. Between reconciliations it re-reads only the paths events name. A file the discovery in effect lists under the consumer root that the inputs leave out is watched and read as an input is, whatever leaves it out: an event naming it, or a directory above it, reads it, a changed digest raises the input revision, a job running then is marked as for an input, and a reconciliation reads it again. On Linux each such file is watched through each existing directory on the way to it that the tree does not watch, re-armed as the entries leading to it change. Its fingerprint still reads it afresh. A file that comes to be listed, or stops being listed, moves the input revision as an edit, never as a change a job made. On Windows one recursive `fs.watch` covers the root; on Linux each included directory has its own, opened before the directory is listed. Every watch is opened on a real path, since Windows aborts the process on the first event of a watch opened through a short (8.3) name. While a reconciliation or a protection walk runs, while events remain unread, while the watcher is unhealthy (a watch of the root's tree that cannot open, a watch error or lost events), or when the input set cannot be established (an unreadable input, or a walk past 64 levels or 200,000 entries), no result is current. After a reconciliation that cannot establish the input set, the next input event brings the following one forward to 10 s after it ended, rather than waiting for the periodic reconciliation. A git file that cannot be located or watched is named among git's unread reasons, and a change to it is then seen only by the periodic reconciliation. A job begins only once every input event seen before it is read and no reconciliation runs.

#### Storing a discovery or run under its fingerprint

A discovery is stored under the fingerprint it started from only when no input changed and no event named one while it ran. A listed test module, setup file, global setup file or env file that the discovery in effect when it began did not list, or that lies outside the consumer root, and that was modified after the discovery began also stores it not fingerprinted, and so does a listed test module or setup file that cannot be found; a listed env file with nothing there when the discovery ends does not. A run is, only when it started with a fingerprint; no watcher failure or loss of the input set was recorded while it ran; no path that changed or that an event named while it ran lies among its workspace's inputs by the dependency build at the revision it started at, any that ended while it ran, or the one at the revision it ended at; and its workspace's fingerprint at the revision it ended at, once that revision's build has ended, equals the one it started from. Each build places a path by selecting it over that build's dependency information, whether or not the file exists at its revision, and every test module, setup file, global setup file and env file the discovery lists for the workspace lies inside; a path whose selection is refused lies inside, and every path does at a revision whose inputs are widened (its build failed or timed out, the discovery yields no selection input, selection refused the inputs, or the builds ended) and for a workspace the build's selection input leaves out. A file an event named that was gone before its read is judged as an input only when it would have been one: not excluded, not ignored by git, and not a declared non-input. Otherwise the run is stored not fingerprinted, and the log names why. A change only outside the workspace's inputs leaves the run's results current. A change a narrowed build places inside them interrupts a run that started with a fingerprint once a newer revision's build has ended; nothing is stored for it, the job is listed with its reason, and the workspace runs again. A widened placement never interrupts, so while builds fail an edit interrupts no run. An event after which an input's content digest, size, modification time and change time all equal the tracker's last read of it from before the event counts as none, when that read came at least 2 s after both times, so the last-access event Windows raises on reading a file untouched for an hour marks no job. A reconciliation that reads an input while an event on it is unread, or finds any of the four moved with its content unchanged, keeps the earlier read for that comparison, and a directory walk keeps the earlier read of every input whose content it finds unchanged and marks every running job for each one an event would mark.

### Dependency information and selection

#### Package workspaces and manifest edges

`findPackageWorkspaces` lists the package workspaces it can read, the consumer root first and then each directory the root `package.json` `workspaces` patterns list, by the same expansion, outside-root refusal and real-path deduplication as `findVitestWorkspaces`. `buildDependencyInformation` reads and parses each package workspace's `package.json`, source files and tsconfig and jsconfig files, and the configs their `extends` chains name, loading and running none of them, into dependency edges that each record their producer: a `dependencies`, `devDependencies`, `peerDependencies` or `optionalDependencies` entry naming a listed workspace by key or alias, or pointing into its directory by a local path; a root `overrides`, `resolutions` or `pnpm.overrides` entry that links a local workspace, which every package workspace then depends on; and, for each Vitest workspace, the package workspaces holding its discovered test modules and its setup and global setup files, and every package workspace whose directory or package name one of its resolved config aliases' replacements begins, since an alias keeps the unmatched rest of an import.

#### Alias analysis and rewriting

That holds only where the resulting import begins with the replacement, so a RegExp `find` is analyzed this way only when its source begins with `^`, has no `|` outside a group or character class, and has neither the `m` nor the `y` flag. Only the replacement's fixed prefix is analyzed, its text before the first `$` reference (`$$` included), since a reference inserts more of the import. A fixed prefix beginning with `/` reaches the workspaces it begins both under the Vite root of the alias's project and as a file-system path, since Vite tries the root first. One beginning with `/@fs/` is the file-system path that follows, as Vite reads it, so Vite's own client aliases add no widening. One that is a `file:` URL is the path it converts to, its escapes decoded, as Vite reads such a replacement. Each alias of each Vitest workspace, except one with a `customResolver`, also rewrites every literal specifier the source scan below reads, in every package workspace and in each of its forms, as Vite's alias plugin rewrites an import: a string `find` matches a specifier equal to it or beginning with it and `/`, a RegExp `find` matches wherever it tests true, read from the specifier's start whatever its `g` or `y` flag kept, and the matched part is replaced as `String.prototype.replace` replaces it, `$` patterns included. The Vitest workspace then depends on the package workspace the rewritten specifier resolves into (producer: alias): one beginning with `/@fs/` as the file-system path that follows, one that is a `file:` URL as the path it converts to, one beginning with any other `/` under the alias's Vite root and as a file-system path, and any other as the scan reads a specifier, so the rest of an import that climbs out of the replacement's directory with `..` still gives its edge. On Windows a `\` separates in an aliased glob and in a plain glob beginning with none of `/`, `./` and `../`, as Vite normalizes a glob it resolves as an id; in any other glob it escapes the next character on every platform. Vite applies only the first of a project's aliases that matches, but every matching alias applies here, since a Vitest workspace's aliases merge those of all its projects. Each alias also applies to files its workspace may never load, so these edges can select more than a run needs, never less.

#### Source scan for undeclared dependencies

It also finds the dependencies no `package.json` dependency field declares. It walks each package workspace's directory without following a directory link, and skips nested package workspaces, `node_modules`, `.git`, and, when the consumer root lies in a git repository, every path git itself reports as ignored. It reads those paths once per build of the dependency information from `git ls-files`, run from outside the consumer's directories with `GIT_*` removed from git's environment and `core.fsmonitor` off. Outside git, or when git cannot be run or read, it skips no gitignored path. It asks git the same for each nested repository or submodule the walk enters. It parses each remaining `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts` or `.tsx` file with `oxc-parser`. A literal specifier in any of these forms produces an edge: a static import or re-export, a dynamic `import()`, `require()` or `require.resolve()`, a `vi.mock`, `vi.doMock`, `vi.importActual`, `vi.importMock`, `vi.unmock` or `vi.doUnmock` call, `import.meta.resolve()`, a TypeScript `import x = require()`, a `/// <reference path>`, an `import.meta.glob` pattern, or a `new URL(specifier, import.meta.url)`. A relative or absolute specifier (producer: relative import) depends on the package workspace it resolves into from the file's real directory, and a `new URL` or `/// <reference path>` specifier is always read as relative. A glob pattern depends on the workspace owning the directory before its first wildcard or `\` escape and on every workspace nested under that directory; one beginning with `**`, which Vite globs from the file-system root, depends on every package workspace. A driveless absolute path takes the consumer root's drive, as the Vitest process running there reads it. A bare specifier (producer: bare import) depends on the listed workspace its package name names, whether or not a manifest declares it. A tsconfig or jsconfig `extends`, `references` path or `compilerOptions.paths` target (producer: tsconfig) does the same. A config without `paths` of its own takes the nearest `paths` along its `extends` chain, and targets resolve against the nearest `baseUrl` along that chain, else the directory of the config that sets the `paths`. Each `extends` target is located as TypeScript's config lookup locates it, each `\` read as `/`: `.` and `..` name a directory, read through its `package.json` `tsconfig` field or its `tsconfig.json`; a rooted target or one beginning with `./` or `../` names that file, or that file with `.json` added; and a package name resolves through the `exports` of the package holding the config when the name is that package's own, then through the `node_modules` directories above. There a package's `exports`, matched under the `require`, `types`, `node` and `default` conditions, decide alone, and without them the named file, the package's `tsconfig` field or its `tsconfig.json` is read. A config found in `node_modules` is read at its real path, as TypeScript reads a linked package, and a cycle in a chain is told by each config's real path. An `extends` also depends on the package workspace holding the config its lookup locates, since a `tsconfig` field or a link can place that config outside the workspace its target names; a config in an installed package under `node_modules` adds no such edge. So does each relative or bare `package.json` `imports` target (producer: manifest imports), and each link the walk meets (producer: link). A query or hash suffix does not change where a specifier resolves. A `file:` URL specifier is the path it converts to, its escapes decoded and its query and hash dropped, and one that converts to no path, or a glob holding a `?` or `#`, widens its workspace. A specifier resolving outside the consumer root, any other URL-scheme specifier such as `node:fs`, and a `#` subpath import add no edge.

#### Widenings

Dependency information it cannot establish becomes a widening that makes the workspace depend on every package workspace and names its cause: a missing or unreadable manifest, a local path or workspace-protocol spec resolving to no listed workspace, a name matching no listed workspace while the listing is incomplete or a listed workspace's name cannot be read, an alias replacement whose fixed prefix is neither an absolute path nor a bare package name, or is exactly `/`, begins with `//`, or begins with `/@` other than a `/@fs/` followed by more than a drive, or is a `file:` URL that converts to no path or to a file-system root or bare drive, a RegExp alias `find` not anchored as above or that does not compile, a specifier an alias rewrites to one beginning with `//`, with `/@` other than `/@fs/`, or with `/@fs/` followed by at most a drive, or to a `file:` URL that converts to no path or is a glob holding a `?` or `#`, an alias with a `customResolver` or a string `find` of `/`, both of which Vite warns against, or with an empty string `find`, which Vite makes of a `/` find whose replacement ends in `/`, a Vitest workspace whose tests are not known, and a root override whose value is neither a string nor an object of overrides or references a root dependency the root does not declare, which widens every package workspace. The scan widens the same way on a file, directory or link it cannot read, and on a source, tsconfig or jsconfig file that does not parse, nests brackets more than 1,000 deep, or whose syntax tree cannot be walked. It also widens on a malformed `extends`, `references`, `paths` or `baseUrl`, a `.vue`, `.svelte`, `.astro` or `.mdx` file, and a tsconfig with `paths`, its own or inherited, whose `extends` chain it cannot follow. An `extends` whose lookup reaches a `typesVersions` field, a `types@` version condition, a package manifest it cannot read or `exports` nested past the JSON bound widens wherever it appears, and so does one that is a `#` subpath import. A walk deeper than 40 directory levels, or past 50,000 files and directories in one workspace (skipped paths not counted), widens too.

#### Test selection and its known limits

`selectTests` maps a change, a set of root-relative paths, to Vitest workspaces: each path selects the deepest package workspace holding it and every workspace that depends on it, each through one shortest chain of edges and widenings. A path `rt-test.json` declares a non-input, given the declaration and the protection its caller passes, built by `protection` over the discovery the tracker reads, selects nothing, and its report names the matching pattern. A lockfile, any `package.json`, a path owned by the root while another package workspace is listed, a path owned by a listed directory that has no `package.json` and is not a Vitest workspace, a Vitest or Vite config file outside a Vitest workspace's directory, and `rt-test.json` at the root, or a path under it, its name compared as the host compares names (case-folded on Windows), each select every Vitest workspace; a config file in a Vitest workspace's directory and a setup or global setup file select their Vitest workspaces and those workspaces' dependents. It returns each selected test with every reason, each changed path with what it selected or why it selected nothing, the broad fallbacks and widenings it used, selected and total test and workspace counts that say when they are incomplete, a nothing-selected state distinct from a selection, and the selection policy version. It refuses a change holding an absolute or root-escaping path, and never selects a workspace the caller marks not runnable. Until file-granularity selection, the scan neither sees nor widens for these known limits:

- a computed module path in any of those forms, such as `import(expr)`, `require(expr)`, `vi.mock(expr)` or a template literal with a substitution;
- a file read by a built path, such as `path.join(__dirname, "../../other")`;
- CSS `@import` and other asset references that Vite plugins resolve;
- Vite root-absolute (`/src/x`) specifiers;
- code generated at build time, and, inside git, any gitignored file, such as build output or generated code, which is not scanned;
- imports a Vite plugin other than the alias plugin rewrites in a file the parser accepts;
- type-level references (`/// <reference types>`, `import()` types), which cannot change a test's runtime result.

#### Dependency build process and selection input

The dependency information is built in an executor process of its own, one per build. A file that ends that process inside the parser fails the build with a reason naming the process's exit and the file's root-relative path, which the build records in the state directory before each parse. A stop ends a build at once. Selection's input is built from the discovery in effect: a discovered workspace is selectable with the setup files, global setup files and aliases of all its projects, each alias with its own project's Vite root, its tests not known when a module failed to collect or collection raised an unhandled error; a workspace whose discovery failed, because its config did not load or its collection threw, is selectable with its tests not known; an unsupported or not-confirmed workspace is not runnable. A discovery that does not report a discovered workspace's selection facts yields no selection input. The daemon builds both to narrow each workspace's inputs; it does not yet select or run tests from them.

### Results store

`openStore` keeps runs and discoveries in a `node:sqlite` database, `store.sqlite`, in the consumer's state directory (`.rt-test` under the consumer root unless the caller names another). Each stored run (one workspace's `runWorkspace` result) and each discovery is bound to its project identity (the git repository's common directory, or the consumer root outside git), its worktree identity (the consumer root's canonical real path), an identity the store assigns, the input fingerprint its caller gives (a digest, or explicitly not fingerprinted) and the Vitest adapter version, and becomes visible whole. Every read answers for one project and worktree, so worktrees can share one state directory, and the store keeps each discovered workspace's reported setup files, aliases, Vite roots, patterns, the spellings they match by, the directory links each project's crawl follows, and each project's env sources or why they are not known, and the discovery's not-covered workspaces, which a discovery stored before version 10 does not report, with its discovery, and it migrates a store of any earlier schema version in place: a version 1 store's runs read as not force-stopped, since that version's code never force-stopped a run, and each discovered workspace of a discovery stored before version 9 reads as not reporting them, since a version 8 report may read complete while leaving out a nested projects container's env sources, a version 7 report holds no env sources, a report before version 7 also lacks the directory links each project's crawl follows, one before version 6 also lacks Vitest's spellings of each project's patterns, and a version 3 report also lacks each project's Vite root. Until the next discovery, no `rt-test.json` pattern applies and every workspace covers the whole project's inputs, which only widens. The code of an earlier version refuses the migrated store, so version 4's code, which cannot read a crashed run, never reads one. A daemon checks the store's schema version again inside every read and write of its records, and refuses both in a store a newer daemon has migrated since it opened it, naming the version it found and its own and saying to restart with the newer RT Test: it plans no discovery or run, its queries fail with that refusal, and each job whose write it refused is listed with it. A daemon of a version before that check keeps writing discoveries in its own version's shape into a store another daemon has migrated. When a worktree's latest discovery is refused as unreadable, whether an earlier daemon wrote it or its row is corrupt, the daemon reads it as if none were stored: it keeps the latest runs, plans a discovery, which widens, and runs no workspace until that discovery is stored, while its summary and path status answers name the refusal and say they answer once a new discovery replaces it, and its log names the refusal whole, once. When a workspace's latest run is refused as unreadable, the daemon plans for that workspace as if no run of it were stored, and no older run of it stands in, since a newer run superseded it: every other workspace's latest run still answers, each test of that workspace reads `run-refused` with freshness unknown, the summary gives that workspace no latest run and names the refusal, a run of it is due whenever the discovery in effect lists it confirmed and the confirmed start holds it, and the run it stores replaces that row as its latest, and its log names each refusal whole, once while it stands. Until that run is stored, the workspace is due for the reason `run-refused`. The store also keeps defect evidence, one record for each defect id in a project and worktree, in the table `defect_evidence`. `writeEvidence` stores a `ran` falsification reply's judgements that have a verdict, each replacing that defect's earlier record, all in one transaction and each read back before it commits. A record holds the verdict, its reason and detail, and its facts, each rebuilt member by member from what its type names, so no error message, stack, code frame or source text reaches a row, and it is bound to the project and worktree identities, an identity the store gives the reply, the definition digest handed in for the defect, the mutation file digest the reply's experiment record carries, the digest of the workspace's input fingerprint handed in, the reply's Vitest and falsifier versions, and the store's Vitest adapter version. The write stores nothing and throws, naming what is wrong, for a reply that does not read `ran`, lacks a version, or carries no list of judgements or of experiment records; a missing identity or fingerprint digest; a judgement or experiment record that is not an object naming a defect id; a defect two judgements name; a verdict with no definition digest, with no experiment record or several, or whose record carries no mutation file digest; and a verdict, reason or detail that is not the one the judge gives the facts beside it. A judgement with no verdict stores nothing and leaves the earlier record. Evidence is read with the latest discovery and runs in one read transaction. The store keeps the evidence of the project and worktree it read last, as that read rebuilt it (`KeptEvidence` in `store/kept-evidence.ts`), and a later read of that project and worktree answers from what is kept until its rows can have changed: the store reads the rows again after each `writeEvidence` call of its own, whatever the call stored, and whenever SQLite's `data_version` has moved, which a commit through any other connection to the file moves and the store's own commits do not. So a row another connection changed is read as it now is, the schema version is still checked inside every read, and one project and worktree is kept at a time. The first read after each evidence write, or after another connection's commit, rebuilds every record: measured through `readLatestResults` over a store filled through `writeEvidence` with detections, compiled, warm, in one process on a Ryzen 7 8700F with 16 logical cores and 32 GB, Node 24.19.0 and Windows 11, a rebuilding read takes a median of 46 ms at 3,195 records and 180 ms at 10,812 (p95 53 ms and 212 ms), a kept read takes 0.06 ms at either (p95 0.10 ms), and the kept records hold 9 MB and 31 MB. A record of another falsifier version is read as its bindings and its verdict alone. A record of the current version that cannot be rebuilt, or whose verdict its facts do not give, is refused alone: its defect reads never verified with the refusal, every other record still reads, and the log names the refusal whole, once while it stands. Schema version 11 adds the table: a store of any earlier version the opener migrates gains it empty, and version 10's code refuses the migrated store. `openStore` refuses, leaving the file unchanged, a store of any other schema version or a file that is not an RT Test store. The daemon opens it at its start, and is its only production writer.

## Intended architecture

The sections below describe the intended architecture. Every component is TypeScript on Node ([ADR-0001](adr/0001-typescript-on-node.md)), and terms follow [the glossary](glossary.md).

### Components

| Component          | Responsibility                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------- |
| Daemon             | The sole executor of tests and falsification for one started project                        |
| Vitest integration | Discover tests across workspaces, schedule supported runs, consume structured events        |
| Input tracker      | Watch saved inputs, reconcile content, assign input revisions                               |
| Dependency index   | Store workspace, module, and function relationships and reasons for uncertainty             |
| Scheduler          | Deduplicate work, prioritize ordinary tests, invalidate runs whose inputs moved             |
| Evidence store     | Persist inputs, runs, results, graph versions, and defect evidence                          |
| Query service      | Serve consistent snapshots and waits without running tests                                  |
| Falsifier          | Run baseline and mutated experiments as in-memory transforms and record run facts           |
| Framework adapter  | Add otherwise hidden dependency edges and synchronization information                       |
| CLI and API        | Query and wait through versioned `--json` output or a small programmatic API; never execute |

The daemon is an independent local process and the only component that executes tests ([ADR-0002](adr/0002-daemon-sole-executor.md)). The CLI and API talk to it over a named pipe on Windows or a Unix socket on Linux, one line of JSON per message, versioned (ADR-0001), and each connection's first answer proves it came from the user's own daemon ([ADR-0006](adr/0006-daemon-proves-itself.md)). The daemon hosts Vitest in an executor process it starts for each job, so no Vitest code runs in the daemon's own process, and nothing a job started outlives the job. The store is SQLite through `node:sqlite`, which needs no flag from Node 22.13, the supported floor. Do not introduce a remote backend for the core.

### Identity and freshness

Identify a project by its git repository's common directory, shared by every worktree checked out from it, or by its canonical root outside git; never by package name alone. Distinguish Vitest workspaces, parameterized test cases, duplicate display names, file paths, and run identities. Scope state to a worktree; two worktrees must not overwrite each other's results. On Windows, Vitest spells a module id with the drive-letter case its job started from (Vitest 4.1 keeps a lowercase `c:`, Vitest 5 gives `C:`), and Vite's `safeRealpathSync` switches from `fs.realpathSync` to `fs.realpathSync.native` partway through a job; RT Test stores each module path relative to its workspace's native real path and derives worktree and project identity from native real paths, so neither spelling reaches a stored identity.

Fingerprint relevant source and test content, fixtures, setup, configuration, the environment less its non-input variables' values, dependency lockfiles, runtime, runner version, adapter version, and selection policy version. Persist digests rather than secret environment values. Content hashes alone cannot establish that the input set is complete; record completeness and reasons for uncertainty.

Publish query snapshots with a sequence number, observed revision, last reconciliation time, and watcher health. On startup, mark old results unconfirmed until reconciliation finishes. An unknown input set cannot yield a current pass.

Results belong to the inputs actually executed. If an input changes during a run, do not promote that run to current: record it as invalidated and rerun from stable inputs. Keep a generation token so a late completion cannot replace a newer result. Because the daemon is the only executor, this replaces an agent-side run lock.

### State dimensions

| Dimension          | Intended values                                                                                     |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Last test outcome  | Passed, failed, skipped, error, never run                                                           |
| Freshness          | Current, stale, unknown                                                                             |
| Execution          | Idle, queued, running, interrupted                                                                  |
| Defect evidence    | Detected, survived, invalid experiment, unclear, anchor missing, invalid definition, never verified |
| Evidence freshness | Current, stale, unknown                                                                             |

Collect module-level errors and run-level unhandled errors independently of individual test outcomes. Include discovered, selected, executed, skipped, stale, and unknown denominators in summaries. An empty or incomplete run cannot be called verified.

### Dependency index

Use a graph of workspaces, source files, functions, tests, configuration, fixtures, and other declared inputs. Store dependency edges separately from observed execution and defect-detection edges. Preserve the reason and producer of each edge.

Selection starts at workspace granularity: the edited file's workspace plus every workspace that depends on it, with configuration, setup, and lockfile changes as named broad fallbacks. File granularity then comes from static module dependencies, conservatively widened for unresolved behavior. Maintain reverse edges for invalidation. Analyze both the old and new graph around deletions and changed imports. Never remove a possible dependency solely because one prior test run did not execute it.

Function identity and per-test execution mapping are experimental until tested against refactoring, aliases, callbacks, mocks, concurrency, and module initialization. Stable test IDs must not depend only on a mutable display name. Per-test coverage instrumentation overhead must be measured separately.

Adapters can add edges or require broader selection. They must not suppress core uncertainty without a tested rule. An adapter result includes its version, completeness, affected inputs, and explanation.

### Convex adapter

Convex tests can use broad module registries and `api`/`internal` references, so every Convex test file globs the whole package and import-based selection, including `vitest related`, cannot see the real edges. The adapter ports Fleet Cooling's `scripts/test-blast-radius.mjs`: static imports plus `api.<path>` and `internal.<path>` name edges resolved against the generated API module list, where anything unresolved becomes a wildcard that widens every selection and an integrity failure refuses to narrow at all. It then extends to scheduled dispatch, components, triggers, and schema inputs.

Keep `convex-test` results distinct from typechecking, development backend synchronization, and live integration results. Use synthetic public fixtures. Do not make the daemon depend on a running Convex backend or automatically push code.

### Execution and falsification isolation

Reuse runner infrastructure where supported, while retaining the configured test isolation. Debounce edit bursts, prioritize direct targets and prior failures, and never run a test that holds a current result for the same inputs. Cancellation must leave explicit interrupted or stale states.

Falsification applies each mutation as an in-memory module transform in a separate Vitest instance and never writes a mutated file ([ADR-0003](adr/0003-transform-falsification.md)). Verify the baseline before mutation. Decide each verdict from run facts: the failure phase, the error kind, whether the intended test reached the step that holds the mutation, and the baseline result. Only an assertion failure in the intended test after it reached that step, repeated in a confirming run, counts as a detection; setup, collection, compile, timeout, and unrelated failures are invalid or unclear experiments. Ordinary results and mutation runs use different namespaces. Changing the test, mutation, input closure, or falsifier invalidates the evidence. Canary fixtures (`packages/daemon/canaries/`) exercise the fact collector and the judge.

A falsification job covers one Vitest workspace in one reused Vitest instance: a baseline, each defect's experiment alone, and a restored baseline, reading each run's facts only from the modules that run executed, and starting only while no ordinary job is due or running ([ADR-0007](adr/0007-reused-instance-per-falsification-job.md)). The facts that decide a verdict, and the canary fixtures that confirm them on each Vitest version a workspace installs before its first falsification there, are in [ADR-0008](adr/0008-detection-from-task-facts-and-canaries.md).

Defect definitions come from the JSON files the `defects` member of `rt-test.json` names in the consumer repository, and evidence stays under the local state directory ([ADR-0004](adr/0004-defect-definitions-in-consumer.md), [ADR-0009](adr/0009-defect-definition-files.md)). The `defects` query reads, checks and resolves them now and reads each one's stored evidence (`Defects query`); falsification does not yet run them. A falsification job's reply carries each experiment's judgement with its facts, and the store's `writeEvidence` keeps each verdict as that defect's evidence (`Results store`); nothing calls it yet, since no job is scheduled. A missing mutation anchor and an invalid definition are per-defect states; the other defects still run.

The bootstrap `scripts/verify-defects.mjs` only validates the known hook-free fixtures listed in the repository's `defects.json` files. Its assertion-message check is not a general attribution algorithm and must not become one by copying it unchanged.

### Query surface

The CLI offers summary, `status <path>` with counts per state for files and folders, failures, affected selection, explanation, defect evidence, gaps, and `wait <files>`. Read operations never trigger execution. `defects` gives each defect definition's evidence state, its freshness and reason, the verified, eligible and total counts, and the gaps. A wait binds to the input revision at call time and returns when every test covering the files has a current result or an explicit non-current state, or as superseded, naming the newer revision, as soon as a covering input changes, or as unsettled, naming each covering workspace's execution state, once its time limit passes. The default limit stays under the two minutes a coding agent's shell tool commonly allows a command, so an agent always gets an answer and can wait again.

Every summary and `status <path>` answer also carries the daemon's round: pending, naming what it waits for (the first reconciliation, the quiet window, the settling of the inputs, a dependency build, a rediscovery, or a job begun at an earlier input revision); planned at an input revision; or held after a failed scheduling step until the daemon tries again at the next input event or reconciliation. It carries each confirmed workspace's execution state: running; queued, with why it is due and up to 3 of the changed paths or broad fallbacks that chose it; interrupted by a change until the next round decides it; or idle, saying why no run is coming when its results are not current. It carries the latest selection: up to 20 changed paths, each with up to 20 workspaces it selected and up to 20 it reached that cannot run, up to 20 broad fallbacks, and the selected and total counts, or why no selection was made. On a workspace's latest run, it says whether this daemon stored it invalidated, with the reason. A query the daemon cannot answer, because no discovery is stored or the latest was refused as unreadable, says in its reason what the round is doing and names up to 20 jobs that ended with nothing stored, counting the rest.

Every `--json` payload carries a schema version, which also serves the later gap report that coding agents read to propose defects ([ADR-0005](adr/0005-no-model-calls.md)). There is no MCP server. Keep local endpoints scoped to an explicitly started project, authenticate access if using HTTP, and avoid binding to external interfaces by default. Do not leak source or environment values in summaries.
