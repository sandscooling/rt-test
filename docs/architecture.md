# Architecture

## Current implementation

`packages/core/src/evidence.ts` assesses a historical result against a caller-supplied fingerprint. It preserves the outcome and returns freshness plus an explicit current-pass predicate. Missing or empty fingerprints produce unknown freshness. `packages/core/src/test-identity.ts` gives each test of one module a test identity (its Vitest workspace, Vitest project, module path, suite and test names, and its position among tests sharing those names), and marks a test whose names repeat in its module as a duplicate.

`packages/daemon` holds Vitest discovery and runs. `findVitestWorkspaces` lists a consumer's Vitest workspaces from the root `package.json` `workspaces` field and config file names (a `vitest.config.*`, or a `vite.config.*` in a directory whose `package.json` depends on Vitest), reading files only; it reports a root `pnpm-workspace.yaml` and each pattern it cannot expand as not read. Apart from those, it lists as not covered each package workspace other than the root whose `package.json` has a string `test` script, which holds no Vitest config file and lists no Vitest in its `dependencies` or `devDependencies`, with a reason quoting the script. It lists no directory that a `workspaces` pattern resolves outside the consumer root, through `..` or a link, deciding by canonical real path, and reports each such directory as not read with the real path it resolves to, so only the started project's own directories are loaded. When entries reached by different paths resolve to the same canonical real path, it lists only the first in pattern order, the consumer root first, and reports each later one as not read, naming the workspace listed in its place; a pattern that repeats a path already examined adds nothing. So no directory is loaded or run twice. `discoverTests` loads each workspace's own Vitest, 4.1.x or 5.x, collects the modules of every project without running a test body or hook, and returns each test with its identity. It reports modules and workspaces that failed to load, workspaces with no supported Vitest, browser-mode projects, and typecheck modules, each as not discovered; it keeps each not-covered workspace in which none of its discovered workspaces' tests or failed modules lies, which the summary and status name as `workspace-not-vitest`; it never collects a typecheck module. For each workspace it discovers, it also reports, per project not in browser mode, the project's setup files and global setup files as root-relative paths (a file outside the root climbs with `..`, or on Windows names its other drive), leaving out RT Test's snapshot guard and crediting the root project's global setup to every such project, since Vitest runs it on every run; the project's Vite root; each alias of the project's resolved config in order: its `find` (a RegExp as its source text and flags), its replacement, and whether it has a `customResolver`; and the project's `include`, `exclude` and `includeSource` patterns with the directory they match from, both root-relative and as Vitest's glob spells it, and, for each `include` and `includeSource` pattern, the directories before its first glob segment (or the file a pattern with none names) as the pattern spells them, with the root-relative path that spelling resolves to, and each directory link found below those directories by a walk that follows at least every link Vitest's crawl follows, as the crawl spells it, with the root-relative path it resolves to, or why those links are not known. `runWorkspace` runs one workspace's tests on that same Vitest and records each test under the identity discovery gives it, with its outcome (passed, failed, skipped or error) and whether it finished or was interrupted as separate fields. It records modules that failed to load, hook errors on their module, crashed modules, modules not run and the run's unhandled errors apart from test outcomes, and gives a run in which no test passed or failed the reason nothing ran. The caller's `AbortSignal` interrupts a run, and a run Vitest stops itself under the consumer's `bail` is interrupted too. `discoverTests` takes an `AbortSignal` as well: once it aborts, discovery loads no further workspace, interrupts the collection in progress, and rejects with the signal's reason after the Vitest instance has closed and the host is restored, so an aborted discovery has no result. When a run or a discovery has not ended `FORCE_STOP_GRACE_MS` (10 s) after its signal aborted, Vitest force-stops its workers, which skips the project's `afterAll` hooks and teardown, and each run that loaded its workspace records whether that happened in a field beside its execution state. Work on Vitest's own thread, such as config loading or `globalSetup`, is beyond that force-stop. Discovery and runs share one queue, so none overlaps another, and each restores the host's environment and exit code. Each also runs in its workspace's directory, as that workspace's own `vitest` does, and restores the host's working directory with its environment. Neither writes into the consumer's tree. Each forces coverage, snapshot updates, Vitest's results cache and its module cache off over the workspace's config, so a snapshot assertion with no stored snapshot fails its test. Each also puts a setup file first in every project that keeps the project's snapshot environment, the consumer's own included, from saving or removing a snapshot file, since under update none Vitest still rewrites a snapshot file holding an entry no test checked; snapshots are still read through that environment. Each also names the config file Vitest would load and loads it through Vite's runner loader when Vite treats it as ESM, or otherwise through Vite's bundle loader, which writes nothing for a CommonJS config. Writes made by the consumer's own code (test bodies, hooks, setup files, `globalSetup`, plugins and config code) are the consumer's own. Five documented exceptions remain, all under `node_modules`: Vitest 4.1 on Vite 6.0.x, which has no runner loader, leaves an empty `node_modules/.vite-temp/`; a consumer that turns on Vite's dependency optimizer gets its cache in `node_modules/.vite/vitest`; a workspace whose project config files differ in format from its root config leaves `node_modules/.vite-temp/` for an ESM project config under a CommonJS root, and fails to load, as a failed workspace, a CommonJS project config under an ESM root; a Vitest 4.1 project config that itself sets `experimental.fsModuleCache` gets the module cache written; and Vitest 5, which creates its API token file whatever `api: false` says, writes it to `node_modules/.vitest/` when it cannot write the user data directory. Both load Vitest configs and import test files, so only the daemon's executor process calls them, after an explicit start. Each takes the start the user confirmed: it loads only a workspace whose path and chosen config file match a confirmed entry, and makes that match again as each workspace is loaded, so a config file added or swapped after the start is never loaded. Discovery lists every other workspace as not discovered, with the reason "not confirmed at start", and a run whose config file no longer matches loads nothing and is not stored.

`startDaemon`, in `@rt-test/daemon/client`, starts one detached daemon process for a consumer worktree. It starts one only for a caller that states the project is trusted and passes the start the user confirmed, and resolves once the daemon answers, before its discovery has finished. The daemon takes its endpoint first, before anything executes: a named pipe on Windows, or a Unix socket in `/tmp/rt-test-<uid>` on Linux, a directory only its user can enter. Each is named from the worktree identity and found from the user alone, never from the environment. It refuses the start when another process holds that endpoint. It then writes a fresh key to a directory only its user can use, and holds a lock on the worktree's store in the state directory until it exits. Every client sends a fresh challenge on each connection and trusts the connection only once its first answer proves, with that key, that it came from this user's daemon for the worktree ([ADR-0006](adr/0006-daemon-proves-itself.md)). The daemon executes nothing until the client, having proven the daemon's status, accepts the start over the spawn-time channel. A daemon whose starter closes that channel first abandons the start, and a start that fails after the spawn, by a refusal, by its deadline or before its acceptance, ends that daemon, so a failed start leaves nothing running. It then opens the store, starts tracking its inputs, and once the first reconciliation has ended, and after each change of the input revision, waits until the revision has held still for 1,000 ms (a target) and the dependency build at that revision has ended, or none can. It then discovers every confirmed workspace again when the stored discovery is not current, and runs, one at a time, each confirmed workspace whose latest stored run is not bound to its current input fingerprint, each at most once per input revision and list of the test modules the discovery gives it (once more when a change while it ran left the revision unmoved), storing the discovery under the input fingerprint it started from, or as not fingerprinted when its inputs moved while it ran, and each run as the input tracker's paragraph says. A change inside a running workspace's inputs interrupts its run once a newer revision's dependency build has ended; nothing is stored for it, the job is listed with the paths, and the workspace runs again once the inputs settle. Each round runs the workspaces owning a changed path first, then those whose latest run holds a failed or errored test, then the rest. A discovery that listed a failed workspace or stored nothing, and a workspace whose latest run failed or crashed or whose last attempt stored nothing while it is still due, are retried at each periodic reconciliation, which is any reconciliation that ends at least 5 minutes after the last one counted as periodic, the daemon's first reconciliation starting the measure. A workspace that becomes due three times in a row only through changes the daemon's own runs and discoveries made to the same input is held: no run of it begins, the periodic retry and the once-more rerun included, until an edit reaches its inputs or the daemon sees a change it cannot attribute. A change the tracker records while a run or discovery runs is the daemon's own, whichever workspace it reaches; an edit is a path whose digest differs between the end of one such job and the start of the next. More than 1,000 paths changed in one job or between two jobs count as an edit to every input, and more than 1,000 changed since a workspace's last run began as an edit to its own. The third of those runs is not interrupted by a change, so it runs to its end, and a change inside its inputs while it runs leaves the run it stores invalidated; every answer names the paths and the jobs that changed them, and while a round is held after a failed step, the CLI's text also names the held round's retry, which may release it. The discovery is held the same way when it becomes due three times in a row only through changes the daemon's own runs and discoveries made to the same input: no discovery begins until an edit or a change the daemon cannot attribute, or until no discovery is in effect. That covers the rediscovery before due runs, the periodic retry and the once-more discovery. Runs are planned from the discovery in effect meanwhile. A discovery held once is held again after the one rediscovery an edit allows, when that rediscovery changes a path the hold named. A discovery stored not fingerprinted because an input or a listed file changed while it ran, at a revision the change did not move, is discovered once more at that revision, no sooner than 2 s after it ended; a change that moves the revision during that wait starts the wait again from the change. Every answer names a held discovery's paths and the jobs that changed them while no round is pending. The counts and holds are kept in memory only. The log explains each round's selection. The daemon idles until it is stopped. Vitest runs only in an executor process the daemon starts for each job, so Vitest's signal handlers, its environment writes and a stuck `globalSetup` never reach the daemon. In that process no unhandled rejection raised on Vitest's own thread, by the project's config, a plugin, `globalSetup` or its teardown, ends the job, whatever `--unhandled-rejections` mode `NODE_OPTIONS` sets: one raised while a workspace's Vitest instance is open, from its loading through its close, is labelled as raised on the host thread and becomes one of that run's or that discovered workspace's unhandled errors, up to 100 per instance with a count of the rest, or follows the error of an instance that failed, and the run goes on and is stored; one raised while no instance is open is written to the log. Neither Vitest's own listener, which would end the process, nor one the project adds on that thread receives it, and a rejection is recorded on the instance open when Node reports it, so in a discovery of several workspaces one a closed workspace's leftover work raises can be recorded on the next. An uncaught exception on that thread still ends the process. A run whose executor process ends during the run while no stop was asked of it, by an uncaught exception or a `process.exit` in the project's code on Vitest's own thread, a native crash, a kill from outside or the end of the job object helper holding its tree, is stored as a crashed run: it holds how the process ended and no test's result, since the executor holds a run's results until it replies, and it is bound to the inputs it started from as any run is. A run's executor that ends after a stop, and a discovery's or a dependency build's that dies, store nothing. The daemon ends that process's whole tree when the job ends, so nothing a job started outlives it: on Linux through the executor's process group, and on Windows through a job object that allows no breakaway, held by a helper process that dies with the daemon, and that the daemon ends, with the tree it holds, once it can no longer rely on it ([ADR-0006](adr/0006-daemon-proves-itself.md)). Only a process the project deliberately detaches on Linux, or one started outside the job on Windows, such as by a service, is not ended. When a job has not ended 15 s after a stop, which is the force-stop grace plus a margin, the daemon ends that tree and stores nothing for the job. The daemon speaks a versioned protocol of one JSON object per line, and writes nothing to a connection that has not sent it a line. It answers each connection's requests in the order they arrived, and an answer may come once its work ends rather than at once, while every other connection is answered meanwhile; a connection that leaves more than 8 requests unanswered is closed. A stop answers every request still pending with the stopping error, and a client that closes its connection ends the work its pending request started. A client sends one request at a time on a connection and waits for its answer up to the bound its caller gives, 10 s when it gives none. The daemon bounds neither what it holds for a client that sends requests without reading their answers nor how many clients connect, since only the user's own processes can connect. Status reports the daemon's identities, its activity, and each job whose latest attempt ended with nothing stored. The hello, the stop request, its acknowledgement, the version-mismatch error and the proof are frozen for every protocol version, so `stopDaemon` checks and stops a daemon of any version, and resolves with its process id once that process has exited. On Linux, `SIGTERM` and `SIGINT` stop it the same way. The daemon logs to one file per worktree in the state directory, which also receives its stdout and stderr. `startPlan` builds what a start would execute, reading files only: the consumer root, the state directory `startDaemon` would use, each Vitest workspace `findVitestWorkspaces` lists with the config file the daemon would load for it, each source it could not read, and what `rt-test.json` at the root declares, as `readNonInputs` reads it: no file, its non-input patterns, or why it declares nothing. `servingDaemon` answers whether a daemon serves the worktree, telling nothing listening apart from an endpoint holder it cannot confirm. `packages/cli` is the `rt-test` CLI, the client's one production caller. `rt-test start` refuses when a daemon already serves the worktree or its endpoint holder cannot be confirmed, shows the plan, and starts the daemon with exactly that plan once the user answers y or yes on a terminal, or, without a terminal, only when `--trust` is passed. Trust lasts for that one invocation. `rt-test stop` stops the worktree's daemon and names the process that stopped. The daemon also answers two read-only queries from its open store: a summary of the worktree, and the status of one path inside its consumer root. It reads the worktree's latest stored discovery and each workspace's latest stored run in one read transaction, and gives each test of that discovery exactly one state from its workspace's latest run. That state is its outcome when it finished; interrupted; its module not run, crashed or failed to load; the run failed, found no supported Vitest, was interrupted before loading or crashed; the run refused as unreadable; not in the latest run; or never run when no run of its workspace is stored. No older run answers for a test. Freshness is counted beside the states: a test with no finished result is unknown, a finished result stored under another Vitest adapter version is stale, a test the discovery or its run marks duplicate is unknown while the discovery is not current, and any other goes to `assessEvidence` with its workspace's current input fingerprint, so it is current only when the digest it was stored under equals that fingerprint, and unknown when it was stored not fingerprinted or no current fingerprint can be computed. Every answer also carries the input revision, whether reconciliation is complete, when the last one ended, the watcher's health, and whether the discovery it counts from is current. A summary also lists what the discovery did not turn into tests, including each not-covered package workspace, since RT Test runs none of its tests, and each discovered workspace whose collection raised an unhandled error, since its listed tests may not be all it holds, each with a reason cut to 1,000 characters, and each workspace's latest run, a crashed one with how its executor process ended, or, for a latest run refused as unreadable, the refusal, each cut the same way. A path status counts the tests whose module file lies at or under the path, decided by canonical real path, gives one entry per file for a folder, and names the workspace, project and source entries above the path. Before it answers, a path status reads the file at the path, or each input the tracker holds under the folder, and answers once those reads and every earlier input event are read, so a file saved just before the query is never answered from its pre-edit result as current. Such a read is evidence of no write, so it changes only what it finds changed (a new entry, a changed content digest, or a held input now gone or no longer readable as one, which it drops): it keeps the held read of an unchanged file and marks no job for it, and counts as no pending change. When it finds an entry it cannot read, the status answers every result unknown, with a reason naming that path. While a reconciliation runs, a path status answers at once, every result unknown with the reconciliation's reason. On Windows a path naming nothing that exists is refused when a missing name in it ends in a dot or a space or holds `~` followed by a digit, an 8.3 short-name form, so a missing long name of that form, such as `notes~2.md`, is refused too. A query starts no job and changes no activity. A stopping daemon, a missing discovery, a summary whose discovery holds nothing to count, a path outside the root or with nothing at or under it, a query that throws, and an answer longer than the protocol's 1 MiB line limit each get an error with its reason instead of an answer. `querySummary` and `queryPathStatus`, in `@rt-test/daemon/client`, send the queries on a connection whose hello the daemon proved, and turn an older daemon's unknown-request error into a reason to restart it. `rt-test summary` and `rt-test status` print the counts, never a pass or fail for a set. None of the four commands loads a Vitest module, consumer config or test file, and each gives one versioned JSON document on stdout under `--json`.

An input tracker in the daemon fingerprints each Vitest workspace's inputs. The inputs are every file under the consumer root except `.git`, `node_modules`, the daemon's state directory and log file, `rt-test.json` at the root, each declared non-input, and, inside git, every path git reports as ignored, in the consumer's repository and each nested one. A path whose ignored status is unknown is an input, and a new path is asked about with `git check-ignore` before it counts. Every test module, setup file and global setup file the latest discovery lists is also an input of its own workspace, whatever git ignores; one the inputs leave out, such as one git ignores or one under `node_modules`, is read afresh each time the fingerprint is composed. So a result stored under a fingerprint that did not count its workspace's setup files reads stale when that workspace has a setup file the inputs leave out, such as a package's, and the workspace runs once more. Every env file Vite loads for a discovered workspace's tests is an input of it too, whatever git ignores. For each project not in browser mode, discovery reports two env sources, the project's own Vite config and the root config, each with its resolved env directory (none when the config turns env files off), its env prefixes (`VITE_` when it sets none) and the mode Vite resolved for it, which is `test` for the root config, since Vitest passes one. Each source lists `.env`, `.env.local`, `.env.<mode>` and `.env.<mode>.local` in its env directory. A listed env file the inputs hold as a file's content is taken from them. Any other, such as one git ignores, a FIFO, or a link to anything but a file, is read afresh each time the fingerprint is composed, as Vite reads it: a path with nothing there, or with a directory, socket or device, counts as absent, and a FIFO is never read. A FIFO or an env file that cannot be read leaves its workspace and the discovery with no fingerprint, and so does a discovered workspace whose env sources are not reported, such as one in a discovery stored before they were, or not known. Under Vitest 5 they are not known for every project of a workspace in which a nested `projects` container declares projects, since Vitest gives those projects' tests the container's env and records which container config files exist but not which projects each declares. They are not known either for a workspace whose root config declares projects by path on a Vitest 5 minor later than the newest RT Test verified (5.0) while Vitest records no container where 5.0 does, or wherever Vitest keeps that record in a shape other than a list of paths. Every answer names the file, or says the workspace's env files are not known and why, naming up to 20 container config files. The discovery's fingerprint counts every env file its discovered workspaces list. A declared non-input is a file a pattern in `rt-test.json`'s `nonInputs` member matches, decided by `declaredNonInputs` in `inputs/non-inputs.ts`, which selection also calls. No pattern removes a `package.json`, a `pnpm-workspace.yaml`, a lockfile, a Vitest or Vite config file, a `tsconfig*.json` or `jsconfig*.json` file, a test module, setup file, global setup file or env file the discovery in effect lists, or a file a discovered project's `include` or `includeSource` patterns match while its `exclude` patterns match neither the file nor a directory above it that the glob walks, each matched as Vitest's discovery globs them through tinyglobby. A file is found when the patterns match it from the real path of the project's pattern directory, or when Vitest's crawl reaches it by another spelling (Vitest's own spelling of that directory, the directories a pattern spells before its first glob segment, or a directory link discovery records below them) and the patterns match it by that spelling. So a project started through a link, a `subst` drive, another drive-letter case or an 8.3 short name still protects the files an absolute pattern spelled that way finds. Discovery finds those links by walking below the directories each pattern spells before its first glob segment, as fdir 6.5.0 walks for tinyglobby 0.2.17: it follows every directory link it can resolve, skips one whose JavaScript `realpath` and that of a link followed on the way to it are equal or one begins with the other as a string, passes over a directory it cannot read and a link it cannot resolve as the crawl does, and prunes only the directories the glob's ignore list prunes (its `exclude` patterns and each negated include pattern). Starting at those directories rather than at the crawl's root, and skipping none of the crawl's other pruning, it follows at least every link the crawl follows. `protection` in `inputs/protection.ts` builds that set from the discovery in effect, for the tracker and for selection alike. While a declaration holds patterns and the discovery in effect is absent, lists a discovered workspace that does not report those files, holds a pattern picomatch cannot compile, or holds a project whose directory links are not known (a link the walk follows that the native `realpath` cannot resolve, or a walk below one glob's pattern directories that reads more than 200,000 directories or follows more than 1,000 links), no pattern applies, and every answer says why. The lifecycle hands the tracker the store's latest discovery before the first reconciliation, and each new discovery before that discovery's fingerprint is taken, so the stored digest already counts the files it protects. The tracker then reads the paths whose status that flips, and, when a project's patterns change or patterns stop applying, walks the root for the files the patterns no longer hide, without marking a job; any other input event during that read fails the discovery's fingerprint, and so does a file the walk finds that was modified after the discovery began. A directory a pattern matches is still walked and watched. An event naming only a declared non-input is dropped before it is queued, so it moves no revision and no job. A declaration that cannot be used declares nothing, and every answer carries the reason. An `rt-test.json` that is a symbolic link or not a regular file cannot be used, and the link, never its target, is excluded from the inputs. The tracker reads `rt-test.json` again at each reconciliation, and logs the declaration in effect after the first one and whenever it changes or its patterns stop or start applying, at warning level while they do not apply. It also logs, by name only, the variables counted by value, the listed entries counted as set and the declared entries, after the first reconciliation and whenever that changes. A workspace's fingerprint is one digest over each input's root-relative path and content digest, a digest of the daemon's environment as it started, the Node version, platform and architecture, the Vitest version the workspace resolves, the adapter version and the selection policy version. Each discovered workspace's inputs are the inputs whose selection, by `selectTests` over the dependency information built at the current input revision, includes it, and every test module and env file the discovery lists for it; an input selection calls a declared non-input lies in every workspace's set. The daemon builds that information in an executor process of its own over the discovery in effect, after the first reconciliation, after each new discovery and after each change of the input revision, and only while the tracker can vouch for its inputs; a build during which an input changed is discarded and followed by another. While the current revision's build has not ended, no workspace has a fingerprint and the answer names the build; a run waits for that build, through one rebuild, and a run whose inputs keep moving proceeds unfingerprinted. A build that fails, a discovery that does not report every discovered workspace's selection facts, or a selection that refuses an input's path leaves every workspace over the whole project's inputs; the log and every answer say why (`inputsNotNarrowed`), and only the next change of the input revision or a new discovery builds again. A build that has not ended 120 s after it began (a target) is ended with every process it started and recorded at the revision it began at as timed out, even when an input changed while it ran, which then counts toward a run's wait as a discarded build does; it widens every workspace as a failed build does, and only a later input revision or a new discovery builds again. If the builds stop working for any cause other than a stop, every workspace covers the whole project's inputs for the rest of the daemon's life, no run waits for a build, and the log and every answer say so. The environment digest covers every variable by name and value except the non-input variables: those a fixed list of shell, terminal, editor, agent and login session and process identifiers names (such as `WT_SESSION`, `VSCODE_*`, `CLAUDE_CODE_SESSION_ID`, `PWD` and `SHLVL`), and those `rt-test.json` declares in `nonInputVariables`, each entry a name or a prefix ending in `*`. Each entry that names a set variable counts once, only as set and as whether any variable it names is non-empty, so a restart from a new terminal or agent session keeps every result, while an entry coming to name a set variable or ceasing to, a variable it names turning empty or non-empty, and any other variable's value, `PATH` and `HOME` included, still stale every result. A listed or declared variable still counts by value for a discovered workspace whose tests Vite can hand it to: when an env file the workspace lists references it in Vite's expansion syntax (`$NAME`, `${NAME}`, or `${NAME` followed by `:-`, `-`, `:+` or `+`), directly or through the value of a variable so referenced, including each set variable whose name begins with the referenced name or begins it, or when one of the workspace's env prefixes begins its name. A listed env file, or a value it reaches, holding any other `$`, escaped or not, counts every listed and declared variable by value for that workspace, since Vite's expansion can build a name from a substituted value. The discovery's fingerprint counts the union over its discovered workspaces. The log names each such variable per workspace and why, never its value, whenever that changes, and warns, naming the env file or the variable whose value holds the `$`, when every one counts by value. On Windows a name compares whatever its case, as Windows looks it up, so `Path` and `PATH` are one variable, and names that fold together each keep their value. Each executor process starts with the environment the daemon copied as it began serving, the one the digest counts, so a test can read any variable, and a later change to the daemon's own environment reaches neither a test nor a fingerprint. Git, the Windows job helper and the Windows system tools read the daemon's live environment, since none runs a test. Vitest, Vite and std-env read no listed variable's value, at most whether it is set and non-empty, apart from what Vite's `.env` expansion and `envPrefix` carry, which counts by value; a variable the list misses fails toward staleness. Each input's digest is kept in memory only, the store keeps only each job's fingerprint, and no environment value or file content is stored or logged. The tracker reads every input in a reconciliation at start, when the watcher reports an error or lost events, when HEAD, the ref it names, `packed-refs`, a file git reads ignore rules from, a git config file or `rt-test.json` changes, and 5 minutes after the last reconciliation ended. Between reconciliations it re-reads only the paths events name. A file the discovery in effect lists under the consumer root that the inputs leave out is watched and read as an input is, whatever leaves it out: an event naming it, or a directory above it, reads it, a changed digest raises the input revision, a job running then is marked as for an input, and a reconciliation reads it again. On Linux each such file is watched through each existing directory on the way to it that the tree does not watch, re-armed as the entries leading to it change. Its fingerprint still reads it afresh. A file that comes to be listed, or stops being listed, moves the input revision as an edit, never as a change a job made. On Windows one recursive `fs.watch` covers the root; on Linux each included directory has its own, opened before the directory is listed. Every watch is opened on a real path, since Windows aborts the process on the first event of a watch opened through a short (8.3) name. While a reconciliation or a protection walk runs, while events remain unread, while the watcher is unhealthy (a watch of the root's tree that cannot open, a watch error or lost events), or when the input set cannot be established (an unreadable input, or a walk past 64 levels or 200,000 entries), no result is current. After a reconciliation that cannot establish the input set, the next input event brings the following one forward to 10 s after it ended, rather than waiting for the periodic reconciliation. A git file that cannot be located or watched is named among git's unread reasons, and a change to it is then seen only by the periodic reconciliation. A job begins only once every input event seen before it is read and no reconciliation runs. A discovery is stored under the fingerprint it started from only when no input changed and no event named one while it ran. A listed test module, setup file, global setup file or env file that the discovery in effect when it began did not list, or that lies outside the consumer root, and that was modified after the discovery began also stores it not fingerprinted, and so does a listed test module or setup file that cannot be found; a listed env file with nothing there when the discovery ends does not. A run is, only when it started with a fingerprint; no watcher failure or loss of the input set was recorded while it ran; no path that changed or that an event named while it ran lies among its workspace's inputs by the dependency build at the revision it started at, any that ended while it ran, or the one at the revision it ended at; and its workspace's fingerprint at the revision it ended at, once that revision's build has ended, equals the one it started from. Each build places a path by selecting it over that build's dependency information, whether or not the file exists at its revision, and every test module, setup file, global setup file and env file the discovery lists for the workspace lies inside; a path whose selection is refused lies inside, and every path does at a revision whose inputs are widened (its build failed or timed out, the discovery yields no selection input, selection refused the inputs, or the builds ended) and for a workspace the build's selection input leaves out. The daemon is an independent local process and the only component that executes tests ([ADR-0002](adr/0002-daemon-sole-executor.md)). The CLI and API talk to it over a named pipe on Windows or a Unix socket on Linux, one line of JSON per message, versioned (ADR-0001), and each connection's first answer proves it came from the user's own daemon ([ADR-0006](adr/0006-daemon-proves-itself.md)). The daemon hosts Vitest in an executor process it starts for each job, so no Vitest code runs in the daemon's own process, and nothing a job started outlives the job. The store is SQLite through `node:sqlite`, which needs no flag from Node 22.13, the supported floor. Do not introduce a remote backend for the core.

## Identity and freshness

Identify a project by its git repository's common directory, shared by every worktree checked out from it, or by its canonical root outside git; never by package name alone. Distinguish Vitest workspaces, parameterized test cases, duplicate display names, file paths, and run identities. Scope state to a worktree; two worktrees must not overwrite each other's results. On Windows, Vitest spells a module id with the drive-letter case its job started from (Vitest 4.1 keeps a lowercase `c:`, Vitest 5 gives `C:`), and Vite's `safeRealpathSync` switches from `fs.realpathSync` to `fs.realpathSync.native` partway through a job; RT Test stores each module path relative to its workspace's native real path and derives worktree and project identity from native real paths, so neither spelling reaches a stored identity.

Fingerprint relevant source and test content, fixtures, setup, configuration, the environment less its non-input variables' values, dependency lockfiles, runtime, runner version, adapter version, and selection policy version. Persist digests rather than secret environment values. Content hashes alone cannot establish that the input set is complete; record completeness and reasons for uncertainty.

Publish query snapshots with a sequence number, observed revision, last reconciliation time, and watcher health. On startup, mark old results unconfirmed until reconciliation finishes. An unknown input set cannot yield a current pass.

Results belong to the inputs actually executed. If an input changes during a run, do not promote that run to current: record it as invalidated and rerun from stable inputs. Keep a generation token so a late completion cannot replace a newer result. Because the daemon is the only executor, this replaces an agent-side run lock.

## State dimensions

| Dimension          | Intended values                                                                 |
| ------------------ | ------------------------------------------------------------------------------- |
| Last test outcome  | Passed, failed, skipped, error, never run                                       |
| Freshness          | Current, stale, unknown                                                         |
| Execution          | Idle, queued, running, interrupted                                              |
| Defect evidence    | Detected, survived, invalid experiment, unclear, anchor missing, never verified |
| Evidence freshness | Current, stale, unknown                                                         |

Collect module-level errors and run-level unhandled errors independently of individual test outcomes. Include discovered, selected, executed, skipped, stale, and unknown denominators in summaries. An empty or incomplete run cannot be called verified.

## Dependency index

Use a graph of workspaces, source files, functions, tests, configuration, fixtures, and other declared inputs. Store dependency edges separately from observed execution and defect-detection edges. Preserve the reason and producer of each edge.

Selection starts at workspace granularity: the edited file's workspace plus every workspace that depends on it, with configuration, setup, and lockfile changes as named broad fallbacks. File granularity then comes from static module dependencies, conservatively widened for unresolved behavior. Maintain reverse edges for invalidation. Analyze both the old and new graph around deletions and changed imports. Never remove a possible dependency solely because one prior test run did not execute it.

Function identity and per-test execution mapping are experimental until tested against refactoring, aliases, callbacks, mocks, concurrency, and module initialization. Stable test IDs must not depend only on a mutable display name. Per-test coverage instrumentation overhead must be measured separately.

Adapters can add edges or require broader selection. They must not suppress core uncertainty without a tested rule. An adapter result includes its version, completeness, affected inputs, and explanation.

## Convex adapter

Convex tests can use broad module registries and `api`/`internal` references, so every Convex test file globs the whole package and import-based selection, including `vitest related`, cannot see the real edges. The adapter ports Fleet Cooling's `scripts/test-blast-radius.mjs`: static imports plus `api.<path>` and `internal.<path>` name edges resolved against the generated API module list, where anything unresolved becomes a wildcard that widens every selection and an integrity failure refuses to narrow at all. It then extends to scheduled dispatch, components, triggers, and schema inputs.

Keep `convex-test` results distinct from typechecking, development backend synchronization, and live integration results. Use synthetic public fixtures. Do not make the daemon depend on a running Convex backend or automatically push code.

## Execution and falsification isolation

Reuse runner infrastructure where supported, while retaining the configured test isolation. Debounce edit bursts, prioritize direct targets and prior failures, and never run a test that holds a current result for the same inputs. Cancellation must leave explicit interrupted or stale states.

Falsification applies each mutation as an in-memory module transform in a separate Vitest instance and never writes a mutated file ([ADR-0003](adr/0003-transform-falsification.md)). Verify the baseline before mutation. Decide each verdict from run facts: the failure phase, the error kind, whether the mutated code was reached, and the baseline result. Only an assertion failure in the intended test counts as a detection; setup, collection, compile, timeout, and unrelated failures are invalid or unclear experiments. Ordinary results and mutation runs use different namespaces. Changing the test, mutation, input closure, or falsifier invalidates the evidence. Canary fixtures exercise the fact collector.

Defect definitions come from a configurable location in the consumer repository, and evidence stays under the local state directory ([ADR-0004](adr/0004-defect-definitions-in-consumer.md)). A missing mutation anchor is a per-defect state; the other defects still run.

The bootstrap `scripts/verify-defects.mjs` only validates the known hook-free fixtures listed in the repository's `defects.json` files. Its assertion-message check is not a general attribution algorithm and must not become one by copying it unchanged.

## Query surface

The CLI offers summary, `status <path>` with counts per state for files and folders, failures, affected selection, explanation, defect evidence, gaps, and `wait <files>`. Read operations never trigger execution. A wait binds to the input revision at call time and returns when every test covering the files has a current result or an explicit non-current state, or as superseded, naming the newer revision, as soon as a covering input changes, or as unsettled, naming each covering workspace's execution state, once its time limit passes. The default limit stays under the two minutes a coding agent's shell tool commonly allows a command, so an agent always gets an answer and can wait again.

Every summary and `status <path>` answer also carries the daemon's round: pending, naming what it waits for (the first reconciliation, the quiet window, the settling of the inputs, a dependency build, a rediscovery, or a job begun at an earlier input revision); planned at an input revision; or held after a failed scheduling step until the daemon tries again at the next input event or reconciliation. It carries each confirmed workspace's execution state: running; queued, with why it is due and up to 3 of the changed paths or broad fallbacks that chose it; interrupted by a change until the next round decides it; or idle, saying why no run is coming when its results are not current. It carries the latest selection: up to 20 changed paths, each with up to 20 workspaces it selected and up to 20 it reached that cannot run, up to 20 broad fallbacks, and the selected and total counts, or why no selection was made. On a workspace's latest run, it says whether this daemon stored it invalidated, with the reason. A query the daemon cannot answer, because no discovery is stored or the latest was refused as unreadable, says in its reason what the round is doing and names up to 20 jobs that ended with nothing stored, counting the rest.

Every `--json` payload carries a schema version, which also serves the later gap report that coding agents read to propose defects ([ADR-0005](adr/0005-no-model-calls.md)). There is no MCP server. Keep local endpoints scoped to an explicitly started project, authenticate access if using HTTP, and avoid binding to external interfaces by default. Do not leak source or environment values in summaries.
