# Architecture

## Current implementation

`packages/core/src/evidence.ts` assesses a historical result against a caller-supplied fingerprint. It preserves the outcome and returns freshness plus an explicit current-pass predicate. Missing or empty fingerprints produce unknown freshness. `packages/core/src/test-identity.ts` gives each test of one module a test identity (its Vitest workspace, Vitest project, module path, suite and test names, and its position among tests sharing those names), and marks a test whose names repeat in its module as a duplicate.

`packages/daemon` holds Vitest discovery and runs. `findVitestWorkspaces` lists a consumer's Vitest workspaces from the root `package.json` `workspaces` field and config file names (a `vitest.config.*`, or a `vite.config.*` in a directory whose `package.json` depends on Vitest), reading files only; it reports a root `pnpm-workspace.yaml` and each pattern it cannot expand as not read. It lists no directory that a `workspaces` pattern resolves outside the consumer root, through `..` or a link, deciding by canonical real path, and reports each such directory as not read with the real path it resolves to, so only the started project's own directories are loaded. When entries reached by different paths resolve to the same canonical real path, it lists only the first in pattern order, the consumer root first, and reports each later one as not read, naming the workspace listed in its place; a pattern that repeats a listed path adds nothing. So no directory is loaded or run twice. `discoverTests` loads each workspace's own Vitest, 4.1.x or 5.x, collects the modules of every project without running a test body or hook, and returns each test with its identity. It reports modules and workspaces that failed to load, workspaces with no supported Vitest, browser-mode projects, and typecheck modules, each as not discovered; it never collects a typecheck module. `runWorkspace` runs one workspace's tests on that same Vitest and records each test under the identity discovery gives it, with its outcome (passed, failed, skipped or error) and whether it finished or was interrupted as separate fields. It records modules that failed to load, hook errors on their module, crashed modules, modules not run and the run's unhandled errors apart from test outcomes, and gives a run in which no test passed or failed the reason nothing ran. The caller's `AbortSignal` interrupts a run, and a run Vitest stops itself under the consumer's `bail` is interrupted too. `discoverTests` takes an `AbortSignal` as well: once it aborts, discovery loads no further workspace, interrupts the collection in progress, and rejects with the signal's reason after the Vitest instance has closed and the host is restored, so an aborted discovery has no result. When a run or a discovery has not ended `FORCE_STOP_GRACE_MS` (10 s) after its signal aborted, Vitest force-stops its workers, which skips the project's `afterAll` hooks and teardown, and each run that loaded its workspace records whether that happened in a field beside its execution state. Work on Vitest's own thread, such as config loading or `globalSetup`, is beyond that force-stop. Discovery and runs share one queue, so none overlaps another, and each restores the host's environment and exit code. Each also runs in its workspace's directory, as that workspace's own `vitest` does, and restores the host's working directory with its environment. Neither writes into the consumer's tree. Each forces coverage, snapshot updates, Vitest's results cache and its module cache off over the workspace's config, so a snapshot assertion with no stored snapshot fails its test. Each also puts a setup file first in every project that keeps the project's snapshot environment, the consumer's own included, from saving or removing a snapshot file, since under update none Vitest still rewrites a snapshot file holding an entry no test checked; snapshots are still read through that environment. Each also names the config file Vitest would load and loads it through Vite's runner loader when Vite treats it as ESM, or otherwise through Vite's bundle loader, which writes nothing for a CommonJS config. Writes made by the consumer's own code (test bodies, hooks, setup files, `globalSetup`, plugins and config code) are the consumer's own. Five documented exceptions remain, all under `node_modules`: Vitest 4.1 on Vite 6.0.x, which has no runner loader, leaves an empty `node_modules/.vite-temp/`; a consumer that turns on Vite's dependency optimizer gets its cache in `node_modules/.vite/vitest`; a workspace whose project config files differ in format from its root config leaves `node_modules/.vite-temp/` for an ESM project config under a CommonJS root, and fails to load, as a failed workspace, a CommonJS project config under an ESM root; a Vitest 4.1 project config that itself sets `experimental.fsModuleCache` gets the module cache written; and Vitest 5, which creates its API token file whatever `api: false` says, writes it to `node_modules/.vitest/` when it cannot write the user data directory. Both load Vitest configs and import test files, so only the daemon's executor process calls them, after an explicit start. Each takes the start the user confirmed: it loads only a workspace whose path and chosen config file match a confirmed entry, and makes that match again as each workspace is loaded, so a config file added or swapped after the start is never loaded. Discovery lists every other workspace as not discovered, with the reason "not confirmed at start", and a run whose config file no longer matches loads nothing and is not stored.

`startDaemon`, in `@rt-test/daemon/client`, starts one detached daemon process for a consumer worktree. It starts one only for a caller that states the project is trusted and passes the start the user confirmed, and resolves once the daemon answers, before its discovery has finished. The daemon takes its endpoint first, before anything executes: a named pipe on Windows, or a Unix socket in `/tmp/rt-test-<uid>` on Linux, a directory only its user can enter. Each is named from the worktree identity and found from the user alone, never from the environment. It refuses the start when another process holds that endpoint. It then writes a fresh key to a directory only its user can use, and holds a lock on the worktree's store in the state directory until it exits. Every client sends a fresh challenge on each connection and trusts the connection only once its first answer proves, with that key, that it came from this user's daemon for the worktree ([ADR-0006](adr/0006-daemon-proves-itself.md)). The daemon executes nothing until the client, having proven the daemon's status, accepts the start over the spawn-time channel. A daemon whose starter closes that channel first abandons the start, and a start that fails after the spawn, by a refusal, by its deadline or before its acceptance, ends that daemon, so a failed start leaves nothing running. It then opens the store, starts tracking its inputs, waits for the first reconciliation of them to end, discovers the confirmed workspaces, runs each once, stores the discovery and each run under the input fingerprint it started from, or as not fingerprinted when its inputs moved while it ran, and idles until it is stopped. Vitest runs only in an executor process the daemon starts for each job, so Vitest's signal handlers, its environment writes and a stuck `globalSetup` never reach the daemon. The daemon ends that process's whole tree when the job ends, so nothing a job started outlives it: on Linux through the executor's process group, and on Windows through a job object that allows no breakaway, held by a helper process that dies with the daemon ([ADR-0006](adr/0006-daemon-proves-itself.md)). Only a process the project deliberately detaches on Linux, or one started outside the job on Windows, such as by a service, is not ended. When a job has not ended 15 s after a stop, which is the force-stop grace plus a margin, the daemon ends that tree and stores nothing for the job. The daemon speaks a versioned protocol of one JSON object per line, and writes nothing to a connection that has not sent it a line. Status reports the daemon's identities, its activity, and each job that ended with nothing stored. The hello, the stop request, its acknowledgement, the version-mismatch error and the proof are frozen for every protocol version, so `stopDaemon` checks and stops a daemon of any version, and resolves with its process id once that process has exited. On Linux, `SIGTERM` and `SIGINT` stop it the same way. The daemon logs to one file per worktree in the state directory, which also receives its stdout and stderr. `startPlan` builds what a start would execute, reading files only: the consumer root, the state directory `startDaemon` would use, each Vitest workspace `findVitestWorkspaces` lists with the config file the daemon would load for it, each source it could not read, and what `rt-test.json` at the root declares, as `readNonInputs` reads it: no file, its non-input patterns, or why it declares nothing. `servingDaemon` answers whether a daemon serves the worktree, telling nothing listening apart from an endpoint holder it cannot confirm. `packages/cli` is the `rt-test` CLI, the client's one production caller. `rt-test start` refuses when a daemon already serves the worktree or its endpoint holder cannot be confirmed, shows the plan, and starts the daemon with exactly that plan once the user answers y or yes on a terminal, or, without a terminal, only when `--trust` is passed. Trust lasts for that one invocation. `rt-test stop` stops the worktree's daemon and names the process that stopped. The daemon also answers two read-only queries from its open store: a summary of the worktree, and the status of one path inside its consumer root. It reads the worktree's latest stored discovery and each workspace's latest stored run in one read transaction, and gives each test of that discovery exactly one state from its workspace's latest run. That state is its outcome when it finished; interrupted; its module not run, crashed or failed to load; the run failed, found no supported Vitest or was interrupted before loading; not in the latest run; or never run when no run of its workspace is stored. No older run answers for a test. Freshness is counted beside the states: a test with no finished result is unknown, a finished result stored under another Vitest adapter version is stale, a test the discovery or its run marks duplicate is unknown while the discovery is not current, and any other goes to `assessEvidence` with its workspace's current input fingerprint, so it is current only when the digest it was stored under equals that fingerprint, and unknown when it was stored not fingerprinted or no current fingerprint can be computed. Every answer also carries the input revision, whether reconciliation is complete, when the last one ended, the watcher's health, and whether the discovery it counts from is current. A summary also lists what the discovery did not turn into tests, each with a reason cut to 1,000 characters, and each workspace's latest run. A path status counts the tests whose module file lies at or under the path, decided by canonical real path, gives one entry per file for a folder, and names the workspace, project and source entries above the path. A query starts no job and changes no activity. A stopping daemon, a missing discovery, a summary whose discovery holds nothing to count, a path outside the root or with nothing at or under it, a query that throws, and an answer longer than the protocol's 1 MiB line limit each get an error with its reason instead of an answer. `querySummary` and `queryPathStatus`, in `@rt-test/daemon/client`, send the queries on a connection whose hello the daemon proved, and turn an older daemon's unknown-request error into a reason to restart it. `rt-test summary` and `rt-test status` print the counts, never a pass or fail for a set. None of the four commands loads a Vitest module, consumer config or test file, and each gives one versioned JSON document on stdout under `--json`.

An input tracker in the daemon fingerprints each Vitest workspace's inputs. The inputs are every file under the consumer root except `.git`, `node_modules`, the daemon's state directory and log file, `rt-test.json` at the root, each declared non-input, and, inside git, every path git reports as ignored, in the consumer's repository and each nested one. A path whose ignored status is unknown is an input, and a new path is asked about with `git check-ignore` before it counts. Every test module the latest discovery lists is also an input of its own workspace, whatever git ignores; one the inputs leave out, such as one git ignores, is read afresh each time the fingerprint is composed. A declared non-input is a file a pattern in `rt-test.json`'s `nonInputs` member matches, decided by `declaredNonInputs` in `inputs/non-inputs.ts`, which selection also calls. No pattern removes a `package.json`, a `pnpm-workspace.yaml`, a lockfile, a Vitest or Vite config file, a `tsconfig*.json` or `jsconfig*.json` file, or a test module of the latest stored discovery, as `discoveredTestModules` lists them. The lifecycle hands the tracker the store's latest discovery before the first reconciliation, and each new discovery before that discovery's fingerprint is taken, so the stored digest already counts the modules it protects. The tracker then reads only the paths whose status that flips, without marking a job; any other input event during that read fails the discovery's fingerprint. A directory a pattern matches is still walked and watched. An event naming only a declared non-input is dropped before it is queued, so it moves no revision and no job. A declaration that cannot be used declares nothing, and every answer carries the reason. The tracker reads `rt-test.json` again at each reconciliation, and logs the declaration in effect after the first one and after each later one that finds it changed. A workspace's fingerprint is one digest over each input's root-relative path and content digest, a digest of the daemon's whole environment, the Node version, platform and architecture, the Vitest version the workspace resolves, the adapter version and the selection policy version. Every workspace covers the whole project's inputs until selection narrows it. The environment digest covers every variable, so a daemon restarted from a shell whose environment differs in any variable, such as a new terminal session's own variables, reads every result stale. Each input's digest is kept in memory only, the store keeps only each job's fingerprint, and no environment value or file content is stored or logged. The tracker reads every input in a reconciliation at start, when the watcher reports an error or lost events, when HEAD, the ref it names, `packed-refs`, a file git reads ignore rules from, a git config file or `rt-test.json` changes, and 5 minutes after the last reconciliation ended. Between reconciliations it re-reads only the paths events name. On Windows one recursive `fs.watch` covers the root; on Linux each included directory has its own, opened before the directory is listed. Every watch is opened on a real path, since Windows aborts the process on the first event of a watch opened through a short (8.3) name. While a reconciliation runs, while events remain unread, while the watcher is unhealthy (a watch of the root's tree that cannot open, a watch error or lost events), or when the input set cannot be established (an unreadable input, or a walk past 64 levels or 200,000 entries), no result is current. After a reconciliation that cannot establish the input set, the next input event brings the following one forward to 10 s after it ended, rather than waiting for the periodic reconciliation. A git file that cannot be located or watched is named among git's unread reasons, and a change to it is then seen only by the periodic reconciliation. A job begins only once every input event seen before it is read and no reconciliation runs. It is stored under the fingerprint it started from only when no input changed and no event named one while it ran; otherwise it is stored not fingerprinted, and the log names the changes. An event after which an input's content digest, size, modification time and change time all equal the tracker's last read of it from before the event counts as none, when that read came at least 2 s after both times, so the last-access event Windows raises on reading a file untouched for an hour marks no job. A reconciliation that reads an input while an event on it is unread, or finds any of the four moved with its content unchanged, keeps the earlier read for that comparison, and a directory walk keeps the earlier read of every input whose content it finds unchanged and marks every running job for each one an event would mark. Known limits: a gitignored file a test reads, such as build output or generated code, that changes with no input edit; a file outside the consumer root; `node_modules` changed with no lockfile or manifest edit, beyond the resolved Vitest version; unsaved editor buffers; a change to the system git config, or to a config file another includes, that sets `core.excludesFile`, seen only by the next reconciliation; an input change no event reports, seen only by the next reconciliation up to 5 minutes later; a declared non-input a test does read; a config an `extends` chain reaches under a name other than `tsconfig*.json` or `jsconfig*.json`, when a pattern matches it; a setup file a pattern matches; a write that restores an input's content, modification time and change time while a job runs, once the tracker's last read of it came at least 2 s after those times; an edit and its revert within one timestamp step, on a network share whose clock runs 2 s or more behind the daemon's; and a new test module a pattern matches, which no discovery lists until the discovery is next stale. On Linux that includes every inotify queue overflow, which is dropped silently.

`findPackageWorkspaces` lists the package workspaces it can read, the consumer root first and then each directory the root `package.json` `workspaces` patterns list, by the same expansion, outside-root refusal and real-path deduplication as `findVitestWorkspaces`. `buildDependencyInformation` reads and parses each package workspace's `package.json`, source files and tsconfig and jsconfig files, and the configs their `extends` chains name, loading and running none of them, into dependency edges that each record their producer: a `dependencies`, `devDependencies`, `peerDependencies` or `optionalDependencies` entry naming a listed workspace by key or alias, or pointing into its directory by a local path; a root `overrides`, `resolutions` or `pnpm.overrides` entry that links a local workspace, which every package workspace then depends on; and, for each Vitest workspace, the package workspaces holding its discovered test modules and its setup and global setup files, and every package workspace whose directory or package name one of its resolved config aliases' replacements begins, since an alias keeps the unmatched rest of an import. It also finds the dependencies no `package.json` dependency field declares. It walks each package workspace's directory without following a directory link, and skips nested package workspaces, `node_modules`, `.git`, and, when the consumer root lies in a git repository, every path git itself reports as ignored. It reads those paths once per build of the dependency information from `git ls-files`, run from outside the consumer's directories with `GIT_*` removed from git's environment and `core.fsmonitor` off. Outside git, or when git cannot be run or read, it skips no gitignored path. It asks git the same for each nested repository or submodule the walk enters. It parses each remaining `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts` or `.tsx` file with `oxc-parser`. A literal specifier in any of these forms produces an edge: a static import or re-export, a dynamic `import()`, `require()` or `require.resolve()`, a `vi.mock`, `vi.doMock`, `vi.importActual`, `vi.importMock`, `vi.unmock` or `vi.doUnmock` call, `import.meta.resolve()`, a TypeScript `import x = require()`, a `/// <reference path>`, an `import.meta.glob` pattern, or a `new URL(specifier, import.meta.url)`. A relative or absolute specifier (producer: relative import) depends on the package workspace it resolves into from the file's real directory, and a `new URL` or `/// <reference path>` specifier is always read as relative. A glob pattern depends on the workspace owning the directory before its first wildcard and on every workspace nested under that directory. A bare specifier (producer: bare import) depends on the listed workspace its package name names, whether or not a manifest declares it. A tsconfig or jsconfig `extends`, `references` path or `compilerOptions.paths` target (producer: tsconfig) does the same. A config without `paths` of its own takes the nearest `paths` along its `extends` chain, and targets resolve against the nearest `baseUrl` along that chain, else the directory of the config that sets the `paths`. So does each relative or bare `package.json` `imports` target (producer: manifest imports), and each link the walk meets (producer: link). A query or hash suffix does not change where a specifier resolves. A specifier resolving outside the consumer root, a URL-scheme specifier such as `node:fs`, and a `#` subpath import add no edge. Dependency information it cannot establish becomes a widening that makes the workspace depend on every package workspace and names its cause: a missing or unreadable manifest, a local path or workspace-protocol spec resolving to no listed workspace, a name matching no listed workspace while the listing is incomplete or a listed workspace's name cannot be read, an alias replacement that is neither an absolute path nor a bare package name, a Vitest workspace whose tests are not known, and a root override whose value is neither a string nor an object of overrides or references a root dependency the root does not declare, which widens every package workspace. The scan widens the same way on a file, directory or link it cannot read, and on a source, tsconfig or jsconfig file that does not parse, nests brackets more than 1,000 deep, or whose syntax tree cannot be walked. It also widens on a malformed `extends`, `references`, `paths` or `baseUrl`, a `.vue`, `.svelte`, `.astro` or `.mdx` file, and a tsconfig with `paths`, its own or inherited, whose `extends` chain it cannot follow. A walk deeper than 40 directory levels, or past 50,000 files and directories in one workspace (skipped paths not counted), widens too. `selectTests` maps a change, a set of root-relative paths, to Vitest workspaces: each path selects the deepest package workspace holding it and every workspace that depends on it, each through one shortest chain of edges and widenings. A path `rt-test.json` declares a non-input, given the declaration and the protected test modules its caller passes, selects nothing, and its report names the matching pattern. A lockfile, any `package.json`, a path owned by the root while another package workspace is listed, a path owned by a listed directory that has no `package.json` and is not a Vitest workspace, a Vitest or Vite config file outside a Vitest workspace's directory, and `rt-test.json` at the root each select every Vitest workspace; a config file in a Vitest workspace's directory and a setup or global setup file select their Vitest workspaces and those workspaces' dependents. It returns each selected test with every reason, each changed path with what it selected or why it selected nothing, the broad fallbacks and widenings it used, selected and total test and workspace counts that say when they are incomplete, a nothing-selected state distinct from a selection, and the selection policy version. It refuses a change holding an absolute or root-escaping path, and never selects a workspace the caller marks not runnable. Until file-granularity selection, the scan neither sees nor widens for these known limits:

- a computed module path in any of those forms, such as `import(expr)`, `require(expr)`, `vi.mock(expr)` or a template literal with a substitution;
- a file read by a built path, such as `path.join(__dirname, "../../other")`;
- CSS `@import` and other asset references that Vite plugins resolve;
- Vite root-absolute (`/src/x`) and `file:` URL specifiers;
- code generated at build time, and, inside git, any gitignored file, such as build output or generated code, which is not scanned;
- imports a Vite plugin rewrites in a file the parser accepts;
- type-level references (`/// <reference types>`, `import()` types), which cannot change a test's runtime result.

A file that overflows the parser's native stack ends the selecting process; 2.3e isolates it. The daemon does not call `buildDependencyInformation` or `selectTests` yet, so selection has no production caller. `openStore` keeps runs and discoveries in a `node:sqlite` database, `store.sqlite`, in the consumer's state directory (`.rt-test` under the consumer root unless the caller names another). Each stored run (one workspace's `runWorkspace` result) and each discovery is bound to its project identity (the git repository's common directory, or the consumer root outside git), its worktree identity (the consumer root's canonical real path), an identity the store assigns, the input fingerprint its caller gives (a digest, or explicitly not fingerprinted) and the Vitest adapter version, and becomes visible whole. Every read answers for one project and worktree, so worktrees can share one state directory, and the store migrates a store of the previous schema version in place, reading each of its runs as not force-stopped, since that version's code never force-stopped a run. It refuses, leaving the file unchanged, a store of any other schema version or a file that is not an RT Test store. The daemon opens it at its start, and is its only production writer. The sections below describe the intended architecture. Every component is TypeScript on Node ([ADR-0001](adr/0001-typescript-on-node.md)), and terms follow [the glossary](glossary.md).

## Components

| Component          | Responsibility                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------- |
| Daemon             | The sole executor of tests and falsification for one started project                        |
| Vitest integration | Discover tests across workspaces, schedule supported runs, consume structured events        |
| Input tracker      | Watch saved inputs, reconcile content, assign input revisions                               |
| Dependency index   | Store workspace, module, and function relationships and reasons for uncertainty             |
| Scheduler          | Deduplicate work, prioritize ordinary tests, invalidate runs whose inputs moved             |
| Evidence store     | Persist inputs, runs, results, graph versions, and defect evidence                          |
| Query service      | Serve consistent snapshots and waits without running tests                                  |
| Falsifier          | Run baseline and mutated experiments as in-memory transforms and record run facts           |
| Framework adapter  | Add otherwise hidden dependency edges and synchronization information                       |
| CLI and API        | Query and wait through versioned `--json` output or a small programmatic API; never execute |

The daemon is an independent local process and the only component that executes tests ([ADR-0002](adr/0002-daemon-sole-executor.md)). The CLI and API talk to it over a named pipe on Windows or a Unix socket on Linux, one line of JSON per message, versioned (ADR-0001), and each connection's first answer proves it came from the user's own daemon ([ADR-0006](adr/0006-daemon-proves-itself.md)). The daemon hosts Vitest in an executor process it starts for each job, so no Vitest code runs in the daemon's own process, and nothing a job started outlives the job. The store is SQLite through `node:sqlite`, which needs no flag from Node 22.13, the supported floor. Do not introduce a remote backend for the core.

## Identity and freshness

Identify a project by its git repository's common directory, shared by every worktree checked out from it, or by its canonical root outside git; never by package name alone. Distinguish Vitest workspaces, parameterized test cases, duplicate display names, file paths, and run identities. Scope state to a worktree; two worktrees must not overwrite each other's results.

Fingerprint relevant source and test content, fixtures, setup, configuration, declared environment inputs, dependency lockfiles, runtime, runner version, adapter version, and selection policy version. Persist digests rather than secret environment values. Content hashes alone cannot establish that the input set is complete; record completeness and reasons for uncertainty.

Publish query snapshots with a sequence number, observed revision, last reconciliation time, and watcher health. On startup, mark old results unconfirmed until reconciliation finishes. An unknown input set cannot yield a current pass.

Results belong to the inputs actually executed. If an input changes during a run, do not promote that run to current: record it as invalidated and rerun from stable inputs. Keep a generation token so a late completion cannot replace a newer result. Because the daemon is the only executor, this replaces an agent-side run lock.

## State dimensions

| Dimension          | Intended values                                                                 |
| ------------------ | ------------------------------------------------------------------------------- |
| Last test outcome  | Passed, failed, skipped, error, never run                                       |
| Freshness          | Current, stale, unknown                                                         |
| Execution          | Idle, queued, running, interrupted                                              |
| Defect evidence    | Detected, survived, invalid experiment, unclear, anchor missing, never verified |
| Evidence freshness | Current, stale, unknown                                                         |

Collect module-level errors and run-level unhandled errors independently of individual test outcomes. Include discovered, selected, executed, skipped, stale, and unknown denominators in summaries. An empty or incomplete run cannot be called verified.

## Dependency index

Use a graph of workspaces, source files, functions, tests, configuration, fixtures, and other declared inputs. Store dependency edges separately from observed execution and defect-detection edges. Preserve the reason and producer of each edge.

Selection starts at workspace granularity: the edited file's workspace plus every workspace that depends on it, with configuration, setup, and lockfile changes as named broad fallbacks. File granularity then comes from static module dependencies, conservatively widened for unresolved behavior. Maintain reverse edges for invalidation. Analyze both the old and new graph around deletions and changed imports. Never remove a possible dependency solely because one prior test run did not execute it.

Function identity and per-test execution mapping are experimental until tested against refactoring, aliases, callbacks, mocks, concurrency, and module initialization. Stable test IDs must not depend only on a mutable display name. Per-test coverage instrumentation overhead must be measured separately.

Adapters can add edges or require broader selection. They must not suppress core uncertainty without a tested rule. An adapter result includes its version, completeness, affected inputs, and explanation.

## Convex adapter

Convex tests can use broad module registries and `api`/`internal` references, so every Convex test file globs the whole package and import-based selection, including `vitest related`, cannot see the real edges. The adapter ports Fleet Cooling's `scripts/test-blast-radius.mjs`: static imports plus `api.<path>` and `internal.<path>` name edges resolved against the generated API module list, where anything unresolved becomes a wildcard that widens every selection and an integrity failure refuses to narrow at all. It then extends to scheduled dispatch, components, triggers, and schema inputs.

Keep `convex-test` results distinct from typechecking, development backend synchronization, and live integration results. Use synthetic public fixtures. Do not make the daemon depend on a running Convex backend or automatically push code.

## Execution and falsification isolation

Reuse runner infrastructure where supported, while retaining the configured test isolation. Debounce edit bursts, prioritize direct targets and prior failures, and never run a test that holds a current result for the same inputs. Cancellation must leave explicit interrupted or stale states.

Falsification applies each mutation as an in-memory module transform in a separate Vitest instance and never writes a mutated file ([ADR-0003](adr/0003-transform-falsification.md)). Verify the baseline before mutation. Decide each verdict from run facts: the failure phase, the error kind, whether the mutated code was reached, and the baseline result. Only an assertion failure in the intended test counts as a detection; setup, collection, compile, timeout, and unrelated failures are invalid or unclear experiments. Ordinary results and mutation runs use different namespaces. Changing the test, mutation, input closure, or falsifier invalidates the evidence. Canary fixtures exercise the fact collector.

Defect definitions come from a configurable location in the consumer repository, and evidence stays under the local state directory ([ADR-0004](adr/0004-defect-definitions-in-consumer.md)). A missing mutation anchor is a per-defect state; the other defects still run.

The bootstrap `scripts/verify-defects.mjs` only validates the known hook-free fixtures listed in the repository's `defects.json` files. Its assertion-message check is not a general attribution algorithm and must not become one by copying it unchanged.

## Query surface

The CLI offers summary, `status <path>` with counts per state for files and folders, failures, affected selection, explanation, defect evidence, gaps, and `wait <files>`. Read operations never trigger execution. A wait binds to the input revision at call time and returns when every test covering the files has a current result or an explicit non-current state, or as superseded, naming the newer revision, as soon as a covering input changes.

Every `--json` payload carries a schema version, which also serves the later gap report that coding agents read to propose defects ([ADR-0005](adr/0005-no-model-calls.md)). There is no MCP server. Keep local endpoints scoped to an explicitly started project, authenticate access if using HTTP, and avoid binding to external interfaces by default. Do not leak source or environment values in summaries.
