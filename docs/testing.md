## Commands

Use `bun run test:run` for Vitest, `bun run test:defects` for the bootstrap defect checks, `bun run check:defects` for the static catalog check, `bun run lint` for oxlint, and `bun run check` for all current gates. Use `bun run test` only when you intend to leave a watcher running. The project does not use Bun's built-in test runner.

## Name the defect

### Named-defect rule and where records live

Give every behavior test a concrete wrong behavior to reject. Record expected behavior independently from the implementation. Prefer examples that distinguish the intended behavior from a plausible mistake.

Each workspace keeps a `defects.json` beside its tests, associating each named test with one explicit mutation and the file it mutates; separate files let lanes in different workspaces add defects without sharing a file. Defect ids are unique across the repository.

## Bootstrap falsification

### Snapshot, sandboxes and links

`scripts/verify-defects.mjs` reads `packages/`, `lint/`, `scripts/`, `test/`, `.claude/hooks/`, the root tsconfigs, `_agent-docs/_flow-config.yaml`, and `.claude/settings.json` into an in-memory snapshot, skipping `node_modules` and `dist` and never following a link, and writes that snapshot into each of its sandboxes. A run's sandboxes share one directory under the operating system's temp directory, named `rt-test-verify-defects-<pid>-<start time>-<random>` after the id and start time of the process that owns it, and the check refuses a temp directory at or inside the repository, or at or below any `node_modules`. It records the links a sandbox needs and recreates them in every sandbox, as a relative symlink or, on Windows, a junction, which can hold only an absolute path. A link in a copied directory whose target the snapshot also copies, such as the `packages/<pkg>/node_modules/@rt-test/<name>` link Bun makes for a workspace dependency, points at that sandbox's own copy. A link in a copied directory into the root `node_modules`, and one link per package in the root `node_modules` (each package of a scope, and no entry whose name starts with a dot), point at the installed package, so a sandbox's `node_modules` is a real directory and Vitest's results cache stays inside the sandbox. The check refuses a root `node_modules` entry that resolves into the repository outside `node_modules`, as a hoisted workspace package does, since a sandbox would run that live source. Since the sandboxes sit outside the repository and below no `node_modules`, an import none of those links answers fails to resolve. It resolves Vitest through its package manifest and executes its Node entry point with argument arrays.

### What a run requires, and how it fails or stops

The check requires every `D###` test to have exactly one defect record, whether its title follows `it(` on the same line or the next, and every mutation anchor to match exactly once. It requires each sandbox to match the snapshot byte for byte and to hold exactly the recreated links, each with its recorded target, and a baseline to pass every named test and no other test before any mutation: a full run's baseline runs the whole configured suite, so a test file with no named test fails the check. New tooling tests under the root `test/` carry no named defect, so run a whole-catalog check the owner asks for as `node scripts/verify-defects.mjs --ids <ids>` over every product record: each record in a `defects.json` under `packages/`, and the run-cleanup records above that mutate files under `packages/`. A run filtered by `--ids`, `--edited` or `--changed` baselines only the test files it verifies. Each sandbox then takes one defect at a time from a shared queue: it applies the exact mutation to the file its record names, runs only the test file that holds the named test, filtered to that test, requires that file alone to be collected and that test to fail with an assertion failure, and restores the file. A mutated run that reports the named test file alone but not exactly one named assertion failure is reported with the run's exit status, its passed count and each failed test's first message line. A baseline or mutated run that otherwise passes or detects still fails when it did not end cleanly: Vitest reported no run end, an unhandled error Vitest reported or its main process recorded, a `process.exit` call its main process recorded, such as a close timeout, or no recorded exit, which a kill leaves; a named assertion failure beside any of these is not a detection. Every failure the check reports for a Vitest run that started, a baseline or a mutated run, whether stopped, interrupted or finished, ends with how Vitest ended the run and its unhandled errors, what the run's main process recorded about its ending, then that run's stderr and its stdout tail; a verdict on a run that wrote a report first quotes each file's error and the tests the report left pending. Each Vitest run carries a reporter, `scripts/lib/defects/progress-reporter.mjs`, that writes a line per collected module and per started or finished test and hook, and one at the run's end with Vitest's end reason and unhandled errors, which the JSON report leaves out. Vitest's main process also loads `scripts/lib/defects/exit-witness.mjs` through `--import`, which appends to a record beside the report each uncaught exception, each unhandled rejection while another listener handles it, each `process.exit` call with its caller, and the exit itself, changing none of them. The check stops a run only when no such line arrives for twice `LONGEST_TEST_TIMEOUT_MS` in `test/scripts/longest-test-timeout.mjs`, the longest per-test timeout any suite may declare. It ends Vitest's main process and then its pool workers, each only while its id still names the worker it listed, sparing the daemon suite's watchdog, and fails naming the tests still running. A run holding a test whose timeout, times its retries and repeats, exceeds that constant, or a hook or teardown timeout that does, fails naming it. A stopped or interrupted run is a failure, never a detection. When the queue is empty, each sandbox must match the snapshot byte for byte again, `dist` and `node_modules` included, apart from Vitest's results cache, and hold the same links, and a final baseline must pass. The working files and the recorded links must still match when the check ends, and the run's directory is removed on exit; a failure to remove it fails the check. A run killed before then leaves its directory behind, and the next run removes each leftover whose owning process has exited and names it; a process that now holds the owner's id with another start time is not the owner, a leftover named by the id alone is kept while any process holds that id, and a leftover whose owner cannot be checked is kept and the reason logged.

### Jobs and selectors

`--jobs <n>` sets the number of sandboxes; it defaults to three quarters of the logical cores, and at least 1. Three selectors filter the run, which verifies the union of what they select. `--ids <ids>` verifies the named defects, written as one comma-separated list (`--ids D12,D40`) and repeatable; an id no `defects.json` records, a list that names no id, or a stray argument stops the run before any sandbox starts. `--edited` verifies the defects whose record differs from `HEAD`, or whose test file or mutated file differs from `HEAD` (staged, unstaged, or untracked); it follows no import and never widens, so a change to a file that no record tests or mutates selects nothing. `--changed` (`bun run test:defects:changed`) verifies those defects and also the ones whose test file or mutated file reaches a changed file through relative imports. A changed file the sandbox copies, or a changed `vitest.config.ts`, `package.json` or `bun.lock`, that no such import reaches selects every defect, and the run names it; type declarations and `defects.json` files are exempt. It follows only relative imports, so a test that reaches a changed file by spawning a process or reading it at run time is not reselected. A filtered run prints the selected and total counts and each selected defect with its reasons, and its last line names its selectors and says it is not the full run. Filtered runs are for iterating and for a lane's proof, which is the only proof a defect gets: `bun run check` re-proves none, and runs `scripts/check-defects.mjs` instead, which requires each `D###` test to have exactly one record and each mutation anchor to match exactly once without running a test. A filtered run says nothing about the defects it skipped, and a run that selects no defect exits 0 after saying that none was verified.

### Hook-free tests and mutation anchors

Keep bootstrap tests hook-free: do shared setup lazily inside the test body, so a setup failure fails the test with a non-assertion error rather than passing as a detection. This check is deliberately limited to those known hook-free tests. It does not classify arbitrary project failures or implement the product's general mutation engine. It does not establish that a mutation kills only one test in the whole suite. Preserve that distinction in claims and reports.

Changing source formatting may invalidate an exact mutation anchor. Update it deliberately; do not silently skip or fuzzy-match missing anchors. A changed test or mutation requires fresh evidence.

## Selection validation

For each controlled edit, run the selected tests and an independent full baseline against the same input snapshot. Compare discovered failures and invalidated states, not just exit codes. Keep negative controls where unrelated changes should retain evidence.

The edit corpus (`test/fixtures/daemon/edit-corpus/`, checked by `packages/daemon/test/edit-corpus.ts`) does this for a consumer shaped like Fleet Cooling, on Vitest 4.1: each sequence of edits is replayed against RT Test's own daemon from the committed fixture, and at a baseline before the first edit and after each edit, once a wait on its files has settled and the daemon is idle, a full run by plain Vitest's command line over the same files is compared test by test with the results the daemon stored and the freshness its answers give. The check reports a selection miss (NFR2), a duplicate execution (NFR1), any other disagreement, a workspace run outside the set the edit declares, a declared run that did not happen, an edit whose full run fails other than what it declares, a wait that does not settle, a daemon that does not go idle, a full run it cannot use, and an input revision moved by an edit that declares no run. Vitest 5 is not in the corpus.

Use observed execution to improve explanations and prioritization before trusting it to narrow selection. Any narrowing rule must have fixtures showing both its precision and its conservative fallback.
