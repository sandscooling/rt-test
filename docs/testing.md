# Testing RT Test

## Commands

Use `bun run test:run` for Vitest, `bun run test:defects` for the bootstrap defect checks, `bun run lint` for oxlint, and `bun run check` for all current gates. Use `bun run test` only when you intend to leave a watcher running. The project does not use Bun's built-in test runner.

## Name the defect

Give every behavior test a concrete wrong behavior to reject. Record expected behavior independently from the implementation. Prefer examples that distinguish the intended behavior from a plausible mistake.

Each workspace keeps a `defects.json` beside its tests, associating each named test with one explicit mutation and the file it mutates; separate files let lanes in different workspaces add defects without sharing a file. ## Bootstrap falsification

`scripts/verify-defects.mjs` reads `packages/`, `lint/`, `scripts/`, `test/`, `.claude/hooks/`, the root tsconfigs, `_agent-docs/_flow-config.yaml`, and `.claude/settings.json` into an in-memory snapshot, skipping `node_modules` and `dist` and never following a link, and writes that snapshot into each of its sandboxes. A run's sandboxes share one directory under the operating system's temp directory, named `rt-test-verify-defects-<pid>-<random>` after the process that owns it, and the check refuses a temp directory at or inside the repository, or at or below any `node_modules`. It records the links a sandbox needs and recreates them in every sandbox, as a relative symlink or, on Windows, a junction, which can hold only an absolute path. A link in a copied directory whose target the snapshot also copies, such as the `packages/<pkg>/node_modules/@rt-test/<name>` link Bun makes for a workspace dependency, points at that sandbox's own copy. A link in a copied directory into the root `node_modules`, and one link per package in the root `node_modules` (each package of a scope, and no entry whose name starts with a dot), point at the installed package, so a sandbox's `node_modules` is a real directory and Vitest's results cache stays inside the sandbox. The check refuses a root `node_modules` entry that resolves into the repository outside `node_modules`, as a hoisted workspace package does, since a sandbox would run that live source. Since the sandboxes sit outside the repository and below no `node_modules`, an import none of those links answers fails to resolve. It resolves Vitest through its package manifest and executes its Node entry point with argument arrays.

The check requires every `D###` test to have exactly one defect record, whether its title follows `it(` on the same line or the next, and every mutation anchor to match exactly once. It requires each sandbox to match the snapshot byte for byte and to hold exactly the recreated links, each with its recorded target, and a baseline to pass every named test and no other test before any mutation: a full run's baseline runs the whole configured suite, so a test file with no named test fails the check, and a `--changed` run's baseline covers only the test files it verifies. Each sandbox then takes one defect at a time from a shared queue: it applies the exact mutation to the file its record names, runs only the test file that holds the named test, filtered to that test, requires that file alone to be collected and that test to fail with an assertion failure, and restores the file. A timeout or interrupted run is a failure, never a detection. When the queue is empty, each sandbox must match the snapshot byte for byte again, `dist` and `node_modules` included, apart from Vitest's results cache, and hold the same links, and a final baseline must pass. The working files and the recorded links must still match when the check ends, and the run's directory is removed on exit; a failure to remove it fails the check. A run killed before then leaves its directory behind, and the next run removes each leftover whose owning process has exited and names it.

`--jobs <n>` sets the number of sandboxes; it defaults to three quarters of the logical cores, and at least 1. `--changed` (`bun run test:defects:changed`) verifies only the defects whose record differs from `HEAD`, or whose test file or mutated file, or any file either reaches through relative imports, differs from `HEAD` (staged, unstaged, or untracked). A changed file the sandbox copies, or a changed `vitest.config.ts`, `package.json` or `bun.lock`, that no such import reaches selects every defect, and the run names it; type declarations and `defects.json` files are exempt. It prints each selected defect with its reasons. It is for iterating: the full run inside `bun run check` is the gate, and a `--changed` run says nothing about the defects it skipped. It follows only relative imports, so a test that reaches a changed file by spawning a process or reading it at run time is not reselected, and a run that selects no defect exits 0 after saying that none was verified.

Keep bootstrap tests hook-free: do shared setup lazily inside the test body, so a setup failure fails the test with a non-assertion error rather than passing as a detection. This check is deliberately limited to those known hook-free tests. It does not classify arbitrary project failures or implement the product's general mutation engine. It does not establish that a mutation kills only one test in the whole suite. Preserve that distinction in claims and reports.

Changing source formatting may invalidate an exact mutation anchor. Update it deliberately; do not silently skip or fuzzy-match missing anchors. A changed test or mutation requires fresh evidence.

## Future integration fixtures

Build synthetic projects for plain TypeScript, mocked imports, shared setup, parameterized tests, dynamic imports, generated files, and framework registries. Add fixtures for setup errors, collection errors, unhandled errors, timeouts, runner crashes, and interrupted runs.

Exercise missed watcher events, edits during runs, branch switches, renamed tests, duplicate names, new untracked files, and deleted dependencies. Check that defects in the selection system cannot produce false current passes.

## Selection validation

For each controlled edit, run the selected tests and an independent full baseline against the same input snapshot. Compare discovered failures and invalidated states, not just exit codes. Keep negative controls where unrelated changes should retain evidence.

Use observed execution to improve explanations and prioritization before trusting it to narrow selection. Any narrowing rule must have fixtures showing both its precision and its conservative fallback.

## Performance validation

Report cold and warm measurements separately. Include runner-only baselines, hardware, OS, runtime versions, file/test counts, and the edit class. Query latency, invalidation latency, selection time, execution time, and instrumentation overhead are separate metrics.

Keep repeatable benchmarks out of correctness tests where machine timing would cause flakes. Never label provisional budgets as achieved measurements.
