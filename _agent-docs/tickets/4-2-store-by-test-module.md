# Ticket 4.2: Results stored by test module

## Ticket

As a developer whose agents edit a consumer while RT Test runs its tests,
I want each stored run to hold the results of the test modules it covered, each bound to an input fingerprint of its own, and to replace only those modules' earlier results,
so that a run of part of a Vitest workspace can be stored without displacing, staling or hiding the results of the test modules it was not sent, while every answer reads as it does today.

## Acceptance Criteria

A run **covers** the test modules it was sent and every other test module it recorded. Until ticket 4.6 names test modules in a run request, the test modules a run was sent are those the discovery it was planned from lists for its Vitest workspace. A covered module the run did not record has no result from that run, and no earlier run answers for it (the orchestrator's ruling, 12:59 on 2026-10-02, quoted in Dev Notes).

- [ ] AC1: Every stored run, whatever its status (`ran`, `unsupported`, `failed`, `interrupted-before-load` or `crashed`), is stored with the test modules it covered, each named by its Vitest project and module path and bound to an input fingerprint of its own, a digest or explicitly not fingerprinted, and the store gives them back as they were handed in, across a close and a reopen. What the run recorded reads back exactly as it recorded it, until a later run replaces part of it: a covered module the run did not record adds no module and no test to the run, and an earlier run a later one took modules from reads back as the modules and tests it still holds. (FR25)
- [ ] AC2: The run write throws naming what is wrong, stores nothing and removes nothing, when the covered modules it is handed are not a list, name one test module twice, give a module a fingerprint that is neither a digest nor explicitly not fingerprinted (an empty digest included), or leave out a module the run recorded. (FR25)
- [ ] AC3: A stored run replaces the earlier results of exactly the test modules it covers, within its project, worktree and Vitest workspace: once its write commits, no earlier run covers such a module or holds a module row or a test row of it, whatever status, fingerprint or adapter version the earlier result was stored under. What an earlier run holds for the test modules the new run does not cover stays as it was: that run still covers them under the fingerprints it stored, with their module and test rows. (FR25)
- [ ] AC4: Once a run's write commits, the store holds no earlier run of that workspace that covers no test module: a run the write left with none and a run that covered none from the start are both removed, with every row of theirs. A stored run that itself covers no test module is kept, and is its workspace's run stored last, until the next run of its workspace is stored. (FR25)
- [ ] AC5: The removal reaches nothing outside the stored run's project, worktree and workspace, and leaves every discovery and all defect evidence as it was. It commits together with the insert: a write that fails leaves every earlier run with its covered modules, module rows and test rows, and a second connection reading while the write is in progress reads the earlier results, never neither. It rebuilds no record, so an earlier run the readers refuse as unreadable is replaced like any other. (FR25)
- [ ] AC6: The store reads, for one project and worktree, each test module a stored run covers, named by its workspace path, Vitest project and module path, with the identity of the run that covered it last, by stored order, the input fingerprint that run stored for it, and whether that run recorded it. A run that covered the module earlier never stands in where the store holds several, no module of another project or worktree is read, and every row comes from the one snapshot its caller holds, which until ticket 4.3 is the run write's transaction. (FR25)
- [ ] AC7: The run write reports how many test modules the run covered and how many of them it stored again under the fingerprint they held. A covered module counts when the run that covered it last before the write, the one AC6's read gives, recorded it, stored it under a digest, and the new run stores the module under that same digest. A module no earlier run covered, a module its last covering run did not record (it has no result from that run), a module last stored not fingerprinted and a module the new run stores not fingerprinted do not count. (NFR1)
- [ ] AC8: For each run the daemon stores, its log holds one `run stored:` entry, written once the write has committed and ahead of the run's `run ended` entry, naming the workspace, the fingerprint digest the run is bound to or that it is not fingerprinted, the number of test modules the run covered and the number of them stored again under the fingerprint they held, in the wording Dev Notes gives. A run whose write failed has no such entry. (NFR1)
- [ ] AC9: For each run it stores, the daemon hands the store as covered every test module the discovery the run was planned from lists for the run's workspace, each Vitest project's listing of a file apart, and every other module the run recorded, each under what the run itself is stored under: its workspace's input fingerprint, or not fingerprinted. (FR25)
- [ ] AC10: No answer changes. Each workspace's run stored last, and each such run refused as unreadable, are read as they are today; a stored run reads back with the fingerprint it was stored under; and `summary`, `status`, `wait`, `changes`, `defects` and the schedule give, for the same stored runs and inputs, the answers they give today. (FR25)
- [ ] AC11: A version 11 store opens at version 12 in place, and its header then reads version 12, which is what version 11's code refuses as newer. Each workspace keeps its run stored last, which covers the modules it recorded, each under the run's own fingerprint, and covers none when it recorded none. An earlier run of a workspace, which no reader reads today, is removed with its rows. The kept runs, the discoveries and the defect evidence read back as they were stored. (FR25)
- [ ] AC12: A store of each version 1 to 10 opens at version 12 reading what its migration gives it today, with what AC11 gives a version 11 store. (FR25)
- [ ] AC13: Saves that store runs covering the same test modules leave the store's size where it was: once a worktree's discovery and each workspace's run have been stored in place of earlier ones, 100 further saves add no page to the file. (FR25)
- [ ] AC14: The store's connection enforces its tables' references: a covered module, a module row or a test row that names a run or a module the store does not hold is refused. The defect a test can prove is enforcement turned off. That the opener asks for it by name, where `node:sqlite` enforces unasked on the runtime probed (Dev Notes, Settled facts), changes no behavior a test can see there, so a review reads it. (FR3)

### What the criteria rest on

ADR-0010 (`docs/adr/0010-results-by-test-module.md`, accepted): "The test module is the unit. A run covers a list of one workspace's test modules and is stored whole. Each test's state comes from the latest stored run that covered its test module, and that module's result is bound to an input fingerprint of the module's own inputs". "A stored run replaces the earlier results of exactly the modules it covers. No later run covers a test module that left its workspace, so a stored discovery removes the results of the modules its workspaces no longer list." The second of those sentences is ticket 4.4's to build (Known limits). "Duplicate execution (NFR1) is measured where every result passes: the write that replaces a module's result compares the fingerprint it stores with the one it replaces, and the log counts each module stored again under the same one."

FR25: "Store each run as the results of the test modules it covered, each bound to that module's input fingerprint, and answer each test's state and freshness from its test module's latest result, so a run of some of a workspace's test modules replaces only theirs." This ticket delivers the storing half; ticket 4.3 delivers the answering half. NFR1: "Never execute a test while it holds a current result for the same input fingerprint, except to falsify it or to rerun an invalidated run." FR3: "Persist results bound to project, worktree, run identity, input fingerprint, and adapter version, and keep them available across a daemon restart."

The sprint's scope for this ticket (`_agent-docs/sprints/sprint-4-file-level-results.md`): "every stored run names the test modules it covered, each with its own input fingerprint, whatever the run's status; the store reads each test module's latest result; a stored run replaces the earlier results of exactly the modules it covers and removes a run left with none, which is what lane store-growth's rule (a stored run replaces its workspace's earlier runs) becomes; the write compares each module's fingerprint with the one it replaces, and the log line that names what a stored run is bound to counts the modules stored again under the same one, which is where NFR1 is read once a run covers part of a workspace; a version 11 store migrates in place, each run covering the modules it recorded under the run's own fingerprint; each entry of `STORE_MIGRATIONS` is composed from one step per version (3.4's review). Callers hand every module its workspace's fingerprint, so no answer changes."

Glossary (`docs/glossary.md`), verbatim. **Test module**: "One test file as one Vitest project runs it: the unit RT Test runs, stores a result for and rates for freshness." **Run**: "One execution of a selection by the daemon, under its own run identity." **Result**: "A test's outcome bound to the run and input fingerprint that produced it." **Input fingerprint**: "A digest of every input, the environment, and the runtime and tool versions that can change a test's result." **Duplicate execution**: "Running a test again while it holds a current result for the same input fingerprint." The glossary has no entry for what a run covers; the criteria's opening paragraph defines it, and the exact glossary text is proposed to the orchestrator in this ticket's ready report.

"Covers" already has two other uses in this code, so name the new symbols by the run they belong to. A test covers a file in `wait` and `changes` ("every test covering the given files"), and a discovery keeps its not-covered package workspaces (`not_covered` on `discoveries`, `ADD_NOT_COVERED`, `NotCoveredWorkspace`), which have nothing to do with a run's covered modules. The glossary's entry for the load record tells writers to avoid "coverage" for it, and this ticket uses "covered modules" and never "coverage" for the same reason.

### Known limits

- **A version 11 run that never loaded covers no module after the migration** (accepted by the orchestrator, 12:59). This ticket changes no answer for it, since every reader still takes each workspace's run stored last. The migration keeps only each workspace's run stored last (13:31, (b)), so no earlier run of the workspace answers beside it. How its workspace's tests read from ticket 4.3 is that ticket's scope clause on a workspace whose run stored last covers no module.
- **A run that covers no module replaces no earlier result** (ruled, 13:31, (a)). A run planned from a workspace whose discovery entry is not `discovered` (the scheduler runs every entry that is not `not-confirmed`, `#confirmed` in `daemon/scheduler.ts`) is sent its whole workspace, but the discovery lists no module for it, so it covers only what it recorded, which is nothing when it also fails to load. The earlier results of its workspace stay. No answer changes in this ticket; ticket 4.3's scope holds what such a workspace's tests read.
- **The latest result of a Vitest workspace the worktree no longer has stays**, as the Results store section already says of its last run.
- **The latest result of a test module that left its workspace stays, until ticket 4.4 lands** (ruled by the orchestrator, 13:08). A test module whose file is deleted, renamed or moved is sent to no later run and recorded by none, so no stored run covers it again, and the run that covered it last is never left with none. The store can therefore hold more than one run of a workspace: the one stored last, and each earlier run that still holds the last result of a departed module. A run that covers none likewise stands beside the earlier runs it replaced nothing of, until a run covers their modules. No answer is wrong for it: nothing reads a module the discovery does not list, a module that comes back is rated by its own fingerprint, and dropping a result can only cost a rerun. The cost is the store's size and, from ticket 4.3, what the per-module read pays to pass over those rows. Measured on Fleet Cooling at 13:02 on 2026-10-02, from git's object store only (`git --no-optional-locks -C C:/source/fleetcooling log -n 500 --no-merges --diff-filter=DR --name-status -M --format= -- '*.test.ts' '*.test.tsx' '*.spec.ts' '*.spec.tsx'`), and counted again by the orchestrator at 13:06: 137 test files deleted and 31 renamed in its last 500 commits, 2026-09-15 to 2026-10-02, against 962 test modules now. Computed, never run: at its mean of about 16 tests a module (14,994 tests in 962 modules, in a store of 6.6 MB), 168 departed modules are about 2,700 test rows, at most about 1.2 MB in 17 days if every one had a stored result. The count is of committed deletions and renames on one branch: a test file an agent adds and removes between commits, and a switch of branch, are not in it, so as a rate of departure it is a floor. Ticket 4.4 ends it: there a stored discovery removes the stored results of the test modules a discovered workspace no longer lists.

### The log entry's wording

One entry for a stored run, in one of two forms, the path being the workspace's, the numbers decimal, and the words around them fixed whatever the numbers (`1 test modules covered`), so a reader parses one shape:

- `run stored: packages/a under fingerprint sha256:9F86D081884C7D65, 12 test modules covered, 0 stored again under the fingerprint they held`
- `run stored: packages/a not fingerprinted, 12 test modules covered, 0 stored again under the fingerprint they held`

The entry names nothing else of the run's bindings. The entry `<job> is stored not fingerprinted: <reason>`, which `storeBindings` writes ahead of the write, stays as it is and names no stored run.
