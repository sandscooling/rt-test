# Ticket 3.6: Canary gate on the consumer's Vitest

## Ticket

As a coding agent or a developer reading defect evidence in a started project,
I want the daemon to falsify a workspace only once RT Test's canaries have read as named on the Vitest that workspace installed, and to say so when they have not,
so that a Vitest release that records run facts differently is refused by name instead of crediting a detection that never happened.

## Acceptance Criteria

A workspace's **Vitest install** and a **canary reading** (confirmed, disagreed, or no reading) are as the glossary and ticket 3.5b define them. A **canary job** is the one executor job a reading takes: it runs the canary fixtures as a falsification job runs a workspace's waiting defects, and is no workspace's falsification job. Where a criterion here says a workspace's falsification job, or its job, it means the job over that workspace's own definitions, never a canary job. An install is **unread** while this daemon holds no reading of it.

- [ ] AC1: The daemon sends a workspace's falsification job only while it holds a confirmed reading of that workspace's Vitest install, taken in this daemon's life. When a look has picked a workspace whose install is unread, the canary job is that look's one job in place of the falsification job, and the daemon plans again when it ends, so an ordinary job that became due goes first and the next look sends the workspace's own job once the reading is confirmed. The canaries run for no workspace whose job is not about to be sent. A reading that is confirmed or disagreed is kept until the daemon stops: the canaries run at most once in a daemon's life for each install that gave one, however many workspaces resolve it and however many jobs follow. (FR23)
- [ ] AC2: A workspace whose install's reading disagreed is sent no falsification job while it resolves that install, and nothing is stored for it. At each input revision at which a look picks it, it is a workspace whose job did not run (ticket 3.5's AC6), marked by the look whose canary job disagreed, unless a stop arrived or the input revision moved while that job ran, and from the kept reading with no canary job at every look after it, so the next look takes the next workspace's definitions and every workspace on a confirmed install is still falsified. Its reason names the Vitest version and the falsifier version and then the canaries that disagreed by id, each with the judgement it read and the judgement named, and says what ends the refusal: the workspace resolving another Vitest install, or a restart of the daemon. What it says of the versions and the canaries is bounded as ticket 3.5 bounds what happened to any workspace whose job did not run, and says how much more the log holds, so an answer's cut never loses the ending and what the bound drops is canaries alone, each of which the log holds (AC5). Beyond its fixed wording, that reason holds versions, canary ids and judgement names alone, and no text a consumer or an error wrote. (FR23)
- [ ] AC3: Nothing is kept of a canary job that gave no reading, and no job is sent for a workspace that resolves no supported Vitest. In each case the workspace is one whose job did not run at that input revision (ticket 3.5's AC6), its reason naming the Vitest version where one resolved, and saying what happened and that a change of the input revision ends the wait, worded and bounded as ticket 3.5 words every such reason, so an answer's cut never loses the ending. The canaries run again when a look next picks a workspace on that install: another workspace on it at that revision, or any workspace on it at another. A change of the input revision, or a stop, ends a running canary job as ticket 3.5's AC4 ends a falsification job: it is aborted and ends within the executor's bound, a job so ended that gave no reading marks no workspace and keeps nothing, and no discovery and no run waits for it. The time bound of ticket 3.5's AC5 ends a canary job as it ends any job, and a job it ended that gave no reading marks its workspace as one whose job did not run. (FR23)
- [ ] AC4: A change the tracker records while a canary job runs is an edit, as ticket 3.5's AC7 makes one recorded while a falsification job runs: it ends the job as AC3 says, it counts toward holding no workspace and not the discovery, and it releases a hold it reaches as any edit does. Nothing of a canary job, neither its begin nor any way it ends, is told to the change record. (FR23)
- [ ] AC5: While a canary job runs, the daemon's activity reads falsifying, with the workspace the look picked and 0 as the number of its definitions in the job, since a canary job holds none of them. A workspace AC2 or AC3 marks appears in every answer and in `status` as ticket 3.5's AC8 lists a workspace whose job did not run: one entry marked as a falsification job, with the reason of AC2 or AC3, from the look that marked it until the input revision changes, and again from the next look that picks it. The daemon's log names each canary job as it starts (the workspace, the Vitest version and the install's directory) and as it ends (confirmed, or every canary that disagreed with what it read and what is named, or why it gave no reading, and its wall time), and names each workspace it marks with its reason, as it names every workspace whose job did not run. The protocol version and the CLI's JSON schema version stay as they are. (FR23)
- [ ] AC6: A canary job stores no run, no discovery and no evidence, and moves no input revision wherever the state directory lies. Neither it nor a reading changes a test's state or freshness, a definition's state, eligibility or evidence freshness, a count of any answer, whether a query answers, or a workspace's execution state: the entry AC5 lists is all an answer gains. Where no reading's directory was left behind in the state directory, no test or module of the canary set appears in a discovery or in any answer. (FR23)
- [x] AC7: Resolving a workspace's Vitest answers what resolves from its directory when it is asked, also in a process that resolved it before. Once a workspace's `node_modules/vitest` link points at another install, the next resolution gives that install's directory and version, whether the first install is still in place or gone, and a directory from which none resolved gives the install that has since appeared. So a workspace that comes to resolve another install while the daemon runs is on an unread install from the next look that picks it, with no restart (AC1), and a refused workspace that does is refused no longer from that look (AC2). (FR23)

#### What the criteria rest on

FR23: "Refuse to falsify in a Vitest workspace whose Vitest version RT Test's canary fixtures have not confirmed its run facts against, naming the version and the canary that disagreed."

ADR-0008: "So RT Test ships canary fixtures, each failing on purpose in one known way, which its own suite checks on both supported Vitest lines. Before a workspace's first falsification in a daemon's life, the daemon runs those canaries under that workspace's Vitest install from its state directory and keeps the reading in memory, one for each install, until it stops; an install whose reading disagrees with any canary is refused falsification, naming the version and the canary." And, rejected there: "trusting these facts on a version no canary has confirmed."

Glossary, verbatim: **Vitest install**: "The Vitest that resolves from a Vitest workspace's directory, told apart by the package's real directory and its version. Several workspaces can resolve one install." **Canary reading**: "What one canary job showed under a Vitest install: confirmed when every canary read the verdict and reason named for it, disagreed with the canaries that did not, or no reading otherwise." **Canary job**: "The one executor job a canary reading takes. It runs the canary fixtures as a falsification job runs a workspace's waiting defects, and is no workspace's falsification job." **Falsification job**: "One executor job that runs, for some of one Vitest workspace's waiting defects, the baseline, each defect's experiment and the restored baseline in one Vitest instance." **Waiting defect**: "An eligible defect whose evidence is missing or not current, which the daemon falsifies when no ordinary job is due."

`docs/architecture.md` § What counts as an input: "The inputs are every file under the consumer root except `.git`, `node_modules`, the daemon's state directory and log file", which is why AC6's job moves no input revision.

#### The seam as built

As the code reads on main at 75bf2712 (§ Where this ticket stands).

- `Falsification.look(plannedRevision)` in `daemon/falsification.ts` waits for the inputs to settle, checks the stop and the revision, and calls `worktreeStandings` with a moment that opens the job's window on the tracker (`inputs.beginJob()`) in the same tick it reads the lifecycle's moment. `#begin`, which holds no await, checks the stop and the revision again, asks the plan for the next job, and calls `#send`. A look whose `#begin` returned true or false closes the window in a `finally` and resolves that value; a look that sent a job awaits its outcome, releases its watch, closes the window, and calls `#settle`, then resolves true.
- `#send(job, read, revision, mark)` finds the workspace's entry in the discovery the standings were read with and its confirmed config, and the workspace's fingerprint digest, calling `#waits` and returning true when either is missing. Then it writes the start entry, sets the activity to `{ state: "falsifying", workspacePath, definitions }` and sends the job on `parts.executor.falsify`, with `#watch(revision)`. The gate is asked between the fingerprint check and the start entry.
- `#waits(job, revision, what)` marks the workspace through `FalsificationPlan.workspaceWaits` with `what`, on one line and cut to 400 characters (`MAX_HAPPENED_CHARACTERS`, "so what ends each wait stays inside an answer's cut of a reason"), followed by "so no further falsification job of the workspace begins until the input revision changes", writes `what` whole with that ending to the log, and returns true. #### Design decisions (scope of analysis: what the daemon keeps of a reading, when it takes one, when it refuses and what answers say; how the set is placed, run and read is ticket 3.5b's; a store record of a reading is unanalyzed beyond decision 1)

Each stands with doing nothing and one coarser rule beside it. The orchestrator at 08:12 on 2026-10-01: the author's choices outside its rulings (design decisions 1, 5 and 8, and the split that made ticket 3.5b) "stand as yours".

1. **The reading is kept in the daemon's memory, for its life** (orchestrator, 08:12 on 2026-10-01: "ACCEPTED: the reading is kept in memory, once in a daemon's life for each Vitest install a workspace resolves, and no store record"). Do nothing, the canaries before every job, costs about 10 s on each job for as long as RT Test runs. A store record costs schema version 12, a table, a store module and the composition of `STORE_MIGRATIONS`, to save one canary job at each daemon start, and it would key by a version text, so it would confirm another install, platform or Node line of that version without reading it, and a disagreement stored on a flake would refuse until someone deleted state. In memory, each daemon life reads the install it runs. So this ticket raises no schema version.
2. **Keyed by the install: its real directory and its version.** By workspace would run five canary jobs at Fleet Cooling for one install. By version text alone would let one install's reading stand for another's. The version beside the directory covers an upgrade in place under a layout that keeps one path.
3. **A reading that is confirmed or disagreed is kept; no reading keeps nothing.** Keeping confirmations alone would run the canaries again for each workspace on a refused install at each input revision, five canary jobs a revision at Fleet Cooling's shape, to learn what is already known (C37). Keeping a no reading for its install until the input revision changes would save the canary jobs of the install's other workspaces at that revision, and costs the gate the input revision in what it keeps and in what it is asked; Fleet Cooling's install reads confirmed, so it meets none of them, and the cost is a known limit.
4. **The canary job is the look's one job.** An awaited canary job between the look and the send would hold the look's window on the tracker open through it, so the falsification job that follows would be sent on standings and a fingerprint read 7 to 18 s earlier, and an event naming an input in that stretch would leave its reply unstorable (ticket 3.5's AC3), wasting that job.
5. **Answers name a refusal through ticket 3.5's entry for a workspace whose job did not run** (orchestrator, 08:12: "ACCEPTED: a refused workspace is 3.5's workspace whose job did not run, with your reason, and the lapse is a recorded known limit"). The exact alternative, entries listed from the gate's own memory, adds a second map by workspace, a rule for when an entry leaves, and a dedupe against the mark's entry.
6. **The activity reads falsifying during a canary job, with 0 definitions.** Do nothing leaves the activity idle while an executor job runs. The number of definitions the look picked would read "with 2 of its defect definitions in the job" of a job that holds none of them. A state of its own changes `daemon/protocol.ts` and `query/answer.ts`, raises the protocol version a second time in the sprint, and tells a reader nothing it acts on for a job of seconds; the log tells the two apart.
7. **The gate is a part the lifecycle is given.** The lifecycle's tests run a `ScriptedExecutor` over consumers under a temporary directory, where no Vitest resolves, so a gate the lifecycle built for itself would refuse every job those tests send.
8. **A change to the canary set raises `FALSIFIER_VERSION`** (orchestrator, 08:12: "yes"). Evidence stored before the change was confirmed by the set as it was. `docs/architecture.md` holds the sentence since ticket 3.5b.
9. **Every mark is made through `#waits`, which takes what ends the wait.** A no reading and an unsupported Vitest end at a change of the input revision, as every workspace whose job did not run; a refusal ends elsewhere, so `#waits` is handed its ending. What happened is then cut to 400 characters in the mark and whole in the log, for a refusal as for any workspace, so no reason pushes what ends a wait past the 1,000 characters an answer keeps, in an entry of a workspace's part and its definitions' part too. The other way, the gate's whole reason handed to the plan's `workspaceWaits` with the ending before the canaries, names up to 20 canaries in an answer where this names about four, and costs a second way to make a mark and a reason of some 2,000 characters. Ticket 3.5's review named the parameter for this ticket (orchestrator, 15:42 on 2026-10-01); decided by the author at 15:43 and accepted by the orchestrator at 15:47.
10. **The resolver answers from the disk at each call** (orchestrator, 16:05 on 2026-10-01, on the dev's question of 16:03; AC7). `require.resolve` keeps its answer for the life of a process (U1), so in the daemon's process a workspace whose Vitest was upgraded still resolved the old install: the gate answered confirmed from the old reading, the job's fresh executor loaded the new Vitest, and its evidence was stored under a version no canary job read, for the rest of that daemon's life. The resolver walks Node's own lookup list in place of that call, about ten lines with the file's nine records proven again, and adds no rule, mark or wording. Do nothing is a known limit to restart the daemon after every Vitest upgrade, with FR23 unmet until then and nothing saying so. A check in the gate that marks the workspace "restart the daemon" adds a mark and a wording and still asks for the restart. A check of the reply's Vitest version in `daemon/falsification.ts` handles it after a whole job ran. `module.findPackageJSON` needs Node 22.14 where `engines` admits 22.13.0, and clearing Node's cache reaches an undocumented internal.

#### Known limits (each entry says what a consumer would see and what must coincide)

- While ordinary work is due after an edit, no answer names a refusal until the next look makes the mark again: an author querying in that stretch reads the workspace's definitions as never verified or stale with no entry beside them. It is seen only in a workspace whose Vitest the canaries disagree with, which Fleet Cooling's 4.1.11 is not (orchestrator, 08:12).
- A reading that disagreed through a flake refuses every workspace on that install until the daemon restarts, with the canary named in every entry. It needs a canary to read differently once on an install that reads it as named; this repository's suite runs the set in every gate.
- A Vitest patched in place, at the same directory and version, keeps its reading until the daemon restarts. Fleet Cooling patches no dependency.
- When an install replaces Vitest after a look's gate answered and before the job loads it, that job's evidence is stored under a version with no reading. It needs a Vitest version change to land in `node_modules` in the seconds between the two.
- A workspace on a refused install costs one look at each input revision, to be marked again from memory.
- A refused workspace that comes to resolve another install with no input changing, by a change under `node_modules` alone, keeps its entry and its refusal until the input revision next changes, though its reason says another install ends the refusal: the gate is asked only at a look, and a marked workspace gets none at its revision. It needs an install replaced with no manifest or lockfile written.
- The readings are kept in memory only, so every daemon start takes one canary job for each install before that install's first falsification job.
- While edits arrive closer together than a canary job takes (8 to 19 s as measured), each ends the canary job with nothing kept, so the install stays unread and nothing on it is falsified until a pause that long. No entry says so, since a job so ended marks no workspace; the activity and the log do. A falsification job is ended the same way and takes longer (about 95 s for 25 definitions by ticket 3.5's estimate), so no pause that lets one finish is too short for a canary job.
- An install whose canary job keeps giving no reading costs one canary job for each of its workspaces that a look picks at each input revision: the milliseconds of a set that cannot be placed, or up to the time bound when a canary job hangs. Fleet Cooling's install read confirmed in ticket 3.5b's spike.
- For a refused workspace, the log's line for a look that took none counts it among the workspaces that get "no further falsification job until the input revision changes", while its entry and its own mark's log line say what ends the refusal. The docblocks of `FalsificationPlan` in `daemon/falsification-plan.ts` and of `UnstoredJob` in `daemon/protocol.ts` say the same of every marked workspace. Each is true of the mark, which holds one input revision, and none is an answer's text, so this ticket edits neither file; a test pins that log line. It is read only in the log of a consumer whose Vitest the canaries disagree with.
