# Sprint 3: Falsification

**Milestone:** M2

Take falsification off coding agents. The daemon reads the defect definitions a consumer commits, falsifies each defect whose test currently passes, and answers which defects have current evidence that their test detects them, which cannot run and why, and which tests have no defect. Today an agent on Fleet Cooling writes a mutation spec, runs `scripts/falsify.mjs`, reads its verdicts and repeats that for every test it adds; after this sprint the daemon does it at lower priority than ordinary tests and re-verifies a defect whenever its inputs change. It ports `falsify.mjs` with its file writes replaced by in-memory transforms in one reused Vitest instance per job (ADR-0003, ADR-0007), its message classifier replaced by Vitest's recorded task facts confirmed per Vitest version by canary fixtures (ADR-0008), and its per-run spec replaced by definitions committed in the consumer (ADR-0004, ADR-0009).

The roadmap's first spike, plugin transforms under Vitest 4.1, held on 4.1.11 and 5.0.1 on 2026-09-30 (ADR-0007, ADR-0008). A second spike that day showed a reach probe recording, on both lines, exactly which test executed the mutated site, so a test that fails an assertion without executing it is never credited (orchestrator, 17:43, on module-level reach). Two spike questions remain and open the tickets that rest on them: 3.2 checks the module id spelling a transform receives on Windows under each Vitest line, and the stale-transform guard on 4.1, which was measured only on 5.0.1; 3.6 checks how the bundled canaries run under a workspace's Vitest from the state directory.

Evidence freshness has workspace granularity (ADR-0007): an edit anywhere in a workspace's inputs stales every defect in it, and M3's file-level dependencies narrow that. Fleet Cooling commits no defect definitions today (its mutation specs live in change records), so the M2 trial there needs definitions written in its repository first, in ADR-0009's format.

Order: 3.1 and 3.2 build in parallel, since 3.1 works in the daemon's query, protocol and CLI and 3.2 in its Vitest session and executor. 3.3 follows 3.2, whose experiment records it judges. 3.3b follows 3.3, whose record it adds one member to. 3.4 follows 3.1, 3.3 and 3.3b, storing 3.3's verdicts against 3.1's definitions and 3.3b's digest. 3.4c follows 3.4, whose definition digest and standings it changes. 3.5 follows 3.4c, since a scheduled job stores evidence, takes its definitions from 3.4c's function and hands its job the names 3.4c reads. 3.4b follows 3.5, which decides what of the definition files the daemon keeps between queries and writes `daemon/lifecycle.ts` as 3.4b does, and lands before 3.7, which measures the counts. 3.6 follows 3.5, gating the job 3.5 starts. 3.7 measures the milestone's acceptance. 3.8 comes last, once RT Test runs this repository's own suite, since its evidence needs this repository started under RT Test. Each ticket is estimated at 30 files or fewer.

## Ticket 3.1: Defect definitions and gaps

Scope: read the definition files `rt-test.json`'s `defects` member lists, validate each definition, resolve its test against the latest discovery and its anchor against the file as it is now, and answer `rt-test defects` with each definition's state (never verified, anchor missing, or invalid with its reason), the counts, and the tests no definition names as gaps, bounded like the other answers and without starting a test. Requirements: FR12, FR13, FR14, FR22, FR24. Ticket file: [3-1-defect-definitions](../tickets/3-1-defect-definitions.md)

## Ticket 3.2: Transform experiments in a reused instance

Scope: a falsification job in the daemon's executor loads one Vitest instance for a workspace, applies each mutation where every project's Vite server hands a module's text to its plugins, runs the intended tests' modules as a baseline, each defect's experiment alone, and the restored baseline, behind the stale-transform guard; the transform places a reach probe at each mutated site, or records that none can be placed, and a setup file RT Test places first marks each test that executed it; the job reads each run's facts only from the modules it executed and returns one raw record per experiment, on Vitest 4.1 and 5, leaving every consumer file byte-identical. Requirements: FR10, FR11, NFR6. Ticket file: [3-2-transform-experiments](../tickets/3-2-transform-experiments.md)

## Ticket 3.3: Verdicts from run facts

Scope: turn each experiment record into the facts ADR-0008 names (the intended test's state by stable identity, its error kinds including declared ones, hook states, module, suite and unhandled errors, whether the mutated site executed during that test, and both baselines), decide detected, survived, invalid experiment or unclear from them alone, and confirm each would-be detection by one confirming run in the same instance, over canary fixtures committed for both Vitest lines that each fail in one known way, including a test that fails an assertion without executing the mutated site. 3.2's job runs each experiment once, over its intended test's whole module as the baselines run it, and keeps one experiment callable again in the same instance before the restored baseline; 3.3 adds the confirming run there, and raises `FALSIFIER_VERSION`. A definition naming an `it.skip` or `it.todo` test resolves and reads never verified, and the resolved test's mode is carried (3.1's review). From 3.2's review: an unhandled error a stopping worker reports late appears in the next run's record, so a would-be detection followed by one reads unclear; `experiment()` has no baseline gate of its own, so the confirming run goes through the gate; a chai `AssertionError` carries no constructor field, only an `expect.extend` failure carries the `JestExtendError` marker, and a hook that threw stays `run`; the record carries no retry facts, so a baseline that passed only on a retry reads as a plain pass and a reach mark carries across retries; and on Vitest 5 vm pools the main process prewarms a file's imports, so a non-empty transform list does not prove a worker loaded the module. Requirements: FR11, NFR7. Ticket file: [3-3-verdicts-from-facts](../tickets/3-3-verdicts-from-facts.md)

## Ticket 3.5: Schedule falsification

Scope: once no ordinary job is due or running, the daemon falsifies the eligible defects whose evidence is not current, in jobs of at most 25 definitions of one workspace (a target until measured), problem and new definitions first; a job ends at any change of the input revision and at a time bound, stores nothing when its inputs moved, and every answer says what falsification is doing and which definitions it left without a verdict. 3.2's job takes each mutation's file as an absolute path; it forces per-file isolation; when aborted it replies interrupted with only its finished runs and no restored baseline; when its executor process dies it returns nothing, with the reason. The daemon tells the change record of each falsification job's begin and every way it ends, as it does for runs and discoveries, so a job that writes its own inputs cannot escape the self-change counts (2.7b's review). `daemon/lifecycle.ts` holds 498 of its 500 code lines. The anchor count reads a mutation's file as UTF-8, keeps a byte order mark, and reads only a regular file (`readMutationFile` in `defects/resolve-definitions.ts`); falsification reads it the same way or the two counts can disagree (3.1's review). From 3.2's review: decide moved inputs from the change events during the job, never from equal fingerprints at its start and end, since a transient edit the restored baseline no longer sees leaves a record that reads like a detection; a mutation that loops forever holds the job until aborted, and the first experiment reading interrupted is the one that was running; `Executor.#job` has no guard against a second job on a busy Executor, so say which Executor falsification uses; and a not-ended outcome tells a crash from a stop only by its reason text. Pass the job the assertion error names 3.4c reads from `rt-test.json`, as 3.3's `Executor.falsify` takes them. 3.4's store takes a job's reply through `store.writeEvidence(bindings, job, definitionDigests)`: the store scope with the digest of the workspace's input fingerprint the job ran at, the `ran` reply whole, and each defect id's definition digest, taken from the standing of the definition its experiment was built from (`defects/defect-standings.ts`). Call it only for a job whose inputs did not move. It throws, storing nothing of the reply, when a verdict's defect has no digest handed in. Pick each workspace's eligible definitions that read never verified or whose evidence freshness is not current from the standings 3.4c's function gives, so eligible and current are each decided once. A job given no experiment reads `ran` with no baseline and an empty list of judgements. A job whose every experiment was decided before any run reads `ran` with no baseline and one judgement for each, of which a no-probe-site and a no-module judgement are invalid experiment verdicts that `writeEvidence` stores (3.3's review, corrected by 3.4's). An executor reply is accepted by its type alone, so `Executor.falsify` can return an ended outcome with no job: treat an ended outcome whose value is not an object as a not-ended one, so the reason is named and `writeEvidence` is never handed it (3.3's review). From 3.3b's review: each experiment record carries `mutationFileDigest`, which covers an edit to the mutation's file that still stands when a query reads it, and nothing else, so an input edited during a job and restored is refused from the change events; the job reads each mutation's file after its Vitest instance has loaded, so the window in which a moved input stores nothing runs from the fingerprint handed to the store to the job's end, the load included; give each mutation's file one spelling, since the job reads a file once for each spelling it is given; and `falsify/falsify-workspace.ts` holds 474 of its 500 code lines, so a ticket that needs more than 26 there first extracts the start-of-job planning. From 3.4's review: hand `defectStandings` the consumer root exactly as `checkDefinitions` was given it, or every digest it stores differs from the one the query computes and all evidence reads stale; `RecordingStore` in `test/scheduling-harness.ts` gives every discovery the id "discovery", its `writeEvidence` always throws and its latest results hold no evidence, so give it a recording write before a lifecycle test stores evidence through it; the store keeps a worktree's evidence between reads and rebuilds every record only on the first read after each `writeEvidence` call or another connection's commit, a median of 180 ms at 10,812 records (`docs/architecture.md` § Results store), so store one reply for each job and never one for each experiment; and `test/experiment-facts.ts` imports the harness for one constant, repeats `RanJob` and a `judgementOf` of `test/falsify/job-readings.ts`, and exports three names nothing imports. A change to where a reach probe stands or to which changes have no probe site raises `FALSIFIER_VERSION`, since evidence is bound to it. Requirements: FR8, FR10, FR13, FR15, FR22. Ticket file: [3-5-schedule-falsification](../tickets/3-5-schedule-falsification.md)

## Ticket 3.6: Canary gate on the consumer's Vitest

Scope: before a workspace's first falsification on a Vitest version, run RT Test's bundled canaries under that workspace's Vitest from the state directory, keep the result per Vitest and falsifier version, and refuse falsification on a version whose reading disagrees, naming the version and the canary in every answer. 3.3's canaries are `packages/daemon/canaries/`: plain `.mjs` importing no package but `vitest`, test modules named `*.canary.mjs`, and `canaries.json` naming each canary's test, mutation and the one judgement it must read, with the assertion error names the set's job is given. The set holds 24 canaries, and the order of its list carries a case: the canary that leaks an unhandled rejection comes directly after one that does not read detected, and is never the last. `mutation.file` is relative to the directory, the reader supplies the workspace path and occurrence 0, and `body.canary.mjs` imports `canaries.json` for the declared error name, so the two travel together. From 3.4's review: each entry of `STORE_MIGRATIONS` spells its whole path to the current version, so a schema raise edits every entry and re-anchors 17 records; compose each entry from one step per version when this ticket raises it. Requirements: FR11, FR23.
