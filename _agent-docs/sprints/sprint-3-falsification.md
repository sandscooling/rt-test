# Sprint 3: Falsification

**Milestone:** M2

Take falsification off coding agents. The daemon reads the defect definitions a consumer commits, falsifies each defect whose test currently passes, and answers which defects have current evidence that their test detects them, which cannot run and why, and which tests have no defect. Today an agent on Fleet Cooling writes a mutation spec, runs `scripts/falsify.mjs`, reads its verdicts and repeats that for every test it adds; after this sprint the daemon does it at lower priority than ordinary tests and re-verifies a defect whenever its inputs change. It ports `falsify.mjs` with its file writes replaced by in-memory transforms in one reused Vitest instance per job (ADR-0003, ADR-0007), its message classifier replaced by Vitest's recorded task facts confirmed per Vitest version by canary fixtures (ADR-0008), and its per-run spec replaced by definitions committed in the consumer (ADR-0004, ADR-0009).

The roadmap's first spike, plugin transforms under Vitest 4.1, held on 4.1.11 and 5.0.1 on 2026-09-30 (ADR-0007, ADR-0008). A second spike that day showed a reach probe recording, on both lines, exactly which test executed the mutated site, so a test that fails an assertion without executing it is never credited (orchestrator, 17:43, on module-level reach). Two spike questions remain and open the tickets that rest on them: 3.2 checks the module id spelling a transform receives on Windows under each Vitest line, and the stale-transform guard on 4.1, which was measured only on 5.0.1; 3.5b and 3.6 rest on how the bundled canaries run under a workspace's Vitest from the state directory, which was run on both lines, on Windows and on Linux, before either was written (§ Ticket 3.5b).

Evidence freshness has workspace granularity (ADR-0007): an edit anywhere in a workspace's inputs stales every defect in it, and M3's file-level dependencies narrow that. Fleet Cooling commits no defect definitions today (its mutation specs live in change records), so the M2 trial there needs definitions written in its repository first, in ADR-0009's format.

Order: 3.1 and 3.2 build in parallel, since 3.1 works in the daemon's query, protocol and CLI and 3.2 in its Vitest session and executor. 3.3 follows 3.2, whose experiment records it judges. 3.3b follows 3.3, whose record it adds one member to. 3.4 follows 3.1, 3.3 and 3.3b, storing 3.3's verdicts against 3.1's definitions and 3.3b's digest. 3.4c follows 3.4, whose definition digest and standings it changes. 3.5 follows 3.4c, since a scheduled job stores evidence, takes its definitions from 3.4c's function and hands its job the names 3.4c reads. 3.5b follows 3.3, whose canary set it runs, and builds beside 3.5, sharing no file with it but a defects file. 3.6 follows 3.5, gating the job 3.5 starts, and 3.5b, whose reading it keeps. 3.7 measures the milestone's acceptance. 3.8 comes last, once RT Test runs this repository's own suite, since its evidence needs this repository started under RT Test. Each ticket is estimated at 30 files or fewer.

## Ticket 3.3: Verdicts from run facts

Scope: turn each experiment record into the facts ADR-0008 names (the intended test's state by stable identity, its error kinds including declared ones, hook states, module, suite and unhandled errors, whether the mutated site executed during that test, and both baselines), decide detected, survived, invalid experiment or unclear from them alone, and confirm each would-be detection by one confirming run in the same instance, over canary fixtures committed for both Vitest lines that each fail in one known way, including a test that fails an assertion without executing the mutated site. 3.2's job runs each experiment once, over its intended test's whole module as the baselines run it, and keeps one experiment callable again in the same instance before the restored baseline; 3.3 adds the confirming run there, and raises `FALSIFIER_VERSION`. A definition naming an `it.skip` or `it.todo` test resolves and reads never verified, and the resolved test's mode is carried (3.1's review). From 3.2's review: an unhandled error a stopping worker reports late appears in the next run's record, so a would-be detection followed by one reads unclear; `experiment()` has no baseline gate of its own, so the confirming run goes through the gate; a chai `AssertionError` carries no constructor field, only an `expect.extend` failure carries the `JestExtendError` marker, and a hook that threw stays `run`; the record carries no retry facts, so a baseline that passed only on a retry reads as a plain pass and a reach mark carries across retries; and on Vitest 5 vm pools the main process prewarms a file's imports, so a non-empty transform list does not prove a worker loaded the module. Requirements: FR11, NFR7. Ticket file: [3-3-verdicts-from-facts](../tickets/3-3-verdicts-from-facts.md)

## Ticket 3.5: Schedule falsification

Scope: once no ordinary job is due or running, the daemon falsifies the eligible defects whose evidence is not current, in jobs of at most 25 definitions of one workspace (a target until measured), problem and new definitions first; a job ends at any change of the input revision and at a time bound, stores nothing when its inputs moved, and every answer says what falsification is doing and which definitions it left without a verdict. 3.2's job takes each mutation's file as an absolute path; it forces per-file isolation; when aborted it replies interrupted with only its finished runs and no restored baseline; when its executor process dies it returns nothing, with the reason.
