# Sprint 4: File-level results and selection

**Milestone:** M3

Make RT Test a gain in an agent's edit loop. M2's trial on Fleet Cooling measured on 2026-10-02 that selecting by workspace is not one: every workspace there depends on its Convex workspace, so one edit in it reran all 14,994 tests (the Convex answer 3 min 41 s after the save, everything 7 min 36 s after it, restarted by every save), a leaf app edit cost that app's whole run (1 min 50 s), and 13.5 s passed before any run started, where its agents get an answer in 1.5 to 4.3 s from the one to five test files they name themselves (owner, 10:16: "This seems like a stopper to me because, when we are actually editing and moving through things, RT Test is going to be in a constant state of redoing tests, which will take several minutes."). A spike that morning and Fleet Cooling's own timings showed what makes it a gain, and the owner asked for it planned (12:00: "Yeah, let's go ahead and plan this out."). This sprint builds it in three parts: results stored, rated and run by test module, with the modules nearest an edit run first as a small run of their own ([ADR-0010](../../docs/adr/0010-results-by-test-module.md), [ADR-0012](../../docs/adr/0012-small-runs-nearest-first.md)); a dependency graph scanned once and updated for the files a save changed; and selection narrowed by what each test module loaded in its last run, read beside that graph and never alone ([ADR-0011](../../docs/adr/0011-load-record-beside-dependency-graph.md)).

What it does not do. A file most test modules load still selects them all: 79 of the 175 Convex source files in Fleet Cooling's last 100 commits reach 263 or more of its 583 Convex test files by real static edges, and those 263 take 172.7 s of the suite's 191 s. For such a file the sprint gives the nearest modules first and nothing more. A test module that can read a file or start code by path keeps its workspace's whole inputs, so in this repository, whose daemon and CLI tests do both, nothing narrows, and its own named defects stay with the bootstrap verifier. No language server, no shared local Convex backend and no Vitest instance kept open between runs is part of it (ADR-0011, ADR-0012), and it ports no Convex adapter.

The figures the tickets quote were measured on 2026-10-02 on a Ryzen 7 8700F with 16 logical CPUs and 32 GB, Windows 11 build 26300, Node 24.19.0 and Vitest 4.1.11, with a warm file cache and real-time protection on: by the spike over consumers written for it (952, 3,250 and 3,365 source files), and by Fleet Cooling's orchestrator on its own suite with plain Vitest. A figure marked computed is arithmetic over measured parts and was never run. Not measured by either: Linux, a cold file cache, Vitest 5.

Order: 4.1 and 4.2 build side by side, since 4.1 works in the source scan and the dependency builds and 4.2 in the store. 4.1 follows the queued scan-widening change, which edits the same scan files, and 4.2 follows lane store-growth, whose replacement rule it restates. 4.3 follows 4.2. 4.5 follows 4.1 (the executor's job types) and 4.2 (the schema), beside 4.3. 4.4 follows 4.1 and 4.3. 4.6 follows 4.3, 4.4 (the scheduler) and 4.5. 4.7 follows 4.1 and 4.6, 4.8 follows 4.7, 4.9 follows 4.5, 4.8 and the measurement of the record named below, and 4.11 measures the milestone's acceptance after 4.9. 4.10 comes last. Each ticket is estimated at 30 files or fewer.

The owner stops the sprint after 4.6. Once 4.6 has landed and the trial build is repinned, he sees two things on Fleet Cooling before 4.7 onward is built: nearest first with measured figures in place of the computed ones below, and how many test modules load each of its source files by 4.5's record on its real suite, which is also the measurement 4.9 waits for. 4.10 is started only once Fleet Cooling has defect definitions committed: until then no consumer holds evidence for an edit to stale, and from that day every edit stales every definition of its workspace until 4.10 lands. The owner asked for the plan at 12:41 on 2026-10-02 ("Yeah, I have the change request go through the inline path. It will create all the documentation needed for this sprint.", then "Sorry, I meant have the change request go through the proposal path."). The stop after 4.6 and the place of 4.10 are the orchestrator's reading of that answer, said to him as its own.

## Ticket 4.1: Kept dependency graph

Scope: the source scan yields one record for each source file (each specifier resolved to a file where it is a path, to a package workspace where it is a name, an alias or a tsconfig path, kept as its pattern where it is a glob; whether it holds a module path computed at run time; which Node built-ins it imports; or why it could not be read); the daemon keeps the records for its life and, after a change, sends a build that re-reads only the files that changed, appeared or went away; the workspace-level dependency information every existing rule reads is derived from the records and selects what it selects today; a newly stored discovery starts no build unless the selection input changed; a change to what decides how names resolve (a manifest, a tsconfig or jsconfig, an alias, the package workspace listing) scans whole again. A parse still runs in an executor process of its own behind the parse record. Requirements: FR27. Size: 20 raw files, 26 estimated; the behavior a split would cut is the save that re-reads only what changed, which the scan and the daemon's builds hold together.

Once it lands: the time from a save to a run starting falls on Fleet Cooling from 13.5 s (measured, two whole-tree builds of 4.6 s and 4.9 s around a rediscovery) to about 5.0 s (computed); from 6.0 s to about 1.6 s on the 3,250-file consumer (computed). Rests on, unverified: a build that reads only what changed does not exist, and its 0.17 s is a sum of measured parts; 2.6 s of Fleet Cooling's 13.5 s is not broken down.

## Ticket 4.2: Results stored by test module

Scope: every stored run names the test modules it covered, each with its own input fingerprint, whatever the run's status; the store reads each test module's latest result; a stored run replaces the earlier results of exactly the modules it covers and removes a run left with none, which is what lane store-growth's rule (a stored run replaces its workspace's earlier runs) becomes; the write compares each module's fingerprint with the one it replaces, and the log line that names what a stored run is bound to counts the modules stored again under the same one, which is where NFR1 is read once a run covers part of a workspace; a version 11 store migrates in place, each run covering the modules it recorded under the run's own fingerprint; each entry of `STORE_MIGRATIONS` is composed from one step per version (3.4's review). Callers hand every module its workspace's fingerprint, so no answer changes. Requirements: FR25, NFR1. Size: 12 raw files, 16 estimated.

Once it lands: nothing an agent sees.

## Ticket 4.3: Answers, due and waits by test module

Scope: each test's state and freshness come from its test module's latest result and that module's fingerprint, in `summary`, `status`, `wait`, `changes` and a defect's eligibility; `not-in-latest-run` leaves the states; a test module is due when its latest result is not bound to its current fingerprint, and a workspace while any of its modules is; the lists a rediscovery carries and the discovery's freshness are judged by module; a wait settles once every covering test module reads current or has nothing coming; the edit corpus reads duplicate execution from 4.2's count. Until 4.7 a module's fingerprint is its workspace's, so every answer reads as before. Requirements: FR9, FR25, NFR1, NFR3. Size: 23 raw files, 30 estimated; the behavior a split would cut is one standing for each test, which every answer reads through the same function.

Once it lands: nothing an agent sees.

## Ticket 4.4: Rediscover only when the test module list can change

Scope: a discovery is bound to what decides which test modules exist, the set of input paths and the shared inputs' content, so a content edit to an existing file that is no shared input starts no rediscovery: the run of the selected modules reports their tests, as a stored run's lists already replace the discovery's; an added, deleted or renamed file and a changed shared input rediscover as now; the discovery freshness every answer carries follows the same rule. Requirements: FR27. Size: 10 raw files, 13 estimated.

Once it lands: about 1.4 s less on Fleet Cooling between a save and a run starting (its rediscovery, measured), so about 3.6 s (computed), of which 1.0 s is the quiet window. Rests on, unverified: the 2.6 s of Fleet Cooling's time that is not broken down, which a read of its daemon's log for one save settles before this ticket is written.

## Ticket 4.5: Load record and its canaries

Scope: a setup file RT Test places first reports, at each test module's end, the consumer files its worker executed; a run's reply carries one list for each module it ran, with whether its project ran each module isolated; the store keeps each module's list with its result and drops it with it; the canary set gains record fixtures (a static import, an import by variable inside a test, a lazy glob registry, a barrel, a module mocked by a factory and never loaded), and a canary reading compares each record with its list exactly, so each Vitest install holds a record reading beside its reading of run facts. Nothing selects by the record yet. It opens with the spike its design rests on, on Vitest 4.1 and 5, on Windows and Linux: whether the worker state gives the list at a module's end under each pool and with isolation off, what the setup file adds to a run, and how large the record is for a consumer of Fleet Cooling's dimensions (about 1,000 test modules). Requirements: FR28. Size: 20 raw files, 26 estimated, with about 10 small fixture files beside them as one repeated edit; the behavior a split would cut is a record together with the canary that says whether to trust it.

Once it lands: nothing an agent sees. At the next repin of the trial build, Fleet Cooling's own records say how many test modules load each of its source files, which is the measurement 4.9 waits for. Rests on, unverified: the list is read from `__vitest_worker__.moduleExecutionInfo`, which is not public API and was read on Vitest 4.1.11 on Windows only.

## Ticket 4.6: Runs of named test modules, nearest first

Scope: a run request names the test modules to run, and a round sends each due workspace's due modules as runs of at most 50 (a target until measured on Fleet Cooling), each a new executor process that replies once and is stored whole: first the nearest and no other, however few (the test modules that changed, then those whose usable load record holds a changed file), then the modules whose latest result failed, then the rest; the daemon plans again between two runs; a run's record names every module it was sent; a change interrupts only the run in progress, and the runs already stored stand, each rated by its own fingerprint; every answer names the run in progress as test modules of its workspace. Under a Vitest install with no confirmed record reading the order leaves the record out, and every answer says so. It opens by measuring what one more run costs under jsdom and with a global setup. Requirements: FR26. Size: 22 raw files, 29 estimated; the behavior a split would cut is the nearest modules run as a run of their own, which the run request, the round's queue and the answers name together.

Once it lands: the results of an agent's own test files are stored a run of those files after the run starts, where they wait for their workspace's whole run today: on Fleet Cooling about 5 s after the save when the agent edited the test file (computed: 3.6 s and the 1.54 s Fleet Cooling measured for one Convex test file), and about 8 to 15 s for the 5 to 38 modules nearest a source file (computed from its measured 4.34 s and 11.27 s), against 3 min 41 s (measured). Everything the edit selects still reruns behind them, and a wait on a source file still settles when all of it has. Rests on, unverified: the 1.3 s one more run costs was measured on the spike's consumer only. A known limit: a project's global setup runs once for each run, which no Fleet Cooling workspace has.

## Ticket 4.7: Test module inputs from the dependency graph

Scope: a test module's inputs are its workspace's shared inputs, which hold every file its config or a setup file reaches, and the files the graph says it can reach, or its workspace's whole inputs where the graph cannot tell (a module path computed at run time, a file it cannot read) and where the module, or a file it reaches, imports a Node built-in that reads files or starts code by path; its fingerprint is taken over them; a changed path selects the test modules whose inputs hold it, a new file those whose inputs hold a file that names it by an import or a glob, a deleted or renamed file those whose inputs held it, each with its reason; a module is stale, due, stored under its fingerprint and interrupted by its own inputs; a wait and a `changes` answer cover the tests of the modules their files select; the selection policy version rises. Requirements: FR9, FR16, NFR2, NFR3. Size: 23 raw files, 30 estimated; the behavior a split would cut is selection and staleness deciding from the same inputs, and `create-ticket` splits it between the selection and the schedule if its count grows.

Once it lands: an edit reruns the test modules that can reach the edited file and not every workspace that depends on its workspace. On Fleet Cooling a Convex edit reruns its 583 Convex test modules, which all reach every Convex file through one registry glob, and the app modules that reach the file, in place of all five workspaces (about 3.5 min in place of 7 min 36 s, computed); a leaf app edit reruns the app modules that import the file in place of the app's 1 min 50 s run (not measured there); a wait on an agent's own test file settles about 5 s after the save (computed); and an interrupted round keeps every stored run the new edit cannot reach. Rests on, unverified: how narrow an app's import graph is on Fleet Cooling, and the graph on a consumer with aliases, tsconfig paths and package exports, where it stays at workspace level by design.

## Ticket 4.8: Selection by test module in every answer

Requirements: FR16. Size: 18 raw files, 23 estimated.

Once it lands: no time changes; an agent reads which test modules its edit selected and why any stayed wide.

## Ticket 4.9: Narrowing by the load record

Scope: a test module whose load record is usable (ADR-0011) takes its own files from the record, with every file of a package workspace it reaches by name and holds no file of; every other module keeps 4.7's rule; where neither the record nor the graph can vouch, the module keeps its workspace's whole inputs; a Vitest install with no confirmed record reading narrows nothing by it, and every answer says so; the edit corpus gains the record's cases (a registry, a dispatch by variable, a barrel, a module with no usable record, a project with isolation off, a reader of files, a package loaded outside Vitest's module runner); the selection policy version rises. It is not started until 4.5's record has measured, on Fleet Cooling's real suite, how many test modules load each of its source files. What the built-in rule costs there is measured: 9 of its 962 test modules import `fs`, none imports `child_process` or `worker_threads`, no other source file of its five workspaces imports any of them, and none of its Vitest configs sets isolation or a global setup (counted from its git index on 2026-10-02; a root script a test imports and a library under `node_modules` were not counted). Requirements: FR16, FR28, NFR8. Size: 19 raw files, 25 estimated.

Once it lands: an edit to a file few test modules load reruns those modules alone. On Fleet Cooling 67 of the 175 Convex source files of its last 100 commits reach 40 test files or fewer by its script's graph, and it measured 1.54 s for 1 Convex test file, 4.34 s for 5 and 11.27 s for 38, so everything such an edit can reach reads current about 5 to 15 s after the save (computed), and a wait on the file settles then. A hub file stays near its 583 Convex test modules (172.7 s for the 263, 191 s for all, measured), its nearest first. Rests on, unverified: the 67 is Fleet Cooling's script's graph and not the record; a test module whose loads differ between runs over the same inputs; consumer code that reads files only through a third-party library.

## Ticket 4.10: Defect evidence by test module

Scope: a defect's evidence is bound to its test module's input fingerprint in place of its workspace's, a job hands the store each definition's module fingerprint, and `inputs-changed` is judged by it, so an edit stales the evidence of the test modules it reaches and of no other; evidence stored under the earlier binding reads stale once. It is the sprint's last ticket and is started only once Fleet Cooling has defect definitions committed. Requirements: FR15. Size: 13 raw files, 17 estimated.

Once it lands: nothing on Fleet Cooling until it commits defect definitions; from then an edit sends back to falsification only the definitions of the test modules it reaches, where today it sends every definition of the workspace.
